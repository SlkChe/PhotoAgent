# Инструкции для ИИ Агентов (Codex AI) команды разработки

## Описание проекта "Ассистент фотографа"
Цель, создать чат-бот ассистента фотографа, который будет помогать фотографу в решении следующих задач:
1. Обучение и развитие фотографа через общение на профильные темы:
  - история развития фотографии как искусства;- развитие фототехники и влияние технологий на нее
  - лидеры отрасли и их работы, как они повлияли на фотоисскуство;
  - теоретические основы, объяснения базовых понятий (композиция построения кадра, влияние света и типа освещения, выбор объектива и др.).

2. Практическая работа - диалог строится на анализе готовых фотографий.
Фотограф может загрузить своё фото через интерфейс чат-бота или направить ссылку.
Анализ проводится по множеству критериев (эмоциональная оценка, сюжет, композиция световая схема и др.), отдельно подчеркиваются типичные ошибки или нарушения канонов.

3. Помощь в поиске:
  - профильных книг, альбомов и тематических статей;
  - примеров изображений или серий фотографий;
  - актуальных выставок и мастер-класов
  - оборудования и оснастки (в продаже или для аренды);
  - локаций и студий для проведения съемки;
  - партнеров и заказчиков (например: фотомодели, визажисты, другие фотографы для коллабораций).

Принцип работы: чат-бот получает запросы от пользователя, направляет их сервису ИИ Агентов для анализа, декомпозиции и поиска решений, затем скомпилированный ответ возвращается в чат-бот для представления пользователю.


## Стек
- Язык: Python 3.14
- Веб-фреймворк: FastAPI + Uvicorn (для Agent Service)
- Фронтенд: Streamlit (для Chat UI)
- Тесты: unittest (встроенный модуль, без pytest)
- Контейнеризация: Docker + Docker Compose
- Менеджер зависимостей: pip + requirements.txt (по одному на сервис)
- Линтинг: ruff
- Форматирование: ruff format


## Структура проекта
Структура проекта представляет монорепозиторий микросервисного приложения на Python.
- `.prompts/` директория содржит **важные правила** работы с проектом (общие и специализированые для роли), каждый агент должен ознакомится с ними;
- `decisions.md` — локальные принятые владельцем решения; `discussion.md` — открытые вопросы и адресные обсуждения; оба файла исключены из Git;
- `docs/` - директория содржит документацию по проекту (описание дизайна, архитектуры, принятых решения и соглашений);
- `docs/ui/` директория содржит дизайн-артефакты;
- `core-api/` — содержит FastAPI-приложение, реализующее логику работы бакенда и агентов (обработка запросов, оркестрация вызовов, бизнес-логика);
- `docker/` — содержит конфигурации и скрипты развертывания (Docker, Docker Compose);
- `streamlit-ui/` — содержит фронтенд-приложение, UI-интерфейс с чатом фотографа;
- `shared/` — содержит общие библиотеки, схемы, утилиты, необходимые всем компонентам проекта.

Проект построен по микросервисной архитектуре: каждый сервис independent,
общается через HTTP API. Все сервисы разворачиваются через Docker Compose.
В первых версиях `core-api` кеширование не используется.
Правила кеширования UI описаны в `.prompts/frontend-rules.md`.

Соглашение об именовании:
- Python-модули: `snake_case` (например, `user_profile.py`).
- Каталоги импортируемых Python-пакетов: `snake_case` (например, `photo_agent/`).
- Каталоги сервисов и документы: `kebab-case` (например, `core-api/`, `streamlit-ui/`, `code-style.md`).
- Стандартные имена документов и файлов инструментов сохраняй: `README.md`, `AGENTS.md`, `SKILL.md`, `__init__.py`, `requirements.txt`.


## Актуальная стадия реализации проекта
Идет работа над этапом "mvp-1", вся актуальная документация в `docs/mvp-1/`.
- `docs/mvp-1/` содржит относящиеся к этапу mvp-1 рассуждения и соглашения, открытые вопросы и задачи, инструкции для частников проекта;
- `docs/mvp-1/purpose.md` описание цели "mvp-1";
- `docs/mvp-1/decisions.md` содержит принятые решения этапа, `docs/mvp-1/discussion.md` — вопросы и обсуждения;
- `docs/mvp-1/tasks.md` — локальный рабочий список задач MVP-1. По решению владельца
  файл исключён из Git: не добавляй его в коммиты и не меняй ради него `.gitignore`.
  В новом checkout файла нет; задания для передачи участникам должны иметь
  самодостаточное описание в версионируемом документе, а не только ссылку на этот список.

## Организация хранения контекста рассуждения и принятых решений.
Правила согласованы владельцем 2026-09-24:
[обсуждения и решения команды](docs/team/discussion-rules.md). Обязательны для всех ролей.

- Открытые вопросы — в локальном `discussion.md`, принятые решения — в локальном
  `decisions.md`; оба файла исключены из Git на любой глубине. Не добавляй их в коммиты.
- Первый блок каждого журнала — `## Rules & agreements`, с форматом, порядком
  записей и ссылкой на правила. Требования и задания храни также в самодостаточной
  версионируемой документации: локальных журналов нет в новом checkout.
  Общепроектные решения для всех этапов закрепляй в соответствующих документах
  и правилах под Git; журнал этапа не является единственным местом их хранения.
- Вопросы группируй по автору (`## from Backend`), блок — `### issue-B123`.
  Новые проблемы добавляй в конец раздела, ответы — в конец блока.
- Каждый агент проверяет все адресованные ему `reqTo-X:` и `fwd-X:`, отвечает
  `from-X:`; частичные ответы/риски/варианты помечает `(R)` / `(A)` / `(V)`.
  Указывай дату/автора; ответ до 100 слов, подробности — в документе по ссылке.
  Эти маркеры действуют и в концептуальных документах. Если решение невозможно
  резюмировать менее чем в 100 словах, в decisions.md оставь краткий итог и ссылки
  на утверждённые разделы концепции; полное описание сохраняй под Git.
- Итог предлагает постановщик или ответчик: 1–3 варианта в чате владельцу.
  Только после явного согласования записывай decision. В issue оставляй проблему,
  статус «принято» и ссылку; после сохранения решения убирай реплики.
  Владелец/тимлид могут позднее чистить закрытые блоки с проверкой ссылок.
- Решения группируй по компонентам, новые сверху. Пересмотр — новый индекс;
  после согласования старый текст зачеркни и свяжи обе редакции ссылками.
  Пока пересмотр обсуждается, прежнее решение действует.
- Индексы не переиспользуй. Отмечай ознакомление и коммит в main; обычная очистка
  решений — после ознакомления участников и переноса требований в main.
  Не считать согласование, изменение файлов, коммит и перенос в main одним действием.

Будущие архитектурные работы фиксируй в `docs/architect-todo.md` с явным указанием,
что они не входят в текущий этап. Не сохраняй дословные рассуждения и переписку:
достаточно решения, краткого обоснования, открытого вопроса и следующего шага.

### Подготовка и локальная разработка

- Python 3.14, окружение `.venv/runtime-env`; первичная подготовка —
  [README](README.md#локальный-запуск). Для работы с обоими сервисами и проверками:
  `.venv/runtime-env/bin/python -m pip install -r requirements-dev.txt`.
- API: `.venv/runtime-env/bin/python scripts/run_dev.py api`.
- UI в другом терминале: `.venv/runtime-env/bin/python scripts/run_dev.py ui`.
- HTTPS ingress: `docker compose -f docker/compose.local.yaml up -d ingress`.
  Docker Desktop должен быть запущен, сертификаты и доверие CA подготовлены
  по основной инструкции. Rosetta для текущих ARM64-образов не требуется.
- `run_dev.py` задаёт адреса UI/API и ограничивает передаваемое окружение.
  Файл `.devsec/.env.local` автоматически не загружается.
- Для отладки API в IDE используй Python из `.venv/runtime-env`, модуль `uvicorn`,
  аргументы `photo_api.main:create_app --factory --host 127.0.0.1 --port 8000 --no-access-log`,
  `PYTHONPATH=.:core-api`; рабочая директория — корень репозитория. Не запускай второй
  API на уже занятом порту. `--reload` допустим для разработки, но теряет RAM-сессии
  при перезапуске и не используется для приёмочных проверок жизненного цикла.

### Docker Compose и остановка

- Для Stage используй `-f docker/compose.local.yaml --profile stage`, для mock —
  `-f docker/compose.test.yaml --profile test`; точные команды — в основной инструкции.
- Корневой `compose.yaml` и команды `docker compose up -d --build` /
  `docker compose down` сохраняют прежний контейнерный запуск прототипа без HTTPS.
  Они не управляют новыми стендами; порты по умолчанию конфликтуют с локальным Dev.
- Остановка только Stage: `docker compose -f docker/compose.local.yaml --profile stage stop stage-ui stage-api`.
  Команда `down` этого Compose-проекта остановит также общий ingress Dev/Stage.
  Локальные API/UI останавливаются отдельно через `Ctrl+C` в их терминалах.
- Удаление томов, в том числе через `down -v`, допускается только после согласования
  с владельцем. Обычная остановка стенда не должна удалять данные.

### Тесты

- Все тесты приложения: `PYTHONPATH=.:core-api:streamlit-ui .venv/runtime-env/bin/python -m unittest discover -s ./tests -p '*_test.py'`.
  Для API/UI замени шаблон соответственно на `api_test.py` / `ui_test.py`.
- HTTPS и WebSocket обоих окружений: `.venv/runtime-env/bin/python scripts/check_https.py`.
  Требуются работающие Dev и Stage, Chrome и доверенный CA в macOS.
- HTTP-сценарии mock: `.venv/runtime-env/bin/python scripts/check_mock.py`.
  Требуется запущенный профиль `test`; проверка сбрасывает счётчик стенда,
  не запускай её одновременно с чужими клиентскими тестами того же mock.
- Линт: `.venv/runtime-env/bin/ruff check .`.
- Проверка форматирования: `.venv/runtime-env/bin/ruff format --check .`;
  применение форматирования: `.venv/runtime-env/bin/ruff format .`.
- Общая конфигурация Ruff — `ruff.toml`: правила `E`, `W`, `N`, `F`, `I`, Python 3.14.
- Успешная проверка HTTPS-стенда с прототипом не закрывает B-02 и приёмку MVP-1;
  ограничения и непроверенные среды фиксируются в протоколе D-01/D-05.


# Ограничения и безопасность

## Как со мной работать (владельцем продукта):
- Сначала уточняй рискованные решения.
- После правок: сообщи что открыть, какой результат увидеть.
- Если задача неясна — задай 1–3 конкретных вопроса.

## Важное правило контекста
Папка '.prompts/' содержит инструкции для твоей работы.
Ни при каких обстоятельствах:
- Не используй файлы из '.prompts\' в качестве примеров кода для бизнес-логики.
- Не пытайся импортировать файлы из папки '.prompts\' в Python-код.
- Это мета-инструкции, а не код приложения.

## Как применять правила разработки (`.prompts/`):
- Изучи Code Style правила '.prompts/code-style.md' и соблюдай их!
- ВСЕГДА и при любых задачах (бэкенд, фронтенд, скрипты) в первую очередь соблюдай правила безопасности, типизации и импорта креденшинов.
- Применяй профильные правила по затрагиваемой части проекта независимо от назначенной роли, в том числе при работе тимлидом.
- Для бэкенда соблюдай `.prompts/backend-rules.md`.
- Для фронтенда соблюдай `.prompts/frontend-rules.md`.
- Для Dockerfile, Docker Compose и развёртывания соблюдай `.prompts/docker-rules.md`.
- Если задача затрагивает несколько областей, соблюдай правила каждой из них.

## Запреты (нельзя никогда нарушать)
- НЕЛЬЗЯ: редактировать '.env', '.env.local' файлы без согласования
- НЕЛЬЗЯ: хардкодить API-ключи или секреты в коде
- Локальное исключение, утверждённое владельцем: секреты приложения Dev допускаются
  в `.devsec/.env.local`, ключи локального HTTPS для Dev/Stage на Mac — в
  `.devsec/ssl/`. Вся `.devsec/` исключается из Git и Docker-контекста; права и
  порядок доступа определены в `.prompts/code-style.md`. На секреты приложения
  Stage/Prod и TLS будущего VPS исключение не распространяется.
- НЕЛЬЗЯ: удалять или переписывать существующие миграции БД
- НЕЛЬЗЯ: устанавливать новые production-зависимости без согласования
- НЕЛЬЗЯ использовать тип `typing.Any`. Встроенная функция `any()` разрешена.
