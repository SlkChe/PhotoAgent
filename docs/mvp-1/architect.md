# MVP-1: архитектура

Архитектура образовательного текстового ассистента по истории и теории фотографии.
Функциональный объём, исключения и пользовательские сценарии определены в
[purpose.md](purpose.md). Система предназначена для закрытой группы до 30 участников
с одновременной работой 2–3 пользователей.

## Компоненты и развёртывание

Backend — модульный монолит FastAPI. UI на Streamlit и локальный inference работают
отдельными процессами. Развёртывание — Docker Compose: один процесс API, один UI,
один процесс inference. Тематики и внутренние модули не выделяются в микросервисы.

| Компонент | Ответственность |
|---|---|
| Ingress-прокси | Единый HTTPS origin для UI и браузерных маршрутов сессии; доступ группы ограничен существующей приватной сетью |
| Streamlit UI | Ввод, отображение диалога и источников, опрос состояния, настройки, очистка и обратная связь |
| core-api | Доступ к сессиям, оркестрация, локальная обработка результатов, внешние вызовы, валидация и статистика |
| Local inference | Выполнение локальной модели с ограниченными входом, выходом и параллелизмом; без внешних инструментов |
| RAM core-api | Рабочее состояние сессий и выполнений; потеря при перезапуске API допустима |
| Постоянный локальный том | Дневные JSON-файлы общей статистики; доступ только у core-api |
| Внешние системы | MCP для поиска/чтения, wiki API и облачная модель для формирования ответа |

Модель загружается один раз, без копии на каждый запрос. Хранилище сессий является
модулем API. Несколько API workers с независимым состоянием не используются.
Ingress не требует Kubernetes.

## Внутренняя структура core-api

| Модуль | Ответственность |
|---|---|
| Session Manager | Состояние диалога, доступ, время жизни и рабочий контекст |
| Orchestrator | Последовательность этапов и фиксация результата |
| Local Query Analyzer | Тематики, задача, сущности, ограничения и неоднозначности |
| Search Planner | Подвопросы, поисковые формулировки и выбор источников |
| Source Registry | Разрешённые адаптеры, операции, аргументы и ограничения |
| MCP/API Gateway | Вызовы инструментов и проверка их результатов |
| Evidence Builder | Нормализация, ранжирование и отбор подтверждающих фрагментов |
| LLM Gateway | Интерфейс к настраиваемому облачному генератору |
| Answer Validator | Проверка структуры, ссылок и представления ограничений ответа |
| Evaluation & Observability | Метрики этапов, ошибок, стоимости и пользовательских откликов |

Оркестратор работает через интерфейс хранилища; внешние системы подключаются
через заменяемые адаптеры. UI обращается к API через отдельный HTTP-клиент.
Общие схемы размещаются в `shared`.

API — источник состояния диалога; `st.session_state` содержит его отображение.
История для пользователя отделена от ограниченного контекста модели: подготовка
контекста выбирает релевантные сообщения и резюме. Источники и время получения
сохраняются вместе с ответом в пределах сессии.

## Обработка запроса

Последовательность обработки:

1. Проверить доступ и состояние сессии, зарегистрировать выполнение.
2. Подготовить контекст и локально сформировать `QueryAnalysis`.
3. При существенной неоднозначности задать уточнение; иначе построить `SearchPlan`.
4. Вызвать разрешённые инструменты поиска и чтения.
5. Локально нормализовать результаты и собрать `Evidence`.
6. Передать релевантный контекст и доказательные материалы облачному генератору.
7. Проверить `Answer` и атомарно сохранить результат для текущей версии сессии.

Разбор и планирование выполняются строго локально, без облачного резерва.
Политики границ, бюджетов, разрешённых инструментов и переходов контролирует код.
Модель возвращает данные для обработки, но не меняет эти политики.

Регистрация выполнения и сохранение результата используют короткие критические
секции. Поиск и генерация не удерживают общую блокировку сессий. Между разными
сессиями действует ограниченный параллелизм; очереди имеют конечную длину.

Смешанный запрос обрабатывается в допустимой части с явным обозначением исключений.
При неполном поиске ответ содержит ограничения и непокрытые подвопросы.
Противоречащие сведения представляются как версии с источниками. Нехватка Evidence
не заменяется неподтверждёнными знаниями генератора. Отказ генератора возвращается
как ошибка, без выдачи непроверенного результата модели.

## Внешние интеграции и источники

MCP предоставляет инструменты поиска и чтения; wiki API — отдельный путь получения
справочных сведений. MCP-сервер выбирается конфигурацией развёртывания, без
автоматического переключения при ошибке. Wiki API не является неявным резервом MCP.
Повторы к тому же серверу ограничены бюджетом выполнения.

Для генерации конфигурация задаёт одного провайдера и одну конкретную облачную модель.
Допускается агрегатор с фиксированной моделью. Автоматическое переключение,
ансамбль и выбор разных моделей для отдельных запросов не применяются.
В пилоте модели испытываются последовательно сменой конфигурации.

Source Registry определяет возможности адаптера, допустимые операции, способы
получения текста, ограничения объёма и времени, сведения об использовании материалов.
Gateway проверяет вход, результат, ошибки протокола и ошибки инструмента.
Результаты поиска проходят локальную обработку; доступность только сниппета
явно отражается в Evidence.

Внешний текст рассматривается как недоверенные данные: инструкции из страницы
не меняют план и права инструментов. Ссылки и редиректы проверяются до загрузки;
внутренние адреса, произвольные схемы и неограниченные загрузки запрещены.
Для чтения используются зарегистрированные инструменты.

Генератору передаются релевантный контекст и Evidence, поисковику — поисковая строка.
Токены доступа, идентификаторы сессии и ненужная история во внешние запросы не входят.
Ключи провайдеров доступны только core-api; UI и inference их не получают.

## Тематики и типы запросов

| Код | Граница и пример |
|---|---|
| `technology` | Техника, оптика, процессы, носители, цифровая обработка как технология: «Как работает дальномер?» |
| `art` | Школы, эстетика, критика, история выставок: «Что такое пикториализм?» |
| `actors` | Авторы, изобретатели, кураторы, организации: «Какую роль играло агентство Magnum?» |
| `genres` | Жанры и их развитие: «Чем документальная фотография отличается от уличной?» |
| `works` | Идентифицированные снимки, серии, книги: «Когда создан и опубликован этот снимок?» |

Темы — метки и профили поиска, не отдельные исполнители с памятью.
«Как малоформатная камера повлияла на фотожурналистику?» → `technology`, `genres`;
задача `explain`, исторические причинные связи отражаются в подвопросах.

| Intent | Ожидаемый результат |
|---|---|
| `reference` | Краткая справка |
| `explain` | Понятие, устройство или причинная связь |
| `historical_overview` | Исторический обзор |
| `timeline` | Последовательность событий с различением видов дат |
| `compare` | Сопоставление по общим критериям |
| `fact_check` | Проверка тезиса: подтверждён, опровергнут, спорен или данных недостаточно |
| `artistic_significance` | Объяснение художественного значения с атрибуцией интерпретаций |
| `source_selection` | Подбор материалов с объяснением полезности |

У вопроса один основной intent, у подвопросов возможны свои intent.
Управляющие реплики `confirm`, `clarification_reply`, `rephrase`, `change_subject`,
`cancel` выделяются отдельно от тематик и intent. «Да» не является шестой темой.
«Объясни проще» использует прежние Evidence без нового поиска, если не добавляет
фактов; новые фактические вопросы проходят поиск.

## Состояния диалога и уточнения

Состояние диалога отдельно от стадии выполнения:

| Состояние | Событие → действие и следующее состояние |
|---|---|
| `ready` | Сообщение → зарегистрировать выполнение → `processing` |
| `processing` | Существенная неоднозначность → один вопрос → `awaiting_clarification` |
| `awaiting_clarification` | Ответ → связать с ожидающим вопросом → `processing` |
| `awaiting_clarification` | Явная смена предмета → убрать старое ожидание → `processing` нового вопроса |
| `processing` | Ответ, ограниченный ответ, приглашение invitation, отказ по границам или ошибка → `ready` |
| `processing` | Ещё одно новое сообщение → HTTP 409, код `session_busy`, актуальное `session_status: in_progress` и active_execution_id; состояние не меняется |
| `awaiting_clarification` | Явная отмена уточнения → убрать ожидание → `ready` |
| Любое живое | Refresh → восстановить историю и прежнее состояние; не запускать повторное выполнение |
| Любое живое | Повтор принятого request_id → вернуть прежнее выполнение; не считать новой репликой |
| Любое живое | Очистка/истечение TTL → отменить задания и удалить данные → `closed` |
| `closed` | Новое обращение → сессия недоступна; создать новую явно |

Стадии выполнения: `queued`, `analyzing`, `searching`, `building_evidence`,
`generating`, `validating`; терминальные `completed`, `failed`, `cancelled`.
Ответ-уточнение завершает выполнение (`completed`), но оставляет диалог ожидающим.
UI отображает понятные статусы из `purpose.md`, не внутренние рассуждения.

Уточнять, когда разные трактовки существенно меняют ответ, а контекст не выбирает
одну: несколько однофамильцев, неизвестный снимок, несколько кандидатов для «он».
Широкий вопрос не требует анкеты: сначала обзор. Для «кто первым изобрёл фотографию»
объяснить разные критерии первенства, а не требовать от новичка выбрать их заранее.
Допускается максимум один раунд уточнения на исходный запрос. Если ответ не снял
неоднозначность, показать варианты/ограничение и предложить явную новую формулировку;
второй уточняющий раунд по тому же запросу не запускать.

Один широкий вопрос либо несколько вопросов об одном предмете/теме переводят
алгоритм в режим тематического обзора. Темы определяются по содержательной связи,
а не только совпадению широкой метки `actors` или `technology`. Обзор объединяет
подвопросы в связное объяснение, сохраняя их покрытие, сравнения и проверку тезисов.
Для нескольких независимых тем остаётся декомпозиция по подвопросам.
Режим обзора не отменяет единственного уточнения, если не определён сам предмет
(например, непонятно, о каком авторе идёт речь), и не разрешает заполнять пробелы
без источников. Это способ организации ответа, а не девятый intent; `historical_overview`
сохраняет своё значение исторического обзора.

Во время `processing` UI блокирует поле ввода и отправку нового вопроса, включая
период ожидания в очереди. API независимо от UI проверяет занятость атомарно.
`session_status: in_progress` — внешнее обозначение состояния `processing`,
не дополнительное состояние диалога. Ошибка содержит статус и ID выполнения,
полученные при проверке; к моменту получения ответа обработка уже может завершиться.
Повтор request_id проверяется раньше занятости. Отклонённый новый вопрос не попадает
в историю/очередь и не продлевает TTL. Опрос статуса и очистка доступны всегда;
после результата, ошибки или перехода к уточнению ввод разблокируется.
После refresh блокировка восстанавливается из состояния API.
Отдельная кнопка отмены активного выполнения в минимальный UI не добавляется:
`cancel` относится к ожидающему уточнению; очистка отменяет выполнение и всю сессию.

Ожидание хранит исходный вопрос, ID уточнения и допустимые варианты. «Да» исполняет
только конкретное ожидающее предложение; при отсутствии такого предложения ничего
не запускается автоматически. Не переносить период и географию на новый предмет
без проверки. Обновления контекста принимает код только для текущей версии сессии.

## Контракты и данные

Состав `QueryAnalysis`, `SearchPlan`, `Evidence`, `Answer`, правила владения запросом,
повторов и публичного цитирования определены в [contracts.md](contracts.md).
UI разрешает цепочку «утверждение → фрагмент → источник» внутри ответа.
Ссылки берутся из полученных источников и проходят проверку.

Один браузерный профиль для хоста приложения использует один временный диалог.
Диалог восстанавливается после обновления страницы по защищённой cookie;
срок жизни — 12 часов бездействия. Правила активности, удаления и восстановления
определены в [session-lifecycle.md](session-lifecycle.md).

Переписка, Evidence и текст обратной связи хранятся только в пределах сессии.
Общая статистика ошибок и откликов сохраняется собственной реализацией в дневных
JSON-файлах на постоянном локальном томе в течение 30 дней. Файлы не содержат
текстов диалогов и идентификаторов пользователей, сессий или запросов.
Выгрузка статистики — защищённый JSON только для владельца, без отдельного экрана.
Средства мониторинга (например Grafana) отложены на следующие этапы.
Правила оценок и расчёта агрегатов определены в
[описании учёта откликов](session-lifecycle.md#учёт-оценок-и-отсутствия-отклика).

В core-api нет кеширования. Evidence и контекст являются рабочими данными сессии;
общий UI-кеш для ответов и Evidence разных сессий не используется.
Предварительное индексирование интернета и собственная векторная база не требуются.
Эмбеддинги необязательны; при их использовании запросы и документы кодируются
совместимой локальной моделью, независимо от облачного генератора.

## Ресурсы и начальные лимиты

Облачные квоты утверждены 2026-09-23: [лимиты и конфигурация LLM](llm-budget.md).
Вход и выход учитываются вместе; общая квота проекта не равна сумме квот сессий.


Выполнение ограничено общим сроком, числом вызовов и повторов, размерами текстов,
контекстом модели и расходами. Повтор возможен только в оставшемся бюджете;
бесконечное перепланирование исключено. Ограничиваются также память сессий,
Evidence и объём промежуточных данных.

| Параметр | Начальное значение |
|---|---|
| Общий deadline выполнения, включая ожидание | 120 секунд |
| Группы подвопросов поиска | До 3; большее число вопросов группируется для обзора с явным указанием непокрытых частей |
| Поисковые/справочные вызовы | До 6, включая повторы |
| Чтение документов | До 6, включая повторы |
| Фрагменты Evidence | До 12 |
| Одновременная проверка | 3 запроса из разных сессий; измеряются очередь, задержка, ошибки и память |

При достижении лимитов поиска причина остановки передаётся в `Evidence.gaps`
и ограничения `Answer`.

## Проверка качества и наблюдаемость

Локальный анализ проверяется на общем фиксированном корпусе примеров.
Нагрузка измеряется при трёх одновременных запросах из разных сессий, включая
ожидание локального inference. Модель не копируется ради каждого выполнения.

Измеряются длительность этапов и ожидания, p50/p95, ошибки, число внешних вызовов,
токены, память inference, доля уточнений и покрытие подвопросов. Измеренная
и оценочная стоимость различаются. Тексты запросов, Evidence и токены доступа
в технические журналы не включаются.

Проверка структуры ответа отделена от оценки достоверности: поддержку утверждений
фрагментами источников проверяют на экспертной выборке.
