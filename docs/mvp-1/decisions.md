# MVP-1: открытые вопросы и замечания специалистам

Постоянный рабочий файл с временными записями: открытые вопросы, рекомендации
и решения, ожидающие ознакомления участников или переноса целевых документов
в main. После согласования укажи статус и ссылку на профильный документ.
Удаление записи допустимо только после ознакомления участников и подтверждённого
переноса целевых документов в main. Дословная хронология обсуждений не ведётся.

Источники требований: [цели](purpose.md), [архитектура](architect.md),
[контракты](contracts.md), [жизненный цикл данных](session-lifecycle.md),
[утверждённая UI-концепция](../ui/concept.md).
Задачи за пределами MVP-1 находятся в [плане развития](../architect-todo.md).

## Передача в разработку и тестирование

Комплект документов позволяет начать реализацию основных модулей, проектирование
UI и подготовку тест-плана. Открытые вопросы ниже не блокируют эти работы.
До реализации зависимых механизмов необходимо завершить протокол браузерной
сессии и правила надёжности статистики; перед интеграцией согласовать HTTP API,
а перед итоговой приёмкой — численные критерии качества и задержки.

## Предложения для проработки

- **Приёмка:** по 5 перефразировок US-01–US-12 (60 запросов) и 20 негативных/
  пограничных запросов; включить анафору, связанные диалоги, обзор и смену темы.
  Ориентиры: macro-F1 тематик и точность основного intent ≥ 0,85, корректность решения
  об уточнении ≥ 0,90, p95 до 90 секунд при трёх активных пользователях.
- **Ресурсы:** проверить модель на ориентире 8 CPU / 16 ГБ RAM; сравнить пользу
  эмбеддингов с правилами/словарями. Лимиты прототипа 4000 символов и 100 пар реплик
  использовать только как исходные значения для измерений, не как новые требования.
- **Интеграции:** рассмотреть внутренний HTTP-интерфейс inference; при выборе MCP
  зафиксировать совместимую версию протокола и доступные инструменты.
- **Генерация:** рассмотреть один вызов на содержательный ответ без автоматического
  платного цикла исправлений и дневной предел расходов с резервом на активные запросы.
- **UX:** язык UI/ответа утверждён — русский; см. решение ниже. Уточнить требования доступности. Браузеры и размеры уже согласованы
  в [U-01](ui-flows.md#язык-экраны-и-доступность). Явно определить поведение при достижении
  лимита диалога: предложить новый, не теряя молча ссылки старых ответов.
- **Афиша — вопрос снят 2026-09-23:** владелец указал, что такого требования
  в целях MVP-1 нет. Граница отражена в purpose.md; из условий A-11 вопрос снят.
  Запись остаётся до ознакомления участников и переноса документов в main.

## Backend: core API

- При проектировании операций сессии явно задать порядок проверки срока,
  авторизации, повторного request_id и занятости. Продумать гонки завершения
  запроса, очистки, истечения TTL, смены оценки и получения снимка для экспорта.
- Описать атомарную передачу итоговых счётчиков из завершаемой сессии писателю
  статистики: исключить повторное начисление и удержание переписки при ошибке диска.
  Зафиксировать границу допустимой потери между удалением сессии и записью снимка.
- Определить схему и версионирование дневного JSON, ограничения очереди записи,
  обработку повреждённого файла и ошибки диска. Подробный проект уже находится
  в [описании хранилища](session-lifecycle.md#json-файлы-с-дневными-агрегатами).
- Выбрать пределы памяти сессии, размера запроса и очереди локального inference;
  согласовать с frontend ответ API при достижении каждого предела.

- При дополнении контрактов разделить анонимного пользователя, тему запроса и роль
  ассистента. Выбор роли при анализе каждой реплики учитывать вместе с контекстом;
  обращение без вопроса должно получать приглашение продолжить без фиктивного поиска.
  Начальное приглашение безымянно; последующие ответы сохраняют авторство.
- Для комментария карточки рассмотреть фрагмент исходной реплики либо её тему,
  без дополнительного вызова генератора. Выбранный способ зафиксировать в контракте.

### Результат согласования контрактов UI — A-13

Владелец задачи — архитектор; backend готовит конкретные схемы и примеры,
frontend подтверждает достаточность данных, UX — соответствие принятым сценариям,
QA — возможность однозначно проверить правила. Добавление invitation отражено в версии 1.1; остальные дополнения не принимаются
одним добавлением задач: согласованное дополнение вносится в contracts.md,
contract-examples.json и затем в OpenAPI в B-01. Порядок работы:

1. **Роли.** Архитектор и backend определяют стабильный идентификатор роли,
   отображаемое имя, поля в Answer, активном выполнении и SessionSnapshot;
   объясняют отсутствие роли до анализа и неизменность автора старого ответа.
   С экспертом по фотографии задают соответствие тематик компетенциям, обработку
   широкого/смешанного вопроса, неизвестной роли и обращения без вопроса.
   Для обращения без вопроса утверждён kind=invitation без оценки и поиска
   (contracts.md 1.1); остаются поля роли и правила её выбора.
   Примеры: новый диалог → друг/специалист; «хочу поговорить с искусствоведом»;
   техническое уточнение → другая роль; refresh → прежние подписи.
2. **Источники.** Backend и frontend выбирают, передаётся ли готовая коллекция
   карточек или она строится из ordered messages. Схема должна однозначно
   определять первичный answer_id, контекстный комментарий и порядок появления.
   Предложение комментария — фрагмент исходной реплики/тема без дополнительной
   генерации. Точные URL объединяются, параметры не удаляются; source_id и фрагменты
   каждого ответа остаются в контексте этого ответа. Примеры: один URL в двух
   ответах с разными фрагментами, разные URL с параметрами, отсутствие источников,
   восстановление полного списка. UX проверяет переход именно к первичному ответу.
3. **Экспорт.** Архитектор, backend и frontend выбирают, кто формирует .md:
   backend либо frontend из согласованного снимка. Нужны версия/граница снимка,
   проверка доступа, представление незавершённого ответа, ошибки и правила повтора
   при очистке/TTL/завершении ответа. Формат должен сохранять текст, имена,
   оговорки, ссылки и контекст без служебных данных. QA нужны примеры обоих файлов
   и ожидаемые результаты гонок. Это задача B-13/F-08, не постоянное хранилище.
4. **Фиксация.** Архитектор определяет версию и совместимость дополнения;
   backend прикладывает валидные/ошибочные JSON-примеры, frontend и QA проверяют
   их на сценариях выше. Готовность A-13 — согласованные схемы, семантика и примеры,
   а не устное согласие «добавить имя/ссылку». После фиксации закрытые вопросы
   получают ссылки на профильные контракты и остаются до ознакомления участников
   и подтверждённого переноса целевых документов в main.

## Frontend

- Проверить браузерный протокол на используемой версии Streamlit: серверный
  HTTP-вызов из UI сам по себе не устанавливает cookie в браузер. Учесть обновление
  cookie при уже открытом соединении и синхронизацию нескольких вкладок.
- Восстанавливать экран из состояния API, включая незавершённый запрос и оценку.
  Дополнения к восстановлению роли и источников описаны в
  [жизненном цикле](session-lifecycle.md#контракт-восстановления-и-защита-от-повторов).
  Проверить, что автоматические перезапуски скрипта не имитируют действия пользователя.
- Определить момент регистрации показа ответа и повторную отправку подтверждения
  после сетевой ошибки; согласовать с backend защиту от двойного учёта.

- Проверить в текущем Streamlit поле высотой 4–7 видимых строк с дальнейшей
  внутренней прокруткой, закрепление ввода и правых полей, длинный список источников,
  мобильное раскрытие, экранную клавиатуру и возврат фокуса. Схема не доказывает
  техническую реализуемость; проверить клавиатурную навигацию и увеличение текста.
- Реализовать переход из маркера в ответе к карточке без фильтрации общего списка;
  меню карточки ведёт к первичному ответу. Клик по ссылке и действие меню открывают
  новую вкладку без одновременного открытия меню. Проверить доступную кнопку меню.
- Использовать имя роли из API, а не извлекать его из текста генерации; не вводить
  селектор ролей и аватары. Отображение — по утверждённой концепции.
  URL брать из публичного контракта, пользовательский HTML не исполнять.
- Проверить два скачивания по [правилам экспорта](session-lifecycle.md#пользовательский-экспорт):
  без повторного поиска/генерации и без служебных данных. В файле диалога рассмотреть
  локальные Markdown-якоря к первичным ответам вместо ссылок на временную веб-сессию.
- Согласовать сохранение настроек для следующих ответов, обработку ошибки и изменения
  во время выполнения; прежние ответы меняются только по отдельной реплике пользователя.
  Сопоставить доступные стадии API с текстами ожидания, безопасным повтором и очередью;
  отдельную кнопку остановки не считать существующей без соответствующего API.

## Тестирование

- Составить матрицу «требование → сценарий → ожидаемый результат» по профильным
  документам. JSON-примеры контрактов использовать как примеры, а не как полный
  набор проверок; добавить некорректные связи claims/fragments/sources.
- Особое внимание уделить изоляции сессий, одновременному первому открытию вкладок,
  повтору request_id, очистке во время генерации и позднему результату после удаления.
- Проверить учёт откликов при смене оценки, повторном показе и отсутствии отклика;
  отдельно проверить нулевой знаменатель и неполную статистику после аварии.
- Проверить сбои записи JSON до и после замены файла, повторный сброс, повреждение,
  заполнение диска и границы хранения с управляемыми часами.
- Для оценки качества подготовить независимую разметку корпуса и экспертную
  проверку поддержки утверждений источниками; нагрузочные результаты фиксировать
  отдельно от целевых значений.

- Вместе с экспертом по фотографии проверить обращение к роли без вопроса,
  техническое уточнение со сменой роли и сохранением контекста, широкий вопрос с другом,
  неизвестную роль, смешанный вопрос и неоднозначное местоимение.
- Проверить рост поля с переносами и длинной вставкой, меню без двойного действия,
  новые вкладки, переход к первичному ответу и мобильный возврат к месту чтения.
  Дополнить матрицу проверками роли, карточек и экспорта из раздела
  [«Проверки при реализации»](session-lifecycle.md#проверки-при-реализации),
  включая UTF-8/Markdown, пустое состояние и ошибку скачивания.
