## Уровни и порядок

1. Unit/контракт: типы, обязательные nullable, перечисления, версии, граф,
   ссылки, временные границы, чистые переходы состояния. Быстрый независимый oracle
   берём из требований; JSON-примеры служат исходными данными, не эталоном качества.
2. Integration: FastAPI TestClient с настоящим хранилищем и управляемыми часами;
   F-02 с подменой HTTP; затем Gateway/mock и оркестратор по готовности B-04/B-05.
   Для идемпотентности и гонок нужны барьеры/события, а не случайные задержки.
3. Browser component: настоящий Chrome и JS с перехватом API. Проверяет браузерное
   поведение, но не интеграцию сервисов.
4. E2E: Chrome/Safari → HTTPS ingress → Streamlit → API; отдельный профиль,
   синтетические данные. Выполняется после возврата согласованной сети.
5. Экспертная оценка и нагрузка: независимый корпус T-02 и эксперт по фотографии;
   три одновременные сессии, p50/p95, очередь и RAM. Не подменять это unit-тестами.

Приоритет исполнения: T-01 → доступная часть T-03 (B-01/B-15/F-02), затем
корпус T-02 и ранний T-07. Базовая разметка T-02 согласована; локальные
T-03/T-07 выполнены с открытыми дефектами. T-04–T-06/T-08 ещё не исполнены.

## Данные и техники тест-дизайна

Используем классы эквивалентности (валидно/невалидно/неизвестно), границы
43200 секунд и числовых лимитов, таблицы состояний выполнения/диалога,
попарные комбинации locale/роли/стиля и явные критические гонки.
Обязательные отрицательные проверки не заменяются попарной выборкой.

Наборы: D1 — `contract-examples.json` плюс независимые мутации;
D2 — `http-contract-examples.json` плюс чужие ID/неизвестные версии;
D3 — две синтетические сессии S1/S2, разные токены и управляемые часы;
D4 — версионируемый корпус T-02 с экспертной разметкой;
D5 — будущие синтетические агрегаты P/N/U, повреждённый JSON и сбои записи;
D6 — длинный синтетический диалог, одинаковые/различающиеся URL,
Markdown-символы и Unicode, все виды Answer.

В D4 нужны стабильный ID, вход, контекст, ожидаемые темы/intent/сущности/уточнение,
основание и статус экспертного согласования; спорные роли — pending A-13.
Ни примеры архитектора, ни ответы проверяемой модели не являются независимым эталоном.

## Запуск и условия

Из корня репозитория, Python из `.venv/runtime-env`, без секретов и облачных вызовов:

```bash
PYTHONPATH=.:core-api:streamlit-ui .venv/runtime-env/bin/python -m unittest discover -s tests -p '*_test.py'
PYTHONPATH=.:core-api:streamlit-ui .venv/runtime-env/bin/python tests/qa_contract_audit.py -v
.venv/runtime-env/bin/python tests/session_probe_browser_check.py
.venv/runtime-env/bin/ruff check .
.venv/runtime-env/bin/ruff format --check .
```

Второй запуск обязателен для текущей T-03: отдельный аудит содержит воспроизводимые
неисправленные дефекты и возвращает ненулевой код. Стандартный discovery его
не включает; зелёные 69 тестов не означают зелёную QA-приёмку.
После исправлений владельцами B/F включить регрессии в обычный набор и повторить аудит.
Для будущего CI эти команды должны быть отдельными обязательными шагами; browser/E2E
требуют подходящего runner. Изменение CI и установка зависимостей здесь не выполнялись.

Живые прогоны: запуск по [инструкции стенда](../deployment/local-mac.md) и
[экспериментальному API](session-probe-backend.md), затем
`.venv/runtime-env/bin/python scripts/check_session_probe.py`.
Сейчас **blocked/environment** по поручению владельца: HTTPS не запускать
до возврата сети. Не менять DNS/TLS/общий ingress для обхода ограничения.
Mock D-05 запускается отдельно после согласования эксклюзивного окна:
`check_mock.py` сбрасывает его счётчики. Платные пробы не входят в этот план исполнения.

viewport CSS px, масштаб ОС/страницы, DPR, устройство или эмуляцию. Playwright WebKit
не считать настоящим Safari, мобильный viewport — Android-устройством.

одну мобильную панель и inert, черновик/позицию, поле 4–7 строк, отсутствие отправки
при переключении панели, длинный диалог, контраст и увеличение текста.
Численные критерии из предложений U требуют согласования; фиксировать измерение,
не заявлять полную WCAG-сертификацию. Ранний layout F-07 проверяется отдельно в T-07.

## Учёт результатов и выход

[Матрица](test-plan.md#requirements-matrix) содержит стабильные QA-ID, статус требования,
сценарий с oracle, уровень, данные, зависимости, автоматизацию и результат.
pass относится только к названному сценарию и среде; fail — расхождение;
blocked — внешняя зависимость; not-run — сценарий не исполнялся.
Для дефекта записываем ревизию, вход/шаги, ожидание/факт, владельца и способ перепроверки.
Не сохраняем токены/cookie, содержимое окружения или пользовательскую переписку.

Метрики: доля принятых строк с определённым сценарием; доля исполненных строк
по уровню/среде; pass/fail/blocked/not-run; открытые дефекты по компонентам.
Строка с частичным прогоном не становится полностью покрытой. Code coverage
в этом прогоне не измерялось; число тестов не равно проценту покрытия.
Defect Density считать только с явно указанным знаменателем (например, число
проверенных требований одной ревизии), а не по всем строкам кода репозитория.
Для T-02/A-10 предложить отдельно пороги классификации, покрытия подвопросов,
поддержки Claims и задержек; конкретные числа утверждает владелец после baseline.

T-01 готова к ревью после трассировки US-01–US-12 и явного обозначения пробелов.
Ранний T-03 завершён как прогон с дефектами, но приёмка B-01/F-02/B-15 не выдана.
Для закрытия B-15 нужны живой HTTPS и повтор критических шагов в Safari;
для полного T-03 — runtime B-04/B-05 и согласованные дополнения A-13.
Исправляет дефект владелец компонента; QA независимо перепроверяет.
