## Итог и границы задач

Рекомендован один API-процесс с RAM-сессиями, браузерный bootstrap через существующий
ingress и серверный HTTP-клиент Streamlit. Отдельный BFF, БД и новые зависимости
для A-07/A-13 не нужны. Роли — профили ответа одного оркестратора, без отдельных
агентов с памятью. Разбор остаётся локальным, генератор не назначает права и роли.

A-07 нельзя закрыть по текущему эксперименту: воспроизведена очистка нового диалога
при устаревшем намерении пользователя; аварийный bootstrap проверен не полностью.
A-13 требует дополнений к кандидату: состояние выбора роли, реестр ролей и браузерная
выдача экспорта. Существующие схемы достаточны для обсуждения, но ещё не для реализации
всех утверждённых сценариев. Ниже — конкретный вариант для согласования и передачи B/F/T/D/U.

## A-07: предлагаемый протокол

### Создание, восстановление и ingress

Сохранить две host-only cookie `__Host-photoagent` и `__Host-photoagent-context`:
Secure, HttpOnly, SameSite=Lax, Path=/, без Domain/Expires/Max-Age. Обе секретны;
контекст восстанавливает выдачу доступа и не должен попадать в JS. Сессионный bearer
передаётся только сервером Streamlit внутреннему API. ID сессии права доступа не даёт.

| Внешний путь с префиксом `/mvp1` | Метод | Проверки / назначение |
|---|---|---|
| `/browser/context` | GET | Создать только CSRF-контекст; отклонить чужой Origin/cross-site; без TTL диалога |
| `/browser/session` | POST | Точный Origin + связанный CSRF; идемпотентное создание/повтор Set-Cookie |
| `/browser/opened` | POST | Origin + CSRF + доступ к ожидаемой сессии; один ID документа учитывается один раз |
| `/browser/clear` | POST | Origin + CSRF + ожидаемая сессия; отзыв и ротация CSRF |
| `/browser/exports/{export_id}/{kind}` | GET | Предлагаемое дополнение A-13: cookie + владение снимком + TTL, без изменения состояния |

Все остальные API-пути, OpenAPI и owner-статистика закрыты внешним ingress.
UI и его WebSocket маршрутизируются отдельно. `/f01/*` — только эксперимент,
его marker не переносится в MVP. Методы allowlist проверяются наряду с путями.
Публичные ответы, включая ошибки/файлы, получают `Cache-Control: no-store`.

Origin сравнивать с заданным origin среды, не с недоверенным Host/X-Forwarded-Host.
Как в B-02, для API достаточно `--no-proxy-headers`; forwarded-заголовки не дают
авторизации. Если они понадобятся для диагностики, доверять только явно заданному
ingress, не `*`. Внутренний API доступен только UI/служебным клиентам по сети
развёртывания; отсутствие маршрута ingress не заменяет проверку bearer.

Внутри одного Web Lock на origin читать context и выполнять browser POST.
Create с прежним request_id восстанавливает ту же живую сессию без TTL;
новый request_id при живой сессии также не создаёт вторую. После Set-Cookie
нужно новое подключение UI. Потерянный ответ исправляется чтением context/повтором
исходного действия, без автоматического нового диалога. После 401 API UI убирает
копию истории; 5xx/сетевая ошибка сохраняют экран и показывают состояние связи.

Основание: [st.context.cookies](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.context)
отражает cookie первоначального запроса. [Web Locks](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)
координирует участников одного origin; это не серверная транзакция и не гарантия
для произвольного клиента. Актуальная документация сверена; измерения B-02 относятся
к установленной Streamlit 1.63.0, не автоматически к последней версии документации.

### Дефект очистки и поправка

Поправка expected_session_id принята владельцем 2026-09-24.
Реализация и проверка — [B-15](#b-15-исправить-устаревшую-очистку).

В `browser.js` подтверждение очистки происходит до ожидания Web Lock, а context
читается после. Пока вкладка A ожидает, B может очистить S1 и создать S2.
A получит свежий CSRF и общую cookie S2: нынешний clear удалит S2, хотя пользователь
подтверждал удаление S1. Ротация CSRF защищает старый HTTP-запрос, но не это намерение.
Повтор clear после потери ответа и получения свежего context имеет тот же риск.

Воспроизведено 2026-09-24 на отдельном in-process TestClient с синтетическими данными:
create S1 → clear → create S2 → свежий context → clear дал 204; context стал пустым.
Это проверка backend-последовательности, не новый браузерный прогон двух вкладок.

Принятое требование: отдельный `SessionActionRequest` для opened/clear:

```json
{
  "request_id": "22222222-2222-4222-8222-222222222222",
  "expected_session_id": "11111111-1111-4111-8111-111111111111"
}
```

Оба поля обязательны UUID. Ожидаемый ID фиксируется из отображаемого snapshot
до подтверждения, не подменяется текущим context при отправке/retry. Он не секрет.
Backend после проверки контекста/CSRF атомарно сравнивает ожидаемую и текущую сессии:

- Совпадают: проверить cookie; выполнить clear, отозвать bearer, отменить работу,
  удалить данные и экспортные снимки, сменить поколение CSRF; вернуть 204.
- Текущая живая сессия другая: 409 `session_changed`, без очистки и без Set-Cookie.
  UI перечитывает snapshot; для удаления новой сессии нужно новое подтверждение.
- Живой сессии нет: clear возвращает 204 как идемпотентное пустое действие;
  opened возвращает 401. Старое открытие не продлевает новую сессию.

Проверка поколения контекста предшествует мутации. Старый CSRF даёт 403;
повтор с обновлённым CSRF сохраняет исходные request_id/expected_session_id.
При повторе уже успешного clear после создания S2 не отправлять удаляющий cookie
заголовок даже при наличии квитанции S1: предпочтителен 409 `session_changed`.

### Refresh, reconnect и пределы RAM

Сохранить ID документа в памяти окна: rerun/remount/reconnect не меняют ID;
явный refresh создаёт новый. Служебный reload после cookie использует одноразовую
несекретную отметку в sessionStorage и сам не продлевает TTL. Потеря хранилища,
восстановление из back-forward cache и авария между отметкой и reload требуют
отдельных проб; не выводить активность из одного факта нового WebSocket.
Все действия проверяют `now >= expires_at` до продления; TTL остаётся 43200 секунд.

Пределы B-02 (1000 контекстов, 256 create ID/контекст, 1024 opened ID/сессия,
24 часа контекста после create, sweep 60 секунд) — проверенная конфигурация
эксперимента, не измеренный предел памяти полноценного MVP. Контекст живёт не меньше
его живой сессии; чтение не продлевает диалог. Переполнение возвращает 409/503,
старые ключи не вытесняются с возможностью повторной мутации.

Для B-04/A-09 дополнительно ограничить сессии, историю/Evidence в байтах,
журналы операций и экспортные снимки. Их значения требуют измерения сериализованной
и фактической RAM; число участников не ограничивает объём диалога.
Не вводить молчаливое усечение истории или абсолютный TTL активной сессии.

При аварии до первой context-cookie Web Lock не отменяет запрос, уже принятый API.
Общий контекст между вкладками тогда ещё не установлен; B-02 не доказал отсутствие
расхождения. Пока считать это открытым критерием A-07, а не ослаблять обещание одного
диалога без согласования. Без HTTPS/Web Locks прекращать создание с понятным сообщением.

## A-13: роли и snapshot

Принят владельцем внешний HTTP-конверт `author: RoleRef` вокруг неизменного Answer 1.1.
Подпись фиксирует backend при публикации; изменение current_role не переподписывает
историю. UI и экспорт получают имя из сохранённого author, не из текущего реестра.
Начальное безымянное приглашение — экран UI, не сообщение Answer.

Предлагаемый минимальный реестр (названия функций, без вымышленных биографий):

| role_id | display_name | Назначение |
|---|---|---|
| `friend` | `Друг` | Общение, начало беседы, очень широкий/смешанный обзор |
| `art_historian` | `Искусствовед` | Эстетика, интерпретации, художественное значение |
| `photo_historian` | `Историк фотографии` | Исторические связи, авторы, даты, развитие жанров и работ |
| `photo_technologist` | `Технический эксперт` | Устройство, оптика, процессы и влияние технологий |

Четыре роли приняты владельцем 2026-09-24; role_id из таблицы — предлагаемые
технические коды для контракта. Эксперт/UX проверяют контрольные
примеры, QA не выводит эталонную разметку из кода. role_id не равен Topic/Intent.
Уточнение A-13 от 2026-09-30: [Query Analyzer / Router, приоритеты и примеры](query-routing.md).
В нём собраны границы ответственности и [четыре правила выбора роли, принятые
2026-10-02](query-routing.md#согласованные-правила-выбора-роли). Остальные ветви
и транспортные детали требуют завершения A-13; таблица примеров не заменяет T-02.

Обращение к известной роли без вопроса → локальный `invitation`, ready, без поиска,
облачной генерации, ожидания уточнения и оценки. Технический вопрос после ответа
искусствоведа может выбрать photo_technologist; если предмет неясен — одно уточнение.
Широкий вопрос остаётся обзором, не превращается в invitation или анкету.

Для утверждённого ограничения имени предлагается 1–20 Unicode code points после
NFC-нормализации, без краевых пробелов/управляющих символов. Имена задаёт реестр,
не модель/пользователь. Это уточнение понятия «символ»; графемы потребуют другого
валидатора, но для предложенных русских названий разницы нет.

Недостающее поле: в `ExecutionSummary` добавить обязательное nullable
`selected_role: RoleRef | null`. При queued/неоконченном выборе — null; после
выбора роли — RoleRef. Snapshot уже содержит active_execution_id и executions:
UI показывает «Определяю тему», пока роль активного выполнения null, затем выбранное
имя. После решения 2026-10-02 требование равенства selected_role и author ниже
нужно пересмотреть: выбор ответа по главной задаче допускает авторство по первому
или главному специалисту. Точная модель ещё не согласована.
`current_role` хранит последнюю выбранную роль (изначально friend); старую роль
нельзя выдавать за выбранную для нового выполнения. Completed требует
selected_role == author; failed до выбора допускает null. Выбор увеличивает revision.

## A-13: карточки и совместимость

`SourceCard` с card_id, source, first_answer_id, first_message_id, context_comment
достаточен frontend. Комментарий — полная исходная реплика запроса, породившего
первый ответ с URL; при цепочке уточнения это исходный содержательный вопрос,
а не отдельное «да». Backend использует связь уточнения с исходным вопросом.
UI может сокращать текст визуально, экспорт сохраняет полный комментарий.
Это поправка к неоднозначному «первому запросу» H-05.

Номер карточки — позиция в упорядоченном source_cards; номер ответа — позиция среди
assistant-сообщений. Переход использует first_message_id. Идентификаторы source_id
и fragment_id разрешаются внутри конкретного Answer; поиск карточки по точному URL
не переносит фрагменты из первого ответа в последующий. Параметры, fragment и строка
URL сохраняются без нормализации. Метаданные первого появления неизменны.

Предлагаемая стабильная HTTP-версия после согласования — `mvp1-http.1`;
Answer остаётся `schema_version: 1.1`. Draft не объявлять совместимой стабильной версией.
При нынешних extra=forbid и закрытых enum даже добавление поля/role_id требует новой
согласованной HTTP-версии и обновления моделей UI/API. Неизвестная версия блокирует
мутации с сообщением о несовместимости, не очищает серверную сессию и не инициирует
повтор генерации. Обновление UI/API выполняется согласованно.

## A-13: экспорт одного снимка

Рекомендуется backend prepare → два файла одной revision, с отдельными действиями
«Сохранить диалог» и «Сохранить источники». Каждое новое действие фиксирует текущую
revision; повтор конкретного скачивания использует прежний export_id. API позволяет
получить оба вида из одного export_id, но два независимых клика после изменения
диалога не обязаны отдавать прежнее состояние. Не добавлять обязательный выбор
технической revision в пользовательский интерфейс.

Prepare через внутренний клиент проверяет bearer/TTL и expected_revision, копирует
публичные данные под короткой блокировкой. Формирование файлов выполняется вне
блокировки; перед публикацией результата повторно проверяются поколение сессии и TTL.
Clear/TTL во время формирования не позволяют вернуть или зарегистрировать снимок.
Временный снимок не меняет last_activity_at, не вызывает LLM, не является показом ответа.

Конкретные предлагаемые ограничения: 60 секунд с prepare, но не позже текущего
expires_at сессии; максимум 2 живых снимка на сессию, 60 на API-процесс,
2 MiB на оба UTF-8 файла одного снимка. Это новые стартовые лимиты для согласования,
не результаты нагрузки. Верхняя граница файлов по счётчику — 120 MiB плюс метаданные
и временные копии; B-13/D проверяют фактический пик. При переполнении отклонять
prepare (`409 export_capacity` для сессии, `503 export_capacity` глобально,
`413 export_too_large` по размеру), не усекать файл и не вытеснять живые снимки.
Повтор истёкшего prepare → 410 export_expired, новый снимок только новым действием.

В H-06 GET файлов внутренний, браузер не может вызвать его с закрытым HttpOnly bearer.
Передача заранее загруженных байтов через обычный
[st.download_button](https://docs.streamlit.io/develop/api-reference/widgets/st.download_button)
создаёт дополнительный путь хранения/выдачи Streamlit; проверка API при подготовке
не подтверждает право при последующем клике. Рекомендуется узкий cookie-защищённый
GET `/mvp1/browser/exports/{export_id}/{kind}` из таблицы A-07, не публикация internal API.

JS получает только export_id/kind; делает same-origin fetch с cookie, проверяет
HTTP-статус, скачивает Blob и освобождает object URL. Backend проверяет сессию и
принадлежность снимка на каждом GET; другой живой сессии — 404, без доступа — 401,
истёкшему ресурсу своей сессии — 410. GET не продлевает TTL; чужой Origin/cross-site
отклоняется, CORS не включается. export_id не секрет и не заменяет cookie.
Выдача: `text/markdown; charset=utf-8`, attachment `dialogue.md`/`sources.md`,
`X-Content-Type-Options: nosniff`, no-store. Ошибка сохраняет диалог и допускает повтор.

Граница гонки — атомарная проверка перед передачей готовых байтов в HTTP-ответ:
clear раньше запрещает выдачу; уже начатую выдачу/скачанную копию отозвать нельзя.
Оба файла сохраняют порядок, имена, ссылки, оговорки, источники и привязку к номеру
первого ответа. Незавершённое выполнение имеет пометку, failed — безопасное сообщение;
сырой черновик/служебные ID/токены не попадают в Markdown. Текст и URL экранируются
по контексту Markdown, HTML не исполняется. Пустому диалогу — 409 export_empty,
без источников available содержит только dialogue. Конфликт revision → перечитать
snapshot и предложить повтор, без бесконечного автоматического prepare.

Альтернатива: формировать файлы frontend из одного snapshot. Это сокращает API,
но потребует отдельного согласования границы отзыва файлов в Streamlit и единого
валидируемого форматирования; не рекомендовано как способ обойти проблему доступа.

| H-07 | Отдельная отмена уточнения технически подходит; clarification_id защищает новое ожидание от старого действия. Без LLM/TTL, история остаётся. UI-кнопку согласовать с U, не добавлять отмену активного выполнения |
| H-08 | shown перед feedback; после ошибки shown допускается идемпотентный повтор. Оценка меняется только по явному действию. Отрицательный комментарий удаляется при positive; конфликт feedback_revision требует перечитывания и явного применения. Не выводить shown из одного получения snapshot/экспорта |
| H-09 | Рекомендуется немедленный 429 до принятия, failed budget_exhausted после принятия; без неявного ожидания окна/новой генерации. Retry-After — только известный срок, не обещание доступности квоты и не автоматическая отправка |

Сетевые ошибки/503 сохраняют текст и request_id исходной неподтверждённой отправки;
413/422 требуют исправления ввода; 409 — сверки состояния; 401 убирает данные прежней
сессии, 403 предлагает восстановить контекст без новой сессии. 410 экспорта требует
нового prepare по действию. UI не повторяет платную работу по одному retryable=true.
Черновик поля ввода сохраняется при rerun/сетевом сбое в текущем UI-сеансе;
его восстановление после полного refresh по действующему контракту не обещается.

## Смежные вопросы A-08 / A-09

Это частичные ответы по адресованным вопросам, не расширение результата A-07/A-13.
Для A-09 рекомендуются скользящие окна, атомарный резерв до облачного вызова,
консервативное удержание резерва при неизвестном usage и сохранение проектного учёта
до отправки. Нельзя восстанавливать квоту из дневных агрегатов или сбрасывать при рестарте.
Точный формат, восстановление/повреждение и Retry-After требуют B/D и отдельного решения.

Для A-08 обнаружено расхождение кандидатов: session-lifecycle предлагает день
завершения сессии, H-08 — день первого показа. Ни один не считать утверждённым.
Предпочтителен день финализации отклика: сессия может жить дольше 30 дней, поэтому
привязка всех последующих исправлений к первому показу конфликтует с удалением
старых дневных файлов. Технические события остаются по дню события, предварительные
оценки отдельно в RAM. Потери RAM при аварии не превращать в no_feedback.
Для согласования ещё нужны интервалы flush/очистки, UTC-граница 30 дней, completeness,
поведение недоступного тома и SIGTERM. Отдельный owner Bearer подходит по границам
доступа; пользовательская cookie и приватная сеть не дают права владельца.
