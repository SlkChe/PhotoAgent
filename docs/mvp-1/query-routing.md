## Место в архитектуре и границы ответственности

По [архитектуре](architect.md#внутренняя-структура-core-api) Local Query Analyzer
является модулем core-api. Оркестратор передаёт ему реплику, релевантный контекст,
ожидающее уточнение и настройки выполнения. Анализ строго локальный; отдельный
inference-процесс, если выбран, исполняет модель, но не управляет диалогом.

| Компонент | Ответственность |
|---|---|
| Query Analyzer | Сформировать QueryAnalysis: scope, темы, intent, сущности, dialogue_act, неоднозначности, предложение обновления контекста |
| Router — предлагаемая функция внутри core-api | По проверенному анализу и контексту выбрать одну роль и рекомендовать сценарий; отдельный сервис/агент с памятью не требуется |
| Orchestrator | Проверить результат, применить политики и переход состояния, зафиксировать выбор; не позволить модели расширить границы MVP |
| Search Planner | Построить SearchPlan для нового поиска; роль сама по себе не назначает инструменты и не предоставляет права |
| UI | Показать полученную роль и сохранённое авторство; не классифицировать запрос повторно |

Роль, предметная тема, intent и сценарий — разные величины. Например, историческое
влияние камеры может иметь topic=technology, intent=explain и роль историка.
Router здесь означает выбор роли/сценария, не FastAPI-маршруты и не ingress.

Предлагаемая граница данных: QueryAnalysis 1.1 не расширять неявно полем роли.
Результат выбора роли передавать оркестратору отдельным внутренним типизированным
объектом: выбранная роль или отсутствие выбора, сценарий и стабильный код основания
для тестирования. Точный DTO, коды и связь с публичным selected_role завершить в
A-13/B-01; это пока не новая утверждённая схема. Внутренние основания не являются
рассуждениями модели и не выводятся в UI. Автор ответа фиксируется при публикации.

## Принятые ограничения

- Один общий диалог, четыре роли: Друг, Искусствовед, Историк фотографии,
  Технический эксперт; выбор выполняет backend при анализе каждой реплики.
- Обращение к роли без вопроса даёт локальное invitation без поиска/облачной
  генерации, завершается ready, не расходует раунд содержательного уточнения.
- Максимум один раунд уточнения исходного вопроса. Широта вопроса сама по себе
  не требует анкеты. Неопределённый предмет не подменяется произвольной догадкой.
- «Да» без конкретного ожидающего предложения не запускает выполнение автоматически.
  Переформулировка без новых фактов может использовать прежние Evidence.
- Роль не расширяет границы MVP; смешанный запрос обрабатывается в допустимой части.
  Смена роли не меняет историю, подписи прежних ответов и накопленные источники.

Источники: [состояния и intent](architect.md#тематики-и-типы-запросов),
[контракт анализа](contracts.md#queryanalysis), [invitation](contracts.md#answer),

## Согласованные правила выбора роли

Утверждены владельцем в чате 2026-10-02. Применяются вместе с принятыми
границами MVP, сохранением авторства и максимумом одного раунда уточнения.

| Ситуация | Принятое поведение |
|---|---|
| Явное обращение к одной существующей роли | Обращение имеет приоритет. Если содержание вопроса не соответствует роли, допустимо уточнить намерение пользователя; уточнение не обязательно |
| Новый вопрос другой тематики после прежнего ответа | Переключение специалиста допустимо. Это несколько пользовательских запросов на разные темы в общем диалоге; прежние ответы и их подписи сохраняются |
| Несколько названных специалистов или множественное «уважаемые эксперты» | При выделенной главной задаче выбирается близкий ей специалист; подпись первого или главного допустима. При равнозначных задачах разных специалистов Друг координирует и подписывает общий ответ (дополнение 2026-10-03) |
| Обращение к неизвестной/несуществующей роли | Обращение можно игнорировать при выборе: роль определяется темой вопроса/задачи. Если тема на границе нескольких ролей, роль по умолчанию — Друг |

Пример: «Историк, объясни устройство объектива» сохраняет приоритет Историка.
Допустимое уточнение: «Ты хочешь узнать об истории развития объективов?».
До ответа пользователя исходный технический вопрос не подменяется вопросом
об истории; пример уточнения не назначает новую тему или intent автоматически.
Уточнение расходует тот же единственный раунд исходного запроса. После его
использования новая несовместимость роли и содержания не разрешает второй раунд.

Выбор **ответа по главной задаче** и разрешённое **авторство по первому/главному** —
разные правила. Первым упомянутый специалист не получает автоматически приоритет
при выборе ответа, если главная задача ближе другому. Подпись фиксируется при
публикации и затем восстанавливается неизменной. Точное представление этого
различия в selected_role/author и технических кодах оформляет A с B/F.
Эти правила сами по себе не требуют нескольких автономных агентов или нескольких ответов.

С 2026-10-03 две ранее открытые ветви согласованы: неизвестная роль без вопроса
получает локальное приглашение Друга; равнозначные задачи нескольких специалистов
консолидируются Другом за одну генерацию. Реестр синонимов/кодов и реализация DTO
остаются деталями A-13/B-01.

## Предлагаемый порядок выбора

Техническая детализация принятой политики от 2026-10-03 приведена ниже в разделе
[выбор содержания и авторство](#выбор-содержания-и-авторство). Она имеет приоритет
над прежними предложениями, допускавшими равенство этих двух значений во всех случаях.

Таблица ниже — кандидат полного алгоритма. При расхождении приоритет имеет
согласованный раздел выше; точный порядок оставшихся ветвей требует A-13.
Применять после проверки
доступа, request_id и занятости. Повтор доставки не запускает новый анализ.

| Приоритет | Условие | Выбор и действие |
|---|---|---|
| 1 | Управляющая реплика или ответ на ожидающее уточнение | Разрешить её относительно ожидаемого действия; отмена/повтор не создают самостоятельную тему. После уточнения снова оценить содержательный вопрос |
| 2 | Запрос полностью вне MVP | Локальный отказ по границам, подпись Друга; не выбирать специалиста ради выполнения запрещённого сценария |
| 3 | Предмет существенно неоднозначен | Единственное содержательное уточнение; подпись явно запрошенной известной роли, иначе последней релевантной роли или Друга. Если раунд уже использован — варианты/ограничение без новой анкеты |
| 4 | Явное обращение к одной известной роли | Принято: существующая роль имеет приоритет; при несовпадении содержания допустимо уточнение в пределах одного раунда; без вопроса — invitation |
| 5 | Переформулировка прежнего ответа без новых фактов | Сохранить его роль и Evidence; не превращать просьбу «проще» в новый поиск |
| 6 | Явного обращения нет, задача определена | Художественная интерпретация → Искусствовед; даты/исторические связи → Историк фотографии; устройство/процессы → Технический эксперт |
| 7 | Общее общение, очень широкий обзор или нет доминирующей специализации | Друг; ширина вопроса не создаёт дополнительного уточнения |

Явное обращение предлагается считать действующим для текущей реплики, без постоянной
фиксации роли до ручного переключения. Следующая содержательная реплика анализируется
заново с учётом контекста. Одинаковая тема не гарантирует ту же роль.

Для нескольких специалистов и множественного обращения действует согласованный
выбор по главной задаче; прежний кандидат «иначе первый содержательный подвопрос»
не является утверждённым правилом. Допустимость подписи первого специалиста
не заменяет выбор ответа по главной задаче.

Для неизвестной роли с содержательным вопросом действует выбор по теме, на границе
ролей — Друг. Без содержательного вопроса локальное приглашение Друга к доступным
компетенциям принято отдельным дополнением 2026-10-03.
Упоминание роли в цитате/отрицании не является обращением: «не отвечай как
искусствовед» не выбирает Искусствоведа по одному совпадению слова.

## Выбор содержания и авторство

Дата: 2026-10-03. Техническая детализация четырёх принятых правил, а не новое
согласование их смысла. Внутренний DTO и публичные поля ниже — спецификация для
B-01/B-05/B-06; в текущем shared/http_draft они ещё не реализованы.

`selected_role` определяет ведущий профиль данного выполнения; при консолидации
это Друг-координатор, а тематические профили задаются отдельно для подвопросов.
`author` — неизменная подпись опубликованного ответа. Это не список реальных
независимых исполнителей: обработка остаётся у одного оркестратора.

1. Одно явное обращение к существующей роли: selected_role — эта роль, author
   при публикации — она же. Несовпадение с темой само по себе не отменяет обращение.
   Уточнение использовать, только если ответ пользователя способен изменить
   интерпретацию; вопрос не подменять до ответа. Отдельный раунд «для выбора роли»
   сверх единственного раунда уточнения запрещён.
2. Несколько/множественное обращение с выделенной главной задачей: selected_role
   определяется главной задачей. Для равнозначных задач действует консолидация
   Другом, описанная ниже; подпись первого специалиста к этой ветви не применяется.
   Для подписи backend вправе использовать главного либо первого явно названного
   существующего специалиста. По умолчанию техническая реализация использует
   главного; альтернативная допустимая подпись сохраняется явно, а не вычисляется
   UI из порядка имён. В «уважаемые эксперты» первого названного специалиста нет:
   подпись главного. Равенство selected_role == author не является общим инвариантом.
3. Неизвестная роль с вопросом: отбросить неизвестное обращение, выбрать по теме;
   на границе ролей — Друг. В неподдерживаемый сценарий этот выбор не даёт доступа.
4. Новая реплика: снова определить содержание и явное обращение; смена роли
   допустима. Повтор request_id использует сохранённый выбор, а не пересчитывает
   его по новой конфигурации/истории. Reconnect также не меняет авторство.

Главная задача сначала берётся из явного указания пользователя: «главное»,
«прежде всего» либо явно названной цели. Её перефразировки объединяются по смыслу,
остальные подвопросы сохраняются. QueryAnalysis.intent первого содержательного
подвопроса при отсутствии явной цели — правило контракта анализа, а не команда
выбрать первым названного специалиста. При неизвестной роли и равной близости тем
Друг уже предусмотрен принятой политикой. Для равнозначных задач нескольких специалистов без
различимой главной задачи принято selected_role=Друг и author=Друг; при этом
каждая тема получает собственный профиль обработки, а не исключается из ответа.

### Внутренний результат маршрутизации

Предлагаемое имя типа — `RoutingDecision`; принадлежность задаёт оркестратор,
модель не создаёт доверенные ID. QueryAnalysis 1.1 остаётся неизменным.

| Поле | Тип / значение |
|---|---|
| session_id, request_id, execution_id | UUID исходного принятого выполнения |
| base_revision | Неотрицательная версия контекста, использованного анализом |
| selected_role | RoleRef ведущего профиля; Друг при консолидации |
| mode | `single` либо `consolidated` |
| subquestion_roles | Список `{subquestion_id: string, role: RoleRef}`; внутренние связи с QueryAnalysis.subquestions |
| author_role | RoleRef, подпись будущего опубликованного ответа |
| author_basis | `selected`, `first_addressed` либо `coordinator`; first_addressed только при выделенной главной задаче, coordinator только для consolidated |
| addressed_roles | Упорядоченный список распознанных существующих ролей без повторов; цитаты/отрицания исключены |
| main_subquestion_id | ID главной подзадачи QueryAnalysis либо null для invitation/общего обзора |
| route_basis | `explicit_role`, `main_task`, `topic`, `boundary_friend`, `context_rephrase`, `equal_tasks`, `unknown_role_invitation` |

До выбора RoutingDecision отсутствует, а execution.selected_role=null. После выбора
execution.selected_role равен RoutingDecision.selected_role. Для author_basis=selected
author_role должен совпадать с selected_role. Для first_addressed author_role равен
первой роли addressed_roles; список содержит минимум две разные роли. Поиск и
профиль генерации определяют selected_role и subquestion_roles, не author_role.
Для consolidated: selected_role=author_role=Друг, author_basis=coordinator,
main_subquestion_id=null. Каждый допустимый подвопрос связан ровно с одним
профилем, ссылки существуют в QueryAnalysis; исключённые части не получают заданий.
Для single author_basis=coordinator запрещён. Invitation имеет пустые subquestion_roles.
Эти поля внутренние: новый DTO не меняет Answer/QueryAnalysis 1.1.

При публикации backend атомарно сохраняет author из author_role вместе с Answer
и связывает их с исходным выполнением. В ExecutionView и AssistantMessage одного
answer_id подпись одинакова. При failed публичного author нет, выбранная до ошибки
роль может оставаться в сводке выполнения. При отмене/очистке запоздавшее решение
не применяется: проверяются доступ, актуальность выполнения и контекста.

Это технический контракт выбора. Коды role_id используют реестр четырёх ролей
из A-13; точные синонимы и незавершённые ветви не становятся утверждёнными от
появления таблицы DTO. Не сохранять в объекте свободные рассуждения модели.

### Публичное представление и примеры

Для UI: пока активное выполнение имеет selected_role=null, показывать
«Определяю тему». После выбора строка текущей обработки показывает selected_role;
каждый готовый ответ подписывается только сохранённым author. current_role —
последний выбранный профиль содержания сессии, не источник подписей истории.
После завершения допустимое различие текущего профиля и подписи не исправляется
клиентом. Экспорт берёт author опубликованного ответа.

| Реплика / состояние | selected_role | author при публикации | Основание |
|---|---|---|---|
| «Историк, объясни устройство объектива» | Историк фотографии | Историк фотографии | Явная существующая роль; допустимо уточнение без подмены исходного вопроса |
| «Историк и технический эксперт, главное — устройство затвора» | Технический эксперт | Технический эксперт по умолчанию; Историк фотографии также допустим | Содержание по главной задаче; альтернативная подпись первого — только author_basis=first_addressed |
| «Уважаемые эксперты, объясните устройство затвора» | Технический эксперт | Технический эксперт | Нет первого явно названного специалиста |
| «Астролог, как работает диафрагма?» | Технический эксперт | Технический эксперт | Неизвестное обращение игнорируется при выборе по теме |
| Новая реплика после Искусствоведа: «Как устроен затвор?» | Технический эксперт | Технический эксперт | Прежний ответ остаётся подписан Искусствоведом |
| Восстановление completed после смены текущей роли | Сохранённое значение выполнения | Сохранённая подпись того ответа | Никакого повторного выбора при refresh/retry |

Для QA авторство первого/главного в соответствующем случае — множество допустимых
результатов, а не требование всегда выбирать первого. Независимо проверяются
главная задача, selected_role, допустимость author и неизменность при восстановлении.
Корпус 0.3.0 и согласованная базовая разметка этим документом не переписываются.

### Неизвестная роль без вопроса

Принято 2026-10-03: переключить на Друга, вернуть локальный invitation:
«Такого эксперта у нас пока нет, но я постараюсь помочь в рамках истории,
искусства и техники фотографии. Что вы хотели обсудить?»
Смысл текста обязателен, стилистика может уточняться UX. selected_role=author=Друг;
mode=single, route_basis=unknown_role_invitation. Поиск/облако не вызываются,
неизвестная роль не создаётся, раунд уточнения не расходуется, состояние ready.
Следующий содержательный вопрос анализируется обычным способом; выбор Друга
не закрепляет его навсегда. Содержимое invitation соответствует Answer 1.1.

### Равнозначные задачи и консолидация

Принято 2026-10-03: один координатор Друг и тематические профили подвопросов.
Триггер — несколько допустимых содержательных задач разных специализаций без
выделенной главной. Само множественное обращение не требует консолидации, если
главная задача определена. Явное обращение к одной роли сохраняет свой приоритет.

Анализатор выделяет подвопросы, Router назначает профили, Search Planner строит
единый ограниченный план поиска. Это не один обязательный поисковый HTTP-вызов:
число вызовов ограничивается общим бюджетом выполнения, не отдельной квотой на роль.
Evidence сохраняет связь с подвопросами. Один вызов облачной генерации получает
подвопросы, их профили и отобранные Evidence, готовит тематические разделы и общий
вывод. Отдельных облачных черновиков специалистов и второго вызова для объединения
в MVP нет. Повторы при транспортных сбоях подчиняются общей политике B-14;
«одна генерация» не разрешает неограниченные скрытые ретраи.

Публикуется один Answer с одним author=Друг и одним состоянием оценки.
Разделы могут называться по темам; UI не изображает отдельные сообщения или
фактически не выполнявшиеся обращения к автономным агентам. Друг может пояснить:
«Разберу вопрос с точки зрения истории и техники и объединю выводы».
Роли — профили одной системы, а не обещание консультации с людьми.

Проверка результата сохраняет цепочки claims → fragments → sources, явные
противоречия и пробелы по каждой теме. Нехватка бюджета/источников не скрывает
подвопрос: ответ limited с соответствующими limitations; при отказе генерации —
failed без частичных черновиков. Если доказательств для ответа недостаточно,
применяются существующие правила insufficient_evidence. Дополнительная генерация
ради неуместившихся частей не запускается. Квоты, включая 1500 токенов на вызов,
не повышаются; B-07/B-09 проверяют укладывание общего контекста в бюджет.

Пример: «В равной мере объясните устройство затвора и историю его развития».
Технический профиль назначается первому подвопросу, исторический — второму;
mode=consolidated, selected_role=author=Друг. Ответ содержит обе части и общий вывод.
Для той же реплики с «главное — устройство» сохраняется single с техническим
профилем и прежним правилом подписи при множественном обращении.

## Фразы, правила распознавания и шаблоны ответов

Нужны три разных артефакта:

1. T-02: независимые примеры фраз и диалогов с ожидаемым результатом, подготовленные
   QA с экспертом. Не ограничивать допустимый ввод перечнем фраз.
2. B-03: словари/синонимы/правила распознавания как baseline для сравнения с моделью.
   «Искусствовед», «эксперт по искусству» — кандидаты синонимов, а не доказательство
   роли без проверки смысла, отрицаний, цитат и контекста.
3. B-06 с UX: тексты локальных invitation, отказа по границам и обработки неизвестной
   роли. Например, «Какую тему фотографии обсудим?» — вариант invitation; окончательные
   формулировки/тон согласует UX. Содержательные ответы не сводятся к этим шаблонам.

## Примеры для подготовки T-02

Это начальная матрица сценариев, не готовый независимый корпус и не результаты
измерения качества. Выбор ролей по новой политике помечен «предложение».

| ID | Контекст и реплика | Ожидаемый результат |
|---|---|---|
| R01 | Новая сессия: «Хочу поговорить с искусствоведом» | Искусствовед, invitation, ready; без поиска/облака — принятое поведение |
| R02 | «Как работает диафрагма?» | Предложение: Технический эксперт; technology/explain, содержательный ответ |
| R03 | «Когда появилась дагеротипия?» | Предложение: Историк фотографии; technology/reference |
| R04 | «В чём художественное значение пикториализма?» | Предложение: Искусствовед; art/artistic_significance |
| R05 | После ответа Искусствоведа о цветной фотографии: «Как устроен трёхслойный цветной материал?» | Предложение: Технический эксперт; новая содержательная задача, прежняя подпись сохранена |
| R06 | «Искусствовед, объясни, как работает диафрагма» | Принято: Искусствовед по явному обращению; допустимо одно уточнение намерения, технический смысл без подтверждения не подменяется |
| R07 | «Расскажи о фотографии в целом» | Друг, обзор без обязательного уточнения; источники для фактических утверждений |
| R08 | «Да», когда нет ожидающего предложения | Не запускать поиск/генерацию автоматически; предложить сформулировать тему |
| R09 | «Да» после уточнения «Вы имеете в виду Луи Дагера?» | Связать с уточнением, продолжить исходный вопрос; предложение роли — Историк фотографии |
| R10 | После обсуждения двух авторов: «Когда он сделал этот снимок?» | Уточнить предмет один раз; если раунд уже израсходован — варианты/ограничение |
| R11 | После ответа Технического эксперта: «Объясни проще» | Rephrase, reuse Evidence; предложение — сохранить роль исходного ответа |
| R12 | «Хочу поговорить с астрологом» | Принято 2026-10-03: Друг, invitation с сообщением об отсутствии эксперта и предложением помощи; без поиска/облака/раунда уточнения |
| R13 | «Найди студию в аренду и расскажи историю студийного портрета» | Mixed: исключить аренду, сохранить историческую часть; предложение — Историк фотографии |
| R14 | «В книге сказано: “спросите искусствоведа”. Как работает затвор?» | Предложение: Технический эксперт; цитата не переключает роль |
| R15 | «Историк и технический эксперт, главное — объясните устройство затвора, затем его историю» | Предложение: Технический эксперт по главной задаче; сохранить второй подвопрос |
| R16 | «В равной мере объясните устройство затвора и историю его развития» | Принято 2026-10-03: два профиля подвопросов, Друг-координатор и автор; одна генерация/один Answer, сохранено покрытие обоих вопросов |

Для каждого теста QA фиксирует: case_id, контекст/ожидание уточнения, текущую роль,
реплику, scope, dialogue_act, intent/topics, ожидаемые роль/сценарий, допустимость
поиска/облака и основание разметки. Поля, ещё зависящие от решения владельца, отмечаются
pending, а не выдаются за эталон. Добавить перефразы, опечатки, отрицания, цитаты,
иноязычный ввод при locale=ru и граничные диалоги. Проверочную часть отделить от
примеров настройки правил/модели, чтобы измерять обобщение, а не запоминание.
