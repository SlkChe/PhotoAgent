## Что уже определяет развёртывание

### Площадки и приоритеты — решение владельца от 2026-09-23

Dev и Stage размещаются на текущем Mac. Приоритет — подготовить обе среды
для команды проекта. Prod предназначен для будущего VPS: сервер пока не арендован,
его требования открыты. Сейчас собираются требования; аренда и развёртывание
пилота на VPS выполняются позже.

Для Dev и Stage предлагаются раздельные Compose-проекты, сети, тома, порты и имена
хостов. Разные порты одного хоста не следует считать изоляцией браузерных cookie.
Stage должен запускать фиксированную сборку, чтобы текущие правки Dev не меняли
результат проверки. Доступ команды к Mac и способ доверенного HTTPS ещё уточняются.

### Локальные имена и HTTPS — предложение

Уточнение владельца от 2026-09-23: существующая приватная сеть — изолированная
домашняя LAN. Предложены hosts либо локальный DNS и собственные сертификаты
либо отключение их проверки. Выбор механизма пока не утверждён.

Рекомендация DevOps для D-01: начать с hosts и двух имён
`photoagent-dev.home.arpa` и `photoagent-stage.home.arpa`; зона `home.arpa`
предназначена для домашних сетей ([RFC 8375](https://www.rfc-editor.org/info/rfc8375/)).
На самом Mac при доступе только с него оба имени могут указывать на `127.0.0.1`.
Для других компьютеров записи должны указывать на LAN-адрес Mac, закреплённый
в DHCP; hosts на Mac не настраивает разрешение имён на других устройствах.
Владелец сообщил: Mac — `192.168.7.100`, адрес закреплён по MAC;
роутер — TP-Link Archer C2 AC750, `192.168.7.1`. Поддержка пользовательских
DNS-записей на его аппаратной версии/прошивке не проверена.
Для одинаковых адресов приложения на Mac и других компьютерах LAN предлагаются
следующие записи hosts на каждом клиенте:

```text
192.168.7.100 photoagent-dev.home.arpa
192.168.7.100 photoagent-stage.home.arpa
```

Владелец добавил эти записи в `/etc/hosts` текущего Mac. Проверка DevOps
через `dscacheutil -q host -a name` для каждого имени подтвердила разрешение
обоих имён в `192.168.7.100`. Разрешение на других устройствах не проверялось.

Это только разрешение имён: HTTPS ingress ещё не запущен. При его настройке
нужно обеспечить доступ через LAN-интерфейс Mac; существующая публикация
прототипа только на loopback не обеспечивает доступ с других устройств.
Для проверки на Android и других устройствах без удобного редактирования hosts
нужен локальный DNS: сначала проверить возможности роутера, затем при необходимости
поднять отдельный DNS-сервис. Клиенты должны действительно использовать этот DNS.

Для HTTPS предлагается собственный локальный CA и сертификаты для этих имён,
с добавлением публичного корневого сертификата в доверенные на тестовых устройствах.
Проверку сертификатов оставить включённой, особенно на Stage: обход ошибок TLS
не подтверждает штатную работу HTTPS/WebSocket и браузерного протокола B-02.
Самоподписанный сертификат без настройки доверия недостаточен для такой приёмки.
Способ выпуска и управления закрытыми ключами пока не выбран; правила проекта
о секретах сохраняются. Hosts изменён владельцем; DevOps системные настройки
не менял. Доверие CA и HTTPS ещё не настроены.

### Требования к VPS, которые нужно собрать

| Область | Что определить до аренды | Основание |
|---|---|---|
| CPU, RAM и ускоритель | Измерить API/UI/inference при трёх одновременных запросах, учесть загрузку модели и запас; определить необходимость GPU | B-03, A-09; 8 CPU / 16 ГБ пока только ориентир исследования |
| ОС и архитектура | Выбрать Linux и поддерживаемую архитектуру после проверки образов и runtime | Mac имеет arm64; архитектура VPS ещё не выбрана |
| Диск | Оценить размер образов, модели, временных файлов, агрегатов и состояния квот, запас для обновления/отката | D-02/D-03, A-08/A-09 |
| Сеть | Приватный доступ группы, DNS/HTTPS, доступность выбранных внешних сервисов из региона VPS | D-01, B-07 |
| Эксплуатация | Согласовать простой при обновлении, способ администрирования, сохранность агрегатов/квот и политику копий | Один API-писатель; потеря RAM-сессий при рестарте допустима |
| Стоимость | Определить допустимый бюджет VPS и трафика после измерений | Решение владельца; конкретный тариф пока не выбирается |

Проверки на Mac не заменяют проверку образов и файлового тома на целевой платформе.
Численные минимальные требования к VPS до измерений не утверждаются.

MVP-1 предназначен для закрытой группы до 30 участников, одновременно 2–3 пользователя.
Один API worker хранит диалоги в RAM; рестарт API теряет сессии, рестарт UI должен
позволять восстановление из живого API. TTL — 12 часов пользовательского бездействия;
heartbeat и закрытие вкладки не управляют сроком жизни MVP-1.

Согласованы Docker Compose, отдельные API/UI/local inference и единый HTTPS origin
через ingress в существующей приватной сети. Наружу доступны UI и ограниченные
браузерные маршруты; нужны WebSocket, cookie и CSRF. Конкретный runtime локальной
модели и протокол браузерной интеграции ещё проверяются.

Дневные JSON-агрегаты хранятся 30 дней на постоянном локальном томе только API.
Обновление должно исключать двух писателей. Потеря RAM-сессий допустима, но незаметный
сброс проектной квоты LLM при рестарте недопустим; её сохранение требует отдельного
решения A-09/B-14. Выгрузка статистики доступна только владельцу.

Секреты поступают из окружения нужного процесса, не из файлов. LiteLLM D-05 —
отдельный тестовый mock без облачных вызовов и рабочих ключей. Мониторинг с Grafana
и горизонтальное масштабирование отложены за пределы MVP-1.

## Фактическая конфигурация

Проверены `compose.yaml`, оба Dockerfile, `.dockerignore`, зависимости и настройки
сервисов. Два образа используют Python 3.14 и UID/GID 10001, копирование прикладных
каталогов, отдельные requirements; API запускается с одним worker без access log.
Порты опубликованы на loopback, UI ожидает healthcheck API.

В Compose ещё нет ingress, inference, постоянного тома, тестового LiteLLM и
healthcheck UI. Используются TTL 180 секунд и heartbeat прототипа. Версии прямых
Python-зависимостей закреплены, но базовый образ `python:3.14-slim` не закреплён
digest; отдельной фиксации транзитивных зависимостей нет. В `.github/` не обнаружены
workflow CI. Это перечень незавершённых работ, а не дефекты относительно README прототипа.

После установки владельцем Docker Desktop проверены Docker CLI и Engine 29.8.0,
Compose v5.5.1. Engine отвечает через локальный сокет; платформа linux/aarch64,
доступны 10 CPU и 8319504384 байта RAM (около 7,75 GiB).
CLI доступен по `/Applications/Docker.app/Contents/Resources/bin/docker`,
но в PATH текущей оболочки агента пока отсутствует. Для проверки Engine потребовался
доступ к сокету вне песочницы. Сборка, запуск контейнеров приложения, HTTPS,
WebSocket и файловый том этой проверкой не подтверждены.
При дополнительной проверке: macOS 14.8.9, arm64, 32 GiB RAM, 10 физических
и 10 логических CPU, примерно 245 GiB свободного места
на разделе проекта. Общий бюджет одновременного запуска Dev/Stage и inference
ещё нужно определить по измерениям; RAM Docker Engine меньше полной RAM Mac.

## Предложения по средам и структуре

Предложения не являются утверждённой конфигурацией.

1. Сохранить корневой `compose.yaml` как документированный локальный вход.
   В `docker/` хранить Dockerfile, общие определения и явно подключаемые конфигурации
   сред: `compose.dev.yaml`, `compose.stage.yaml`, `compose.prod.yaml`.
   Для MVP-1 Prod означает закрытый пилот. Общая часть не должна публиковать порты
   API/UI на хост; локальная публикация относится только к Dev.
2. Stage и пилот запускать из одних проверенных образов с фиксированными digest,
   разделяя имена Compose-проектов, origin, сети, тома и окружение процессов.
   Dev и Stage размещаются на одном Mac по решению владельца; Prod — на будущем VPS.
   При разных архитектурах проверять обе платформы и фиксировать соответствующие
   варианты образов одного релиза.
3. D-05 вынести в `docker/compose.test.yaml` с тестовым профилем и отдельной сетью
   без исходящего доступа; проверять изоляцию экспериментом. Фикстуры backend/QA
   хранить в `tests/fixtures/`, несекретную конфигурацию mock — в `docker/test/`.
4. Несекретную конфигурацию ingress хранить в `docker/ingress/`, проверочные и
   эксплуатационные скрипты — в `scripts/`. Сначала документировать прямые команды;
   добавлять обёртки только для повторяемых операций с проверками ошибок.
5. Создать `docs/deployment/` для инструкций запуска, обновления/отката и диагностики;
   протоколы исследований D-01/D-05 оставить в `docs/mvp-1/` со ссылками из README.
   При обновлении сначала останавливать прежний API-писатель; предусмотреть потерю
   активных сессий и совместимость сохранённых форматов при откате.
6. В D-04 проверять Ruff, unittest, C4, сборку и итоговую конфигурацию каждой среды,
   затем доступность HTTP/WebSocket. Проверять отсутствие лишних опубликованных портов
   после объединения Compose-файлов: списки портов могут сохраняться при слиянии.
   Основание: [правила объединения Docker Compose](https://docs.docker.com/reference/compose-file/merge/).
   Полный вывод конфигурации с подставленными секретами не публиковать в CI-логах.

Ближайший порядок: подготовить контейнерный runtime и доступ команды на Mac,
разделить Dev/Stage, подготовить HTTPS-стенд и независимо
тестовый D-05, затем совместно проверить B-02. D-02/D-03 зависят от A-07/A-08/A-09
и соответствующей реализации backend. Вопросы специалистам — в
[журнале этапа](decisions.md#уточнения-devops-после-ознакомления--2026-09-23).
