## F-01: клиентская часть B-15

В `streamlit-ui/photo_ui/session_probe/`:

- Компонент получает только ID **показанного серверного snapshot**, без cookie/bearer.
  clear фиксирует request_id и expected_session_id до confirm и ожидания Web Lock.
- opened фиксирует ID показанной сессии и ID документа. Свежий CSRF из context
  не заменяет ожидаемую сессию. Повтор после ошибки сохраняет первоначальные поля.
- 409 session_changed блокирует устаревшие действия и предлагает переподключение;
  очистка новой сессии требует нового подтверждения. Служебное переподключение
  помечается для исключения дополнительного продления TTL.
- При отсутствии snapshot очистка недоступна. Несовместимое тело (422) показывается
  как необходимость обновления API; отката к небезопасному пустому clear нет.

Основание уже принято: [B-15](session-ui-review.md#b-15-исправить-устаревшую-очистку).
Обновление статуса 2026-10-03: backend уже принял SessionActionRequest и проверку
ожидаемого ID (результат B от 2026-10-01, [протокол](b15-checks.md)). Прежний
блокер несовместимого тела снят. Живой HTTPS остаётся отложенным владельцем
до возврата в прежнюю сеть; B-15 не закрыта.
Подмена в `tests/session_probe_browser_check.py` адаптирована к новым полям,
но не запускалась и не доказывает исправление гонки на настоящем backend.

## F-07: переиспользуемая компоновка Streamlit

Реализация: `streamlit-ui/photo_ui/layout/`, точка просмотра —
`streamlit-ui/layout_preview.py`. Это компонент Streamlit v2 с локальными HTML/CSS/JS,
а не открываемый отдельно HTML-макет. Новых зависимостей нет.

- Desktop: три области, ориентир 15/62/23, ограничение ширины строки диалога,
  сворачиваемое левое меню, отдельно прокручиваемые диалог и источники.
- До 1150 px меню становится накладной панелью; до 760 px скрыты обе боковые
  области. Две иконки имеют доступные названия и цели 44×44 px.
- Открыта одна накладная панель; доступны переключение, явное закрытие, Escape,
  циклический Tab и возврат фокуса. Перекрытый диалог и другая панель получают inert
  и aria-hidden. При изменении ширины скрытые элементы исключаются из взаимодействия.
- Черновик хранится в состоянии компонента/`st.session_state`; браузерная память
  сохраняет прокрутку, выделение текста и открытую панель при rerun. Переключение
  панели не отправляет запрос и не сбрасывает место чтения.
- Ввод растёт от 4 до 7 строк с внутренней прокруткой. Enter переносит строку,
  Ctrl/⌘+Enter вызывает отправку. Размер учитывает visualViewport экранной клавиатуры.
- Новое сообщение не уводит читающего старую реплику вниз; появляется действие
  «К новому ответу». Переход из источника закрывает панель и фокусирует первичный ответ.
- Внешние ссылки открываются отдельно; текст данных вставляется через textContent,
  URL ограничены HTTP/HTTPS. Полный рендеринг Answer/claims/фрагментов — F-04.

Вызов `render_layout(LayoutView)` возвращает типизированное событие send/settings
с уникальным event_id. UI-оболочка не делает HTTP-запросов. После подтверждённой
отправки вызывающий код увеличивает draft_revision; после обработанной попытки
без очистки черновика — submission_revision. session_key меняют при явной смене
сессии, чтобы не переносить её черновик в другой диалог. Поля не содержат bearer.
Настройки и блокировку ввода задаёт вызывающее приложение из серверного состояния.

Для просмотра из корня (отдельный свободный порт, остановка Ctrl+C):

```bash
PYTHONPATH=.:streamlit-ui .venv/runtime-env/bin/python -m streamlit run \
  streamlit-ui/layout_preview.py --server.address 127.0.0.1 --server.port 8504 \
  --server.headless true --browser.gatherUsageStats false
```

Открыть `http://127.0.0.1:8504`: состояния «Новый диалог», «Длинный диалог»,
«Ожидание», «Нет связи». Данные/ссылки синтетические; отправка добавляет только
локальную реплику просмотра. API/LLM не вызываются. Это отдельный просмотр;
старый чат прототипа не переключён на новые, ещё не готовые операции MVP-1.

Реализация F-07 подготовлена, но браузерная приёмка HD/Full HD/4K, Android,
200% текста, фокуса и экранной клавиатуры **не выполнена**. Макетные пороги и
цвета взяты из U-02; финальные визуальные параметры остаются уточнением UX/A-11.

## F-02: начальный адаптер HTTP-кандидата

`streamlit-ui/photo_ui/mvp_client/` содержит:

- `DraftApiClient`: чтение SessionSnapshot и ExecutionView, отправка MessageRequest,
  SettingsUpdate с проверкой типов и соответствия request/session/execution ID.
- `Transport`: BaseSettings, таймаут, bearer только в заголовке; без кеша, redirect
  и автоматических повторов. Тела ошибок и исключения транспорта не выдаются в UI.
  Неизвестная версия/невалидная схема дают ошибку совместимости.
- `DeliveryState`: восстановление из snapshot, монотонная revision, обнаружение
  принятого request_id после потерянного ответа, неизменный JSON отправки для
  явного retry. Сеть сохраняет снимок/черновик, 401 очищает локальные данные.
  После failed новая попытка должна быть отдельным явным действием с новым ID.

Хранить экземпляр DeliveryState только в `st.session_state`. До новой отправки
нужно успешное restore; prepare фиксирует сообщение/настройки, accepted/failure
требуют последующей сверки с API. Перечитывание не выполняет send автоматически.
Транспорт не реализует браузерный bootstrap или выдачу экспорта; их подключение
и полноценная обработка конфликтов виджетов остаются продолжением F-02/F-03.

Клиент использует `shared/http_draft` явно, изолирован от старого приложения.
По умолчанию сетевой доступ этого адаптера заблокирован:
`PHOTO_MVP_UI_ALLOW_DRAFT_CONTRACT=false`. Для будущего исследовательского API
требуются явное включение, `PHOTO_MVP_UI_BACKEND_URL` и timeout (10 секунд по умолчанию).
Сейчас готового runtime `/mvp1` нет; кандидат не объявлен стабильным контрактом.

## Какие схемы и кто согласует

Уточнение 2026-10-01: [жизненный цикл](session-lifecycle.md) и
[UI-потоки](ui-flows.md) достаточны как описание требуемого поведения и основание
для HTTP-схем. Уже утверждённые сценарии повторного согласования не требуют.
Они не заменяют точный транспортный контракт: имена и типы полей, обязательность,
формат ошибок, версии и ответы каждого маршрута фиксируются в DTO/OpenAPI и
[HTTP-кандидате](http-contract-draft.md). Превращение принятых требований в эти
форматы — работа Backend/Frontend; владельцу выносятся только действительно
открытые варианты поведения, а не каждое техническое поле.

Предметный Answer 1.1, четыре роли и внешний author уже приняты;
их повторное согласование не требуется.

| Схемы/часть | Что осталось | Участники |
|---|---|---|
| SessionActionRequest, BrowserContext, ошибки браузерных операций | Внести уже принятое expected_session_id в clear/opened, DTO/OpenAPI/примеры и backend. Согласование принципа B-15 уже есть | Backend реализует; Frontend/QA проверяют; DevOps сверяет allowlist |
| SessionSnapshot, ExecutionSummary/ExecutionView, RoleRef | selected_role для активного выполнения, коды ролей, длина имени, стабильная HTTP-версия. Не подставлять current_role как выбранную роль нового выполнения | Архитектор + Backend; Frontend/QA проверяют достаточность, UX — представление |
| MessageRequest/ExecutionAccepted, SettingsUpdate/SettingsReceipt | Полный snapshot, revisions, busy/конфликты и семантика квитанций H-02/H-03; предметная идемпотентность уже определена | Backend + Frontend, Архитектор/QA |
| CancelClarification, AnswerState, FeedbackUpdate/FeedbackReceipt | Отмена уточнения H-07; показ/оценка, revisions и ошибки H-08. Не относится к отдельной отмене активной генерации | Backend + Frontend/QA; UX уточняет действие/состояния |
| SourceCard, ExportPrepare/ExportReady, выдача Markdown | Исходный вопрос до уточнения, браузерный маршрут, TTL/лимиты/гонки экспорта H-05/H-06 | Архитектор + Backend + Frontend; DevOps/QA/UX по своей части |

Backend готовит конкретные модели/OpenAPI/JSON-примеры; архитектор отвечает за
семантику и совместимость; frontend подтверждает, что данных хватает UI.
Новые итоговые решения по обсуждению утверждает владелец. После этого backend
и frontend синхронно обновляют схемы и runtime, QA проверяет результат.
Экспорт и маршрутизация ролей не должны задерживать уже согласованное B-15.

### F-02: принадлежность и запоздавшие ответы

QA-D02 подтверждён чтением DraftApiClient.execution: метод принимает только token
и execution_id и не может сравнить ожидаемую сессию. Повтор отдельного теста
`qa_contract_audit.IndependentContractAudit.test_execution_rejects_foreign_owner_with_matching_execution_id`
2026-10-03 дал FAIL: ClientError не поднят. Согласованные между собой чужие ID
проходят Pydantic-валидацию; это не доказательство утечки реального API.

Требование к исправлению: execution(token, execution_id, expected_session_id)
с обязательным ожидаемым ID из snapshot, зафиксированным до HTTP-запроса.
Проверять оба идентификатора до выдачи результата вызывающему коду. Несоответствие —
ClientError(kind=protocol, code=session_mismatch/execution_mismatch), без отображения
Answer и без автоматической отправки/создания сессии. Внешний и вложенный session_id
должны совпадать с ожидаемым. API независимо проверяет bearer и владение выполнением.

В слое применения отдельно сверять актуальность: после clear, смены сессии или
запуска другого выполнения ответ старого polling не меняет ленту/статус новой работы,
даже если принадлежность исходному запросу корректна. Снимок API остаётся источником
истории; меньшая revision не откатывает более свежую. Ошибка протокола требует
повторного чтения состояния, не подстановки результата как успешного ответа.

Регрессии: правильная пара ID; чужая согласованная пара; правильная сессия и чужой
execution_id; смена/очистка между запросом и применением; потерянный 202; повтор
completed/failed без новой генерации. Изменение обязательного аргумента требует
обновить вызывающие места и QA-тест, сохранив его негативное ожидание.

### F-07: панели и отправка

QA-D03/QA-D04 принимаются как открытые дефекты локального preview. Наличие обработчиков
в shell.js и корректной геометрии не опровергает результат настоящего Streamlit.
Причина пока не установлена; нельзя объявлять её ошибкой API, сети HTTPS или CSS
без воспроизводимого подтверждения. В этом проходе браузер повторно не запускался.

Для QA-D03 проверить цепочку click → обработчик текущего root → state.panel →
setAccess → классы/aria/inert на том же видимом DOM. Если обработчик не вызывается,
проверить регистрацию/очистку при remount и принадлежность root текущему экземпляру.
Если вызывается — найти последующее изменение состояния. Новые listeners не должны
накапливаться на старом DOM после rerun. Фокус/Tab/Escape проверяются после открытия.

Для QA-D04 проверить submit/requestSubmit → emit(action,event_id,text) → result.action
в render_layout → валидация LayoutEvent → единственное применение в preview → rerun.
Отдельно проверить соседнее обновление draft и сохранение pending до подтверждения.
Это точки диагностики, не доказанные причины. Оба способа отправки должны давать
ровно одну user-реплику, очистку после принятия и сохранение текста при отказе.
Не устранять симптом автоматической повторной отправкой или сетевым вызовом.

### План QA и доступные среды

Матрица UI/F-02 достаточна как основа ранней проверки, с дополнениями выше и
раздельной проверкой selected_role/author по [A-13](query-routing.md#публичное-представление-и-примеры).
После исправлений нужны два разных прогона: F-07 на localhost в настоящем Streamlit
и F-01/B-15 через HTTPS. Изолированный HTML не заменяет F-07; подмена API не заменяет
cookie/ingress/WebSocket. В T-07 добавить Cmd+Enter на Mac, явную смену session_key
с очисткой черновика/панелей и проверку обоих вариантов подписи при разных ролях.

Свежие свидетельства доступности: локальный Python-аудит исполнен в этом проходе;
QA ранее запускал настоящий Chrome на Mac. Safari требует отдельного прогона,
Android-устройство/исполнитель не подтверждены, Firefox на ПК владельца — отдельная
проверка после восстановления доступа. Размер viewport не подтверждает физический
экран/Android, WebKit не подтверждает Safari. Новых результатов этих сред нет.
Пять сценариев check_session_probe.py остаются ожидающими восстановления сети;
отсутствие нового разрешения на HTTPS-прогон не заменяется отключением TLS.
