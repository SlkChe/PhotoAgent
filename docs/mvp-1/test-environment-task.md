Дата: 2026-09-23. Статус: в работе по поручению владельца; приёмка не выполнена.
Исполнитель: DevOps. Backend предоставляет фикстуры и клиентские сценарии,
QA независимо проверяет воспроизводимость. Задание самодостаточно: локальный
tasks.md не входит в Git.

DevOps подготовил и запустил кандидат стенда: [протокол проверок](deployment-checks.md),
[инструкция запуска](../deployment/local-mac.md). HTTP-сценарии и изоляция проверены;
согласование тестовой обвязки/фикстуры с backend и независимая приёмка QA впереди.

## Цель и границы

Добавить контейнер LiteLLM в отдельный тестовый профиль Docker Compose для
воспроизводимых HTTP-проверок B-07, а затем B-09/B-14. Первый реальный провайдер —
Groq; тестовый контейнер имитирует OpenAI-совместимый API без облачных вызовов.
Он не включается в обычное развёртывание MVP-1 и не маршрутизирует production-трафик.

D-05 можно начинать независимо от D-01 и архитектурного решения A-09.
Готовность D-05 не заменяет HTTPS/браузерный стенд D-01 для B-02 и реальные пробы B-07.
Изучить `.prompts/docker-rules.md`, `.prompts/code-style.md` и
[требования mock](integration-research.md#локальный-mock-для-тестов).

## Результат DevOps

1. Зафиксировать версию образа LiteLLM, способ сборки/получения и настройки mock.
   Проверить HTTP `/v1/chat/completions`: наличие библиотечного `mock_response`
   само по себе не подтверждает работу контейнера. Если выбранная версия не
   поддерживает нужный сценарий, описать пробел и согласовать с backend небольшой
   тестовый обработчик; не подменять результат реальными облачными ответами.
2. Изолировать mock в тестовой сети без исходящего доступа к провайдерам,
   upstream, fallback и рабочих ключей. При необходимости доступа с хоста
   публиковать порт только на loopback. Адрес клиента задаётся конфигурацией.
   Передача реального ключа Groq в этот контейнер запрещена.
3. Обеспечить healthcheck, управляемый выбор сценария, сброс состояния между
   тестами и безопасный счётчик обращений для проверки повторов. Не записывать
   заголовки авторизации и содержимое реальных диалогов в диагностические логи.
4. Документировать команды из корня репозитория: сборка, запуск тестового профиля,
   проверка готовности, выбор сценария, просмотр логов и остановка без удаления томов.
   Проверить, что обычный запуск Compose не поднимает LiteLLM.
5. Приложить протокол: версии, команды, результаты проверок и известные ограничения.
   Конфигурация Compose, инструкции и тестовые данные должны находиться в Git;
   секреты и локальные файлы окружения — нет.

## Приёмка совместно с backend и QA

| Проверка | Ожидаемый результат |
|---|---|
| Echo | Последний `user.content` возвращается как текст в OpenAI-совместимом ответе |
| JSON-фикстура | Заданный компактный черновик генератора, детерминированные числовые `prompt_tokens`, `completion_tokens`, `total_tokens` |
| Отказы | Управляемые 429 с Retry-After, 5xx, задержка до timeout, повреждённый JSON, `finish_reason=length`, отсутствующий/некорректный usage |
| Изоляция | Запросы работают без ключей провайдеров; исходящие подключения запрещены и не происходят |
| Повторы | Число HTTP-обращений наблюдаемо; backend проверяет возможность отключить автоматические повторы своего клиента |
| Воспроизводимость | После перезапуска/сброса сценарий даёт тот же результат; QA повторяет команды из инструкции |

Backend определяет форму черновика и поставляет фикстуры; публичный Answer
собирается и валидируется отдельно. Эхо не обязано соответствовать схеме Answer.
Проверка отказа до отправки при исчерпании бюджета, конкуренции сессий и отсутствия
сброса бюджета при смене провайдера относится к B-14; она не блокирует приёмку D-05.
Проверка качества русского ответа, реального usage и совместимости Groq остаётся
в B-07. Задача D-05 не требует завершённого адаптера B-09 для запуска стенда.
