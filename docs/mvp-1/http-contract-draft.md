## Версия и безопасность

HTTP-объекты имеют `contract_version: mvp1-http-draft.2`. Вложенный Answer и ApiError
сохраняют `schema_version: 1.1`. После согласования назначаем стабильную HTTP-версию;
не выдаём несогласованные поля под видом новой редакции предметного Answer 1.1.
ExecutionView — новый HTTP-конверт вместо прямого ExecutionResult для этого кандидата.
Добавленный код ошибки выполнения budget_exhausted относится только к кандидату.

Браузер обращается только к `/mvp1/browser/*`: cookie `__Host-photoagent` и отдельная
`__Host-photoagent-context`, HttpOnly/Secure/SameSite=Lax/Path=/, без Domain и
постоянного срока. Context-cookie тоже является секретом восстановления. GET context
не создаёт диалог и не продлевает TTL; чужой Origin/cross-site bootstrap отклоняется.
POST требует точный Origin и X-PhotoAgent-CSRF, связанный с контекстом. Create
повторяет выдачу cookie после потери ответа; clear отзывает доступ и меняет поколение
CSRF. Устаревшее создание не восстанавливает отозванный диалог. Подробный кандидат
механизма уже проверялся в [B-02](session-probe-backend.md); окончательное принятие — A-07.

Сервер Streamlit передаёт значение сессионной cookie в `Authorization: Bearer` для
`/mvp1/internal/*`. Эти пути закрыты внешним ingress; токен не передаётся JS,
не записывается в URL, файлы скачивания и логи. В Swagger это SessionBearer.
Все изменяющие операции через сервер UI возможны только по явному действию пользователя;
повторный рендер или polling не создают мутаций. Forwarded-заголовки не дают авторизации.
OwnerBearer — отдельный секрет/право, недоступное UI и пользовательской сессии.
Все ответы, включая ошибки и файлы, имеют Cache-Control:no-store.

## Синхронизация B-15 от 2026-10-01

Принятое требование expected_session_id внесено в общий
`shared/session_actions.py`: обязательные request_id и expected_session_id (UUID).
Его используют экспериментальный backend и OpenAPI-кандидат; runtime не импортирует
остальные draft-модели. Создание по-прежнему использует OperationRequest.
ID ожидаемой сессии фиксируется до confirm/Web Lock по показанному snapshot;
получение свежего CSRF и повтор сохраняют оба ID. После Origin/CSRF backend
атомарно сверяет текущую живую сессию: несовпадение → 409 session_changed,
без мутации, Set-Cookie и продления TTL. При отсутствии живой сессии clear → 204,
opened → 401; при совпадении проверяется cookie. Старый CSRF → 403 до мутации.
Проверка текущей сессии имеет приоритет над старой квитанцией clear.
Старый клиент с пустым clear/без expected_session_id получает 422, обхода нет.
Ошибки F-01 остаются `{detail: code}`, MVP-кандидат использует ApiError 1.1.

[Протокол совместной проверки B-01/B-15](b15-checks.md). Согласование поведения
не означает приёмки по HTTPS; полный кандидат сохраняет draft-статус.

Все пути ниже имеют префикс `/mvp1`. Поля nullable обязательны, лишние запрещены.
204 не содержит JSON. После 401 UI очищает копию состояния и предлагает явное создание;
ошибка сети/5xx не означает удаления диалога.

## Версии, повторы и активность

`revision` — версия всего публичного состояния, в том числе истории, стадии,
настроек, откликов и времени активности. `settings_revision` меняется только при
изменении настроек, `feedback_revision` — при изменении оценки/комментария ответа.
Это защищает от конфликтов настроек из-за обычного прогресса выполнения.

Для мутации request_id хранится с областью операции, целевым объектом и отпечатком
тела в RAM сессии. Проверять доступ/TTL, затем прежний request_id, затем версии,
занятость и лимиты. Для message сохраняется принятая нормализация текста и
первоначальные настройки. Retry всегда несёт прежнее тело; смена тела — 409,
а новая явная попытка после failed использует новый ID.
Повтор принятой операции не меняет TTL и не выполняет побочный эффект снова.
При переполнении ограниченного журнала отклонять новую мутацию, не вытеснять запись
так, чтобы её повтор стал новым действием. Конкретная ёмкость — конфигурация A-09.

SettingsReceipt/FeedbackReceipt — квитанции исходной операции: поздний retry может
вернуть более старую версию, чем текущая. UI не откатывает локальную версию, после
подтверждения перечитывает snapshot. PUT shown идемпотентен по answer_id и возвращает
текущее AnswerState; request_id не нужен, TTL не меняется.

Новая принятая реплика, реальное изменение detail/level, изменение отзыва и новое
явное открытие продлевают TTL по принятому жизненному циклу. GET, shown, экспорт,
повторы и запись того же состояния не продлевают. Для отдельной команды отмены
уточнения предлагается не менять TTL: она не является новой репликой. Отмена не
запускает LLM и не удаляет историю. Это уточнение вынесено на согласование H-07.
Фоновое переключение стадии не меняет TTL, хотя повышает revision.
Стартовые brief/beginner/ru уже приняты в UI-концепции и решении о языке;
повторного согласования не требуют. H-02 касается поведения при busy и конфликтах.

## Настройки и отправка

PUT settings заменяет полный набор detail/level/locale. Рекомендация MVP: при активном
выполнении возвращать 409 session_busy; UI делает настройки временно недоступными.
При устаревшем expected_settings_revision — 409, UI получает новый snapshot и
предлагает явно применить желаемые значения. Старые ответы не изменяются.
Неподдерживаемая locale даёт 422. Выбор языка не выводится из языка ввода.

MessageRequest содержит текст, settings_revision и полный снимок settings. Для
новой отправки они должны соответствовать текущим настройкам; для retry проверяется
прежняя принятая отправка раньше текущей версии. Backend не принимает тихо иные
настройки. Отправка ответа на уточнение указывает clarification_id; при сменившемся
ожидании — 409 clarification_conflict. Обычная новая тема передаёт null; отказ от
старого уточнения при этом определяет согласованный локальный анализатор.

## Восстановление, роли и источники

Snapshot полностью восстанавливает ленту, текущую роль, настройки, первичные карточки,
оценки и список выполнений с ошибками. Полная выдача без пагинации предлагается только
для ограниченной сессии MVP; пределы реплик/размера согласуются по A-09. История
не обрезается молча. При исчерпании лимита API отклоняет новую отправку, UI предлагает
экспорт/новую сессию. Предлагаемый код — 409 session_history_limit; численный предел остаётся конфигурацией.

Принятый запрос попадает в messages и executions атомарно до ответа 202.
После потери 202 и refresh UI находит request_id/execution_id в snapshot и продолжает
GET выполнения. Новый запрос не создаёт. При failed пользовательская реплика и
безопасная ошибка остаются; частичный ответ генератора не появляется.

Порядок messages — серверный; не пересортировывать по времени или роли. `author`
каждого assistant-сообщения фиксируется при публикации, `current_role` может меняться.
Внешний HTTP-конверт авторства вокруг Answer 1.1 принят владельцем
(фиксация 2026-09-30); версию самого Answer из-за подписи не меняем. Список role_id и маршрутизация ролей требует A-13/эксперта;
friend/art_historian в примерах — кандидаты, а не утверждение полного реестра.
display_name — непустая строка до 20 Unicode code points; вопрос графем — H-04.

Карточки вычисляет backend: одна на точную строку URL, порядок первого появления.
source/first_answer_id/first_message_id фиксируются по первому ответу. Комментарий —
исходная реплика первого запроса без дополнительной генерации; UI может визуально
сокращать её. Новый ответ с тем же URL не заменяет карточку и её метаданные.
Его Answer при этом содержит собственные источники и фрагменты. Переход — по
first_message_id, а не поиск совпадающего URL в последнем ответе.

## Оценки и статистика

AnswerState хранится отдельно от Answer. Положительная оценка отправляется с
comment=null; старый отрицательный комментарий удаляется. При negative null
удаляет комментарий, непустое значение заменяет его. Самостоятельное снятие оценки
до no_feedback пока не предлагается: UI требует только positive/negative.
Перед оценкой UI подтверждает shown; если запрос показа не принят, отзыв получает
409 answer_not_shown. Повтор shown не меняет feedback_revision и не продлевает TTL.
Для invitation/clarification/out_of_scope eligible=false; их показ не считается.

StatsReport содержит дневные суммы и completeness без пользовательских ID/текстов.
Показанные ответы разбиты на positive, negative, итоговые no_feedback и
pending_feedback живых сессий. Нулевой знаменатель долей означает «нет данных».
Привязку отзывов/исправлений к дню, долговечность и completeness должен подтвердить
A-08; предлагается день первого подтверждённого показа с последующими корректировками.
from_date/to_date — UTC, включительно, в доступных 30 днях. Точная календарная граница
зависит от A-08. Неизвестный день/утраченные данные нельзя молча представить нулями.
Для недоступного хранилища — 503; частичный отчёт явно помечен partial/unknown.
Владельцу предлагается отдельный Bearer через HTTP-клиент с окружением, без UI-экрана;
альтернатива — аутентификация владельца на ingress. Ключи в файлы/URL не добавляются.

## Экспорт и гонки

Рекомендация: backend фиксирует один RAM-снимок и формирует оба файла. При prepare
проверяются доступ/TTL и expected_revision, затем под короткой блокировкой копируются
публичные данные. Генерация/поиск не запускаются, partial-текст не экспортируется.
При активном выполнении в диалоге остаётся пометка о незавершённом ответе.
Успех возвращает export_id, snapshot_revision, срок и доступные kind. Если диалог
пуст — 409 export_empty; без источников available содержит только dialogue.

Оба файла относятся к одной версии независимо от завершения нового ответа.
Это временный ресурс операции в RAM, не постоянная история и не общий HTTP-кеш.
Срок предлагается конфигурируемым, не позже срока сессии; лимит снимков обязателен.
Каждое скачивание снова проверяет владельца и TTL. Clear/TTL удаляют снимки;
новая сессия не получает старые файлы. Не обещаем отозвать уже отправленные клиенту байты.

Повтор prepare с прежним request_id возвращает прежний снимок; после его срока —
410, не создаёт свежий незаметно. Новый снимок — новый ID и актуальная revision.
При revision conflict UI обновляет состояние и предлагает повтор, не создаёт
бесконечный автоматический цикл. GET можно повторить пока ресурс жив.
Файлы: UTF-8, Content-Disposition attachment с безопасными именами dialogue.md и
sources.md; экранирование Markdown, локальные якоря вместо ссылок на живую сессию,
без bearer/request_id/execution_id и внутренних данных. source URL остаются.

## Бюджеты и ошибки

ApiError 1.1 сохраняется; retryability определяется кодом, не текстом message.
401/403 не вызывают автоматического создания сессии. 409 требует сверки состояния
или исправления действия, 422/413 — исправления ввода, 429 — ожидания/явной попытки,
503 — временной недоступности. Retry-After, если известен, задаётся в секундах;
он не разрешает повторную платную генерацию автоматически.

429 rate_limited/budget_exhausted до принятия не создаёт выполнение и не продлевает
TTL. Если бюджет закончился после принятия, предложение — failed с кодом
budget_exhausted в новом ExecutionView; принятую реплику не теряем, сырой ответ не
показываем. Частично успешный поиск может дать ограниченный Answer по уже принятым
правилам, если хватает бюджета генерации. Точная политика — H-09/A-09/B-14.
Для уже принятого request_id повтор не отвергается новой предварительной квотой.

## Вопросы для согласования

В каждом пункте вариант A — рекомендация backend, B — альтернатива. Это не решения.
Frontend отвечает о достаточности UI, архитектор — о совместимости, затем владелец
выбирает вариант. Принятые ранее TTL, язык, виды Answer и отсутствие экрана статистики
повторно не согласовываются.

| ID / адресат | Вариант A | Вариант B | Что подтвердить |
|---|---|---|---|
| H-01 · A/F/D | Браузерный bootstrap/clear + внутренний Bearer от UI; механизм B-02 | Отдельный BFF с другим bootstrap, после дополнительного эксперимента | Граница маршрутов, ротация CSRF и потерянный ответ создания |
