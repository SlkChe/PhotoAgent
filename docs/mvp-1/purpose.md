# MVP-1: AI-наставник по истории и теории фотографии

**A-01 «Зафиксировать границы MVP и исключения»: закрыта, 2026-09-21.**
Этот документ фиксирует функциональный объём MVP-1. A-02–A-04 также закрыты;
описания тематик и диалога находятся в [архитектурном разборе](architect.md).
Закрытие архитектурных задач не означает завершения реализации.

MVP — анонимный диалоговый сервис, который отвечает на вопросы об истории фотографии, её техническом развитии, художественных направлениях, авторах, организациях и произведениях. Он ищет материалы во внешних источниках, сопоставляет их и формирует понятный ответ со ссылками.

**Архитектурный принцип:** локально понимаем запрос и управляем поиском, во внешних источниках получаем сведения, облачной LLM поручаем формулирование ответа. Под «LLP» далее подразумеваются LLM.
Это первый самостоятельный модуль будущего универсального помощника фотографа, а не весь ранее обсуждавшийся набор функций.

Уточнения пользователя от 2026-09-21: разбор входящих запросов и планирование строго локальны.
MVP предназначен для закрытой группы до 30 человек, с одновременной работой 2–3 человек.
Анонимная сессия временная, переживает обновление страницы и имеет срок жизни 12 часов бездействия.
Регистрация пользователей рассматривается на следующем этапе.
Согласовано восстановление диалога через защищённую cookie.
Срок продлевают действия пользователя: отправка сообщения/уточнения, изменение настроек объяснения,
оценка ответа, явное открытие или обновление страницы.
Опрос статусов показывает ход обработки и готовый ответ без продления TTL, heartbeat для продления не используется.
Согласовано хранение в RAM одного процесса API с потерей информации при перезапуске
core-сервиса. Доступ группы ограничен существующей приватной сетью; единый HTTPS-вход
обеспечивает ingress-прокси.
Для хоста приложения один браузерный профиль использует один активный диалог;
его вкладки и окна не создают параллельных диалогов. Переписка, уточнения и текст
обратной связи хранятся только до завершения сессии.


## 1. Цель и границы продукта
Ценность для пользователя
Пользователь получает не просто историческую справку, а возможность:
- задать вопрос обычным языком;
- получить объяснение с учётом своего уровня;
- проверить утверждение или распространённую легенду;
- сравнить авторов, техники и художественные подходы;
- перейти от краткого ответа к подробному обсуждению;
- изучить источники и продолжить самостоятельное исследование.
**Основной цикл:**
Вопрос → понимание темы → поиск → ответ с источниками → уточняющее обсуждение.

### Что входит в MVP
| Возможность                           | Содержание                                                              |
| ------------------------------------- | ----------------------------------------------------------------------- |
| Анонимный текстовый диалог            | Без регистрации и личного кабинета                                      |
| Локальный разбор запроса              | Тематика, задача, сущности, ограничения, связь с предыдущими репликами  |
| Многотемная маршрутизация             | Один вопрос может относиться к нескольким разделам                      |
| Уточнение неоднозначностей            | Один содержательный вопрос, если без него возможна существенная ошибка  |
| Внешний поиск                         | Облачные MCP-серверы и API wiki-справочников                            |
| Формирование доказательного контекста | Отбор фрагментов, источники, устранение повторов, фиксация противоречий |
| Облачная генерация                    | Одна модель, выбранная конфигурацией развёртывания; сменяемые адаптеры позволяют последовательно испытывать разные LLM и агрегаторы |
| Ответы со ссылками                    | Ссылки на конкретные материалы, использованные в ответе                 |
| Продолжение разговора                 | Сохранение предмета обсуждения внутри сессии                            |
| Настройка объяснения                  | Кратко/подробно; для начинающего/подготовленного читателя               |
| Завершение сессии                     | Очистка диалога и временных данных                                      |
| Обратная связь                        | «Понравился / не понравился», необязательный текст жалобы при отрицательной оценке |
| Общая статистика                      | Агрегаты технических ошибок и оценок; отсутствие отклика учитывается отдельно как условно положительный результат |

### Что не входит
- художественная и техническая критика загруженных фотографий;
- установление автора неизвестного снимка по изображению;
- обработка и генерация фотографий;
- подбор покупок, студий и локаций;
- актуальная афиша предстоящих мероприятий; история выставок и их художественное значение остаются в образовательной тематике;
- бронирование, оплата, переписка от имени пользователя;
- долговременный профиль и история обучения;
- массовая загрузка внешних архивов;
- собственная универсальная энциклопедия фотографии;
- отдельные автономные агенты-персонажи с независимой памятью.

Персонализация агентов (например _персонаж "Проскура" или "Теоретик"_) может быть стилем подачи уже в MVP, но не требует отдельной модели или отдельного исследовательского процесса.

### Обратная связь и оценка пилота

У содержательного ответа пользователь может нажать «Понравился» или «Не понравился».
Во втором случае можно оставить необязательный комментарий, например «неверная дата»
или «ссылка не открывается». Комментарий и его связь с ответом удаляются вместе с сессией.

В общей статистике раздельно учитываются явные положительные оценки, явные отрицательные
и отсутствие отклика. Последнее считается условно положительным по принятому правилу
пилота, но не отображается как поставленный пользователем положительный отзыв.
Техническая ошибка без показанного содержательного ответа не считается условно
положительным ответом. Общие счётчики не содержат переписки и идентификаторов сессий.
Общая статистика хранится 30 дней, затем устаревшие агрегаты удаляются автоматически.
Для хранения выбрана собственная реализация JSON-файлов с дневными агрегатами
на постоянном томе, доступном только backend.
Доступ к статистике получает только владелец проекта через защищённую выгрузку
JSON; отдельный экран статистики в MVP-1 не создаётся (решение 2026-09-23).
Конкретный механизм проверки доступа описывается в HTTP-контракте B-01;
анонимный токен сессии и доступ к приватной сети не предоставляют права владельца.
Инструменты мониторинга, например Grafana, отложены за пределы MVP-1;
это не отменяет предусмотренные агрегаты ошибок и откликов.

Этот срок не распространяется на переписку и комментарии: они удаляются с сессией.
Подробная семантика учёта — в [жизненном цикле данных](session-lifecycle.md#учёт-оценок-и-отсутствия-отклика).


## Язык MVP-1

Решение владельца от 2026-09-23: язык интерфейса и ответов — русский.
UI и API проектируются с возможностью последующего выбора языка: выбранная
локаль определяет язык интерфейса, ответа и локализацию предметной области вопроса,
даже если пользователь ввёл текст на другом языке. Язык ввода не переключает
локаль автоматически. Под локализацией предметной области понимаются отображаемые
названия тематик, терминология и пояснения; смысл вопроса и идентичность сущностей
сохраняются. Язык не задаёт географическое ограничение поиска.
В MVP-1 поддерживается только `ru`; другие переводы и переключатель не требуются.
Правила передачи локали: [контракты](contracts.md#язык-и-локализация).

## 2. Предметная область
**Используем пять тематик**, и они не взаимоисключающие.
| Код          | Раздел                   | Примеры содержания                                                         |
| ------------ | ------------------------ | -------------------------------------------------------------------------- |
| `technology` | Техника и процессы       | Камеры, оптика, светочувствительные материалы, печать, цифровые технологии |
| `art`        | Фотография как искусство | Направления, школы, эстетика, критика, выставки                            |
| `actors`     | Участники индустрии      | Фотографы, изобретатели, редакторы, кураторы, агентства, издательства      |
| `genres`     | Жанры                    | Портрет, пейзаж, документальная, уличная, fashion-фотография               |
| `works`      | Произведения             | Снимки, серии, фотокниги и история их создания, публикации и восприятия    |

Независимо от темы, требуется определить тип задачи (что ожидает клиент):
- краткая справка;
- объяснение понятия;
- исторический обзор;
- хронология;
- сравнение;
- проверка утверждения;
- объяснение художественного значения;
- подбор источников.
Например: "Как малоформатная камера повлияла на фотожурналистику?" относится одновременно к technology и genres, а задача — объяснить историческое влияние.
Технические вопросы допускаются в образовательном контексте. "Как работает дальномер?" — внутри MVP.
"Какую камеру купить?" — вне его границ.

## 4. Интерфейс

При утверждении UI-концепции добавлены: поле ввода высотой 4–7 строк; контекстный
комментарий у карточки источника; меню с переходом к первичному ответу и открытием
ссылки в новой вкладке. Повторные ссылки не создают карточки и не меняют первичную
привязку. Все внешние ссылки открываются в новой вкладке. В MVP-1 входят скачивание
диалога в `.md` и отдельное скачивание всех источников. Скачивание и его повтор
не продлевают срок сессии. Экспорт — пользовательский
файл, а не постоянная история на сервере; см. [концепцию](../ui/concept.md).

Уточнения владельца от 2026-09-22: аудитория — начинающий и развивающийся фотограф.
Новая сессия начинается с «О чём поговорим сегодня?» без имени специалиста.
Backend выбирает роль ассистента по каждой реплике с контекстом; прямое обращение
«хочу поговорить с искусствоведом» допускается без вопроса. Уточнение может сменить
роль без нового диалога. Имя до 20 символов показывается над ответом и у текущего
ассистента; иконок в MVP-1 нет. Предусмотрен ассистент-друг по умолчанию и для очень
широких вопросов, без добавления шестой предметной темы. На правых полях собраны
ссылки всего текущего диалога. Подробности — в [UI-брифе](ui-design-questions.md)
и [утверждённой концепции](../ui/concept.md). Дополнение контрактов роли
предстоит согласовать архитектору и backend.
Минимальный экран:
- поле вопроса;
- история текущего разговора;
- переключатель «Кратко / Подробно»;
- карточки источников;
- кнопка «Очистить диалог»;
- кнопки «Понравился / не понравился» у ответа;
- необязательное поле комментария после «Не понравился» и действие отправки;
- понятное сообщение о технической ошибке.
- Во время обработки показываются понятные статусы:
- «Уточняю предмет вопроса»;
- «Ищу источники»;
- «Сопоставляю материалы»;
- «Готовлю ответ». Не показываем внутренние рассуждения модели.

Структура ответа адаптивная:
- прямой ответ;
- необходимое объяснение;
- примеры или сравнение;
- оговорки и спорные сведения;
- источники;
- при необходимости — варианты продолжения.


## 5. Сценарий обработки одного запроса

### Шаг 1. Восстановить контекст или создать новый контекст и сессию
Backend получает сообщение и контекст текущей сессии:
- активную тему;
- упоминавшиеся сущности;
- ограничения периода и географии;
- последние релевантные реплики;
- краткое резюме обсуждения.
Не нужно передавать всю историю во все компоненты.

### Шаг 2. Локально разобрать вопрос
Результат — структурированный QueryAnalysis:
| Поле                  | Содержание                                   |
| --------------------- | -------------------------------------------- |
| `intent`              | Задача пользователя                          |
| `topics`              | Одна или несколько тематик                   |
| `entities`            | Имена, произведения, технологии, организации |
| `time_scope`          | Период, если задан                           |
| `geography`           | Географические ограничения                   |
| `subquestions`        | Подвопросы                                   |
| `ambiguities`         | Неразрешённые значения                       |
| `needs_clarification` | Необходимо ли уточнение                      |
| `in_scope`            | Соответствие границам MVP                    |
| `context_update`      | Изменения состояния диалога                  |
Самооценку уверенности, выданную LLM, не следует считать вероятностью правильного ответа.
Решение об уточнении проверяется на эталонных примерах.

### Шаг 3. Уточнить — только при необходимости
Например, фамилия относится к нескольким людям, а контекст не позволяет выбрать.
Если вопрос просто широкий, сервис сначала даёт полезный обзор и предлагает углубление.
Он не должен превращать каждое обращение в анкету.
Допускается максимум один раунд уточнения на исходный запрос. Если неоднозначность
осталась, ответ показывает варианты и ограничения без повторной анкеты.
Один широкий вопрос либо несколько вопросов одной темы переключают алгоритм
в режим тематического обзора с сохранением покрытия подвопросов. Неопределённый
предмет обсуждения по-прежнему требует уточнения; обзор не подменяет идентификацию.
Во время обработки нового вопроса ввод в UI заблокирован. API отклоняет новую
реплику с ошибкой и статусом `in_progress`; опрос состояния и очистка доступны.

### Шаг 4. Построить план поиска
Для каждого подвопроса определить:
- поисковую формулировку;
- русские и оригинальные варианты имён;
- предпочтительные источники;
- подходящий MCP/API;
- предел количества результатов;
- бюджет времени и внешних вызовов.
Модель выбирает только зарегистрированные инструменты.
Она не создаёт произвольные адреса API.

### Шаг 5. Получить сведения
В MVP предусмотрены два пути:
- MCP-поиск: поиск материалов и, если инструмент поддерживает, получение текста страницы;
- wiki API: поиск сущностей, энциклопедических записей и связанных данных.
Если MCP возвращает только сниппет, его нельзя выдавать за прочитанный полный документ.
Нужен разрешённый механизм получения текста либо ответ с явно ограниченной доказательной базой.

### Шаг 6. Собрать доказательный контекст
Для каждого фрагмента сохраняются:
- идентификатор источника;
- адрес и название;
- автор или организация, если известны;
- текст фрагмента;
- дата публикации, если доступна;
- время получения;
- тип источника;
- связь с подвопросом;
- ограничения использования.
Затем выполняются:
- удаление повторов;
- фильтрация нерелевантного;
- ранжирование;
- проверка покрытия подвопросов;
- выделение расхождений;
- ограничение объёма контекста.
Для спорных утверждений желательно независимое подтверждение.
Несколько сайтов, перепечатавших один текст, не являются независимыми источниками.

### Шаг 7. Передать контекст облачной LLM
Генератор получает:
- вопрос;
- необходимый контекст диалога;
- выбранные фрагменты;
- идентификаторы источников;
- требования к стилю;
- правила работы с противоречиями и недостатком сведений.
Числовые эмбеддинги в генератор не передаются.

### Шаг 8. Проверить и показать ответ
Backend проверяет:
- корректность структуры;
- существование упомянутых идентификаторов источников;
- отсутствие придуманных ссылок;
- наличие обозначения пробелов, если поиск был неполным;
- соблюдение границ сценария.
