Дата: 2026-10-03. Исполнитель: Backend/тимлид.
Статус: базовое сравнение; независимая проверка QA и полная проверка ролей отдельно.

## Границы результата

Сравниваются прозрачные правила/словари и Qwen3-0.6B Q8_0 через llama.cpp.
Это исследовательский код `scripts/b03/`, не реализация B-06 и не выбранный
production-runtime. Зависимости приложения, HTTP-контракты и корпус QA не менялись.
Облачных вызовов нет. HTTPS, Groq и доступ к пользовательским данным не нужны.

Основание: [методика B-03](test-plan.md#согласование-базовой-проверки-b-03),
[маршрутизация](query-routing.md), [контракты](contracts.md).
Корпус QA **0.3.0**, 43 случая: 10 development, 33 evaluation.
SHA-256: `a71d9cf28d72ccbe187aefbf2376201a855c539e89988df5058e5663c768d2e7`.
Evaluation — открытый фиксированный контрольный набор, не слепая выборка.

Настройка велась только на development. Три предварительные версии промпта:
текст правил; текст + JSON Schema; текст + JSON Schema + два примера T02-001/004.
Последняя дала 5/10 точных наборов topics и 6/10 intent на development;
после этого добавлено поле для экспертной проверки декомпозиции и конфигурация
заморожена. Итоговая версия заново проверена на всех 43 случаях.
Ожидаемые ответы evaluation не включались в словари, промпт или few-shot.
После просмотра контрольных результатов анализаторы не дорабатывались.
Для следующей итерации этот набор уже использован: нужны новые контрольные примеры QA.

## Измеренный результат

**В проверенной конфигурации ни один кандидат не рекомендован как готовый анализатор B-06.**

выбирает необходимость уточнения. Оба пропускают блокирующую неоднозначность
и не выполняют декомпозицию. Валидный JSON не доказывает корректность плана.

### Сущности и планирование: техническое ревью Backend

Это разбор наблюдаемых ошибок, не независимая экспертная приёмка QA и не
автоматический NER exact-match. `none` исследовательской проекции соответствует
запрету вызова (`forbidden` в корпусе); сами search/cloud вызовы не исполнялись.

| Случай | Наблюдение | Последствие для B-06 |
|---|---|---|
| T02-013 | Оба связали «она» с author-a | Простая анафора с одним кандидатом работает |
| T02-014/015 | Оба допускают поиск при неразрешённом объекте; 014 копирует все сущности | Нужна проверка разрешённости ссылки до плана |
| T02-017 | Правила копируют всех кандидатов, модель теряет выбранного автора | «Первый из двух» не разрешён корректно |
| T02-020 | Правила запрещают генерацию, модель запрашивает новые факты | Reuse Evidence/переформулировка не реализованы надёжно |
| T02-023/029 | Оба теряют исключение проката; правила также реагируют на отрицание магазина | Разделять допустимую часть и отрицание до поиска |
| T02-027 | Правила не понимают английский; модель оставляет label `shutter speed` | Локализация домена в locale=ru не обеспечена |
| T02-031–033 | Модель допускает поиск/генерацию для invitation | Служебные ветви должны исполняться локально до генератора |
| T02-037 | У обоих subquestion_intents=[] | Нет требуемой декомпозиции history/compare/fact_check |
| T02-038 | Модель запрещает поиск, но допускает cloud_generation | Проверяемые инварианты плана обязательны |

Baseline не извлекает новые сущности из текста, только переносит context.entities;
это явное ограничение, а не нулевая потребность в NER. Модель извлекает часть
технических терминов (например T02-028/035), но иногда подменяет вид сущности
тематикой и копирует нерелевантный контекст. Ни один кандидат не готов исполнять
свой план без проверки кодом.

Рекомендация для A-09: сохранить правила как воспроизводимый baseline, проверить
более способную локальную модель на новых контрольных примерах и отдельно
измерить CPU/Docker-конфигурацию целевой среды. Размер следующей модели и бюджет
должны быть согласованы по ресурсам; текущие 1.66 GiB RSS не доказывают предел
полного потребления памяти. Готового production-кандидата этот проход не выбрал.

## Кандидаты и конфигурация

- `rules`: фиксированные регулярные выражения для тематик/intent и диалоговых
  актов, переданные сущности контекста, простые условия поиска/reuse/уточнения.
  Морфологии, NER и полноценного планировщика нет. `subquestion_intents=[]`
  означает отсутствие декомпозиции у этого baseline, а не её успешную реализацию.
- `model`: [официальные веса Qwen3-0.6B-GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF),
  ревизия `23749fefcc72300e3a2ad315e1317431b06b590a`, Q8_0, 639446688 байт.
  [llama.cpp b11146](https://github.com/ggml-org/llama.cpp/releases/tag/b11146),
  версия `0.5.0-dev`, commit `7fe450e19`, официальный macOS ARM64 binary.
  Лицензии весов и runtime сохраняются в исходных пакетах.

MacBookPro18,2, 32 GiB RAM, 10 CPU, macOS 14.8.9 ARM64, Python 3.14.7,
Pydantic 2.13.5. Native Mac: это **не** измерение Docker Stage или будущего VPS.
4 потока generation/batch, 3 слота, общий context 12288 (4096 на слот);
выбор устройства/offload автоматический, без принудительного CPU-only.
Thinking выключен, temperature=0, seed=42, максимум 768 выходных токенов,
HTTP timeout=120 секунд. Это исследовательские параметры локального анализа;
они не заменяют отдельные квоты облачной генерации B-14.
Гарантии битовой повторяемости на другом железе нет.

Один warm-up на T02-001, отдельно от метрик. Затем 3 полных последовательных
повтора и 3 повтора с максимумом 3 запросов одновременно. Контекст каждого случая
передаётся заново, `cache_prompt=false`, cache RAM отключён. Примеры промпта общие,
но выход предыдущего теста в историю следующего не добавляется.
Задержка — от начала работы клиента до валидированного ответа, включая HTTP
и ожидание сервера; очередь executor до старта клиента не включена. Внутренняя
очередь сервера отдельно не измерена; сохранены его token/timing counters.

p50/p95 — nearest rank, отдельно по split и режиму, ошибки остаются в n.
Три повтора одного случая не являются тремя независимыми примерами качества.
RSS — выборочная сумма runner + llama-server через `ps` каждые 100 мс;
это не полный расход unified/GPU memory и не memory budget для A-09.
Быстрый baseline получает один RSS sample на режим; микросекундные различия
между serial/parallel3 не интерпретируются как выигрыш масштабирования Python.
Startup — запуск нового процесса до `/health`, с уже загруженными в ОС файлами;
не измерение холодного дискового кеша. Startup/warm-up не включены в warm latency.

## Воспроизведение

Из корня проекта, после установки существующих `requirements-dev.txt`.
Runtime/веса расположить в игнорируемой `.venv/b03-research/`.
Новые production-зависимости не устанавливаются. Источники загрузки:

```sh
mkdir -p .venv/b03-research
curl -fL --retry 2 -o .venv/b03-research/Qwen3-0.6B-Q8_0.gguf \
  https://huggingface.co/Qwen/Qwen3-0.6B-GGUF/resolve/23749fefcc72300e3a2ad315e1317431b06b590a/Qwen3-0.6B-Q8_0.gguf
curl -fL -o .venv/b03-research/llama-b11146-bin-macos-arm64.tar.gz \
  https://github.com/ggml-org/llama.cpp/releases/download/b11146/llama-b11146-bin-macos-arm64.tar.gz
```

Перед распаковкой/исполнением проверить SHA-256 обоих файлов:

| Файл | SHA-256 |
|---|---|
| Qwen3-0.6B-Q8_0.gguf | `9465e63a22add5354d9bb4b99e90117043c7124007664907259bd16d043bb031` |
| llama-b11146-bin-macos-arm64.tar.gz | `1ad3f9eff80edb9dbef4259ad564d1720612ef7eea48fa4afed0e54f5f3d5711` |

Распаковать archive с `tarfile.extractall(..., filter="data")` в ту же директорию;
получится `llama-b11146/llama-server`. SHA-256 исполняемого файла этого прогона:
`41df13c126456f8e5fab2057c86a790067a85ea1dfd8fbc0071cc45fbba56262`.
Порт 8087 должен быть свободен. Runner запускает только свой loopback-сервер,
передаёт ему PATH/HOME без секретов и завершает его в finally.
Не запускать кандидатов одновременно и не совмещать с нагрузкой стенда.

```sh
.venv/runtime-env/bin/python -m scripts.b03.run --candidate rules \
  --split all --repeats 3 --output .venv/b03-research/recheck-rules
.venv/runtime-env/bin/python -m scripts.b03.run --candidate model \
  --split all --repeats 3 --output .venv/b03-research/recheck-model
```

Каталог результата должен быть новым: существующие измерения не перезаписываются.
Manifest содержит revision базы Git и SHA-256 всех модулей исследовательского
инструмента, поскольку новые файлы во время замеров ещё не закоммичены.
`records.jsonl` содержит финальные JSON-выходы/ошибки, latency и usage каждого
случая; reasoning trace не запрашивается и не сохраняется.
`summary.json` содержит метрики, ошибки по case_id, ресурсы и вариативность повторов.
`server.log` остаётся в локальном исследовательском окружении, под Git не переносится.
