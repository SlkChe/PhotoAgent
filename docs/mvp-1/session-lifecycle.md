## Утверждённые требования

- Полностью временная анонимная сессия.
- Обновление страницы сохраняет возможность продолжить диалог.
- Удаление после 12 часов бездействия.
- TTL продлевают только действия пользователя, перечисленные ниже.
- Опрос статусов сохраняется и не продлевает TTL; heartbeat для управления TTL не нужен.
- Диалог восстанавливается через защищённую браузерную cookie.
- Один активный диалог на браузерный профиль для хоста приложения; вкладки и окна
  этого профиля используют одну сессию, второй параллельный диалог не создаётся.
- Вся переписка и текстовая обратная связь хранятся только до завершения сессии.
- Собирается общая статистика технических ошибок и откликов; отсутствие отклика
  учитывается отдельной категорией как условно положительный результат пилота.
- Общая статистика хранится 30 дней, затем устаревшие агрегаты удаляются автоматически.
- Хранилище статистики — собственная реализация дневных JSON-файлов (решение 2026-09-22).
- Закрытая группа до 30 участников, одновременно работают 2–3 человека.
- Регистрация рассматривается на следующем этапе.

## Восстановление через защищённую cookie

Выбор защищённой cookie, RAM-хранилища и единого HTTPS-входа через ingress утверждён.
Точные параметры интеграции остаются проектом реализации.

История, контекст, настройки, ожидающее уточнение, Evidence и выполняемые задания
хранятся в RAM одного процесса API. UI восстанавливает их из API при новом подключении.
Перезапуск UI допускает восстановление при живом API; перезапуск API теряет сессии.
Потеря информации при перезапуске core-сервиса явно согласована пользователем.
Постоянная БД для MVP-1 не требуется.

Одного `st.session_state` недостаточно: при перезагрузке страницы сбрасываются
WebSocket и связанное состояние. Это описано в
[документации Streamlit](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.session_state).

Утверждён один HTTPS origin для UI и ограниченных браузерных маршрутов сессии.
Ingress-прокси маршрутизирует запросы к Streamlit и API; группа работает
в существующей приватной сети. Для локального стенда D-01 выбран и запущен Caddy
в Docker; [протокол HTTPS/WebSocket](deployment-checks.md). Это не завершает
эксперимент браузерной сессии B-02. Ingress не вводит требование Kubernetes.
Первое создание сессии выполняется браузерным POST к API, который устанавливает
случайный непрозрачный токен в cookie с `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`,
без `Domain`. После этого браузер переходит в UI. Одного серверного HTTP-запроса
Streamlit → API недостаточно: его Set-Cookie не попадает автоматически в браузер.

Cookie предлагается сессионная, без Expires/Max-Age: срок доступа проверяет backend.
Cookie предназначена для восстановления страницы, не содержит текстов диалога,
ключей внешних провайдеров или личности участника. HttpOnly запрещает чтение
из JavaScript. Семантика атрибутов: [Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie).
При восстановлении браузерной сессии cookie может сохраниться после закрытия браузера;
это не гарантирует возвращения и никогда не продлевает серверный TTL само по себе.

Streamlit может прочитать входящие cookies через доступный только для чтения
[`st.context.cookies`](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.context).
Получение cookie на WebSocket-подключении и восстановление после refresh необходимо
проверить сквозным экспериментом с установленной версией Streamlit и выбранным прокси.
Серверный клиент UI передаёт токен API отдельным заголовком. Backend проверяет токен,
срок и соответствие сессии при каждом обращении. ID сессии не даёт права доступа.
В RAM API хранится хеш токена; само значение не выводится в URL, логи или диагностику.

При очистке backend отзывает старый токен и отменяет выполнение; браузерный маршрут
сбрасывает cookie. Новая сессия получает новый токен; для чтения нового cookie UI
переподключается. Нельзя ожидать изменения snapshot st.context в старом соединении.
Изменяющие браузерные маршруты защищаются от CSRF с проверкой origin и токена формы;
GET не очищает диалог. Прямой доступ к основным API-маршрутам и inference закрыт.

Доступ к приложению для группы и доступ к конкретной сессии — разные проверки.
Используется существующая приватная сеть. Ingress предоставляет единый HTTPS-вход;
проверка токена сессии на API сохраняется. Закрытая ссылка сама по себе не ограничивает доступ.
Регистрация PhotoAgent и долговременный профиль в MVP-1 не вводятся.

Утверждён один активный диалог на браузерный профиль для одного хоста приложения.
Несколько вкладок и окон этого профиля видят одну сессию; очистка действует для всех.
При действующей cookie повторное создание возвращает существующую сессию, не создаёт
вторую. «Новый диалог» сначала завершает текущую сессию. Первичное открытие двух
вкладок одновременно требует согласования создания на стороне браузерного входа;
при реализации проверить, что обе вкладки в итоге подключены к одной сессии,
а лишнее незавершённое создание не оставляет доступного второго диалога.
После отзыва токена другая вкладка очищает свою копию на следующей проверке API.
Раздельные диалоги вкладок и продолжение с другого устройства не обещаются.
Потерянный токен не восстанавливается по одному session_id.

Граница анонимной идентичности — браузерный профиль с сохранённой cookie.
Другой профиль, приватное окно с отдельным хранилищем или удаление cookie не позволяют
надёжно установить прежнюю личность. Ограничение не реализуется по IP-адресу:
это могло бы объединить разных участников приватной сети. Восстановление личности
между такими окружениями относится к будущей регистрации.

## Переписка, обратная связь и агрегаты

«Текст жалобы» означает отдельный свободный комментарий пользователя к ответу,
например «ссылка не открывается» или «в ответе неверная дата». Это не название
всего диалога и не копия истории. Обратная связь предусмотрена purpose.md.

До завершения сессии в её RAM хранятся запросы пользователя, ответы агента,
уточняющие вопросы и ответы на них, контекст/резюме, Evidence, оценки и текст
обратной связи с привязкой к ответу. При очистке, истечении TTL или перезапуске API
эти данные удаляются; отдельный архив обращений и жалоб не создаётся.
Закрытие вкладки само по себе сессию не завершает: действует согласованный TTL.
Не записывать эту переписку в логи и постоянные диагностические выгрузки.
Политика внешних MCP/LLM рассматривается отдельно при выборе провайдеров:
удаление в PhotoAgent не означает удаления уже переданных им данных.

«Обезличенные агрегаты» означают согласованную общую статистику, а не сообщения
с удалённым именем и не строки событий с захешированным session_id. Примеры:

- за день обработано 40 запросов, 3 завершились ошибкой;
- получено 12 положительных и 2 отрицательные оценки;
- распределение времени ответа по диапазонам и суммарное число токенов.

Числа выше иллюстративные, не результаты измерений. Не сохраняются тексты,
цитаты, URL из диалога, cookie, IP, session_id, request_id, execution_id, answer_id
или точные времена действий отдельных участников. Для расчёта задержек можно
накапливать счётчики по диапазонам без сохранения исходных строк запросов.
После удаления диалога такую статистику нельзя использовать для его восстановления
или расследования конкретной жалобы.

Сбор и сохранение агрегатов включены в MVP-1. Срок хранения **30 дней утверждён**.
Устаревшие агрегаты удаляются автоматически; их чтение и обновление отчёта срок
не продлевают. Это отдельный жизненный цикл, не TTL переписки.
Выбран формат дневных JSON-файлов на постоянном локальном томе. Протокол надёжности
ниже описан как проект реализации; RAM диалогов этим не заменяется.

### Пользовательский экспорт

По утверждённой [UI-концепции](../ui/concept.md#сохранение-в-файлы) пользователь
скачивает диалог в `.md` и отдельно все источники; для источников выбран Markdown.
Оба файла — UTF-8, снимок доступных данных текущего диалога на момент действия.
Диалог включает реплики по порядку, имена ассистентов, ответы со ссылками,
оговорками и неопределённостями, общий список источников с контекстными комментариями.
Файл источников включает карточки без повторных точных URL в порядке появления,
названия, адреса, контекстные комментарии, доступные сведения об авторах и текстовую
привязку к номеру первичного ответа. Он не обещает переход в завершённую веб-сессию.

Скачивание не создаёт постоянную историю на сервере. Файл у пользователя остаётся
после очистки, TTL или рестарта API; правила удаления серверной переписки не удаляют
уже скачанную копию. Во время обработки доступен экспорт имеющейся переписки с
пометкой о незавершённом ответе, без частичного текста генерации. При отсутствии
реплик или источников соответствующее действие недоступно с пояснением.

Экспорт не запускает поиск/генерацию повторно и не содержит токенов доступа,
служебных данных или внутренних рассуждений. Ошибка скачивания не удаляет диалог;
предусмотрен повтор. Механизм согласованного снимка и поведение гонки с очисткой,
завершением ответа или истечением сессии прорабатывают backend и frontend;
изоляция пользователей сохраняется. Экспорт не является подтверждением показа
нового ответа или пользовательской оценкой.

## JSON-файлы с дневными агрегатами

**Выбор хранилища утверждён 2026-09-22.** Предлагаемый протокол реализации:

1. Каталог статистики на постоянном локальном томе подключён только core-api.
   Один файл `YYYY-MM-DD.json` на день UTC содержит schema_version, дату,
   revision снимка, агрегаты по конфигурации генератора, технические счётчики,
   распределения задержек и признак полноты. Не хранить события по одному,
   тексты, URL диалогов, session_id/request_id/answer_id или их хеши.
2. Технические события относятся к дню их возникновения; итоговые отзывы — к дню
   завершения сессии и модели соответствующего ответа. Пока сессия жива, её оценки
   доступны как предварительные только в RAM. Это исключает перезапись старых
   дневных итогов при изменении оценки и бесконечное продление их срока хранения.
3. Единственный писатель в выделенном потоке последовательно обрабатывает изменения
   и снимки; файловый ввод-вывод не блокирует event loop. Сохраняется полный снимок
   дня, а не повторно прибавляемая дельта. Повтор записи одной revision идемпотентен;
   более старый снимок не может перезаписать новый. Параллельные процессы-писатели
   к одному каталогу не поддерживаются.
4. Новый снимок записывается во временный файл в том же каталоге, выполняются flush
   и fsync файла, затем атомарная замена целевого файла и синхронизация каталога
   на целевой Unix-файловой системе. Не перезаписывать действующий JSON на месте.
   Основа: [Python os.replace и os.fsync](https://docs.python.org/3/library/os.html).
   Атомарная замена не является сама по себе гарантией сохранности при отказе диска.
5. При запуске читать и валидировать существующие снимки, продолжать с сохранённых
   абсолютных значений. Незавершённые временные файлы не считать зафиксированной
   статистикой. Повреждённый или неизвестный формат не заменять молча нулевым:
   помечать период недоступным/неполным, регистрировать техническую ошибку без данных
   диалога и требовать разбирательства с файлом.
6. Предлагаемая детализация срока: текущая дата UTC плюс 29 предыдущих календарных
   дней. Старые периоды исключаются из выдачи сразу; очистка при запуске и смене
   суток удаляет старые снимки и соответствующие временные файлы. Перезапуск и
   чтение отчёта не сдвигают срок. Конкретное правило границы 30 дней проверить
   тестом с подменой часов.

Предлагается сбрасывать технические счётчики каждые 10 секунд, при завершении
сессии и при штатной остановке. При закрытии сессии сначала отозвать доступ,
однократно извлечь только агрегированный вклад под блокировкой, затем удалить
переписку и передать вклад писателю. Ошибка записи не должна удерживать удаляемую
переписку: повторяется сохранение только агрегированного снимка из RAM.
Смена оценки до закрытия влияет на итоговое значение ровно один раз.

После перезапуска сохраняются только успешно зафиксированные снимки. RAM диалогов,
нефинализированные отзывы и ещё не записанные счётчики могут быть потеряны;
их нельзя восстанавливать вымышленными no_feedback. На следующем запуске отметить
статистику текущего дня как потенциально неполную; для выявления затронутых ранее
дней можно хранить служебный JSON-маркер незавершённого запуска с диапазоном дат,
без идентификаторов пользователей/запросов. Его также записывает единственный
писатель; подробный формат определить вместе с форматом снимка.

Гарантия «ни одно событие не теряется при аварии» выбором JSON **не утверждена**.
Допустимые потери незафиксированных агрегатов и точность отметки неполноты остаются
вопросом завершения A-06. Устойчивость проверяется на фактическом томе развёртывания;
изменения кода и установка компонентов этим документом не выполняются.

## Доступ к статистике

Решение владельца от 2026-09-23: только владелец проекта получает защищённую
выгрузку JSON, без отдельного экрана статистики. Выгрузка содержит агрегаты,
не тексты диалогов, комментарии, токены или идентификаторы сессий.
Право владельца проверяется отдельно от доступа к анонимной сессии;
конкретная авторизация и ошибки выгрузки определяются в B-01.
Grafana и аналогичные средства мониторинга относятся к следующим этапам;
см. [план развития](../architect-todo.md#мониторинг-после-mvp-1).

## Учёт оценок и отсутствия отклика

У показанного содержательного Answer пользователь может поставить положительную
или отрицательную оценку. При отрицательной оценке необязательный комментарий
отправляется явным действием. Пустой комментарий допустим. Текст не копируется
в агрегаты, технические логи или отдельный архив.

Для каждого доступного для оценки ответа в RAM сессии хранится ровно одно текущее
состояние: `positive`, `negative` или `no_feedback`. При повторе отправки оценки
состояние не дублируется; смена оценки заменяет прежнее значение. При смене
отрицательной оценки на положительную комментарий удаляется. Ответ принадлежит
только авторизованной сессии, оценка чужого answer_id запрещена.

Сразу после показа ответа отсутствие оценки предварительное: пользователь ещё
может её оставить. При завершении сессии оно становится итоговым `no_feedback`,
которое по правилу пилота считается **условно положительным**. Для промежуточного
отчёта число ещё не оценённых ответов показывается отдельно как ожидающее отклика.
В статистике никогда не подменять no_feedback значением positive.

Пусть P — число явно положительных оценок, N — отрицательных, U — итоговых ответов
без отклика. Хранятся отдельные счётчики P, N, U; условно положительная доля пилота
равна `(P + U) / (P + N + U)`. Доля положительных среди оставивших оценку равна
`P / (P + N)`, доля ответов с откликом — `(P + N) / (P + N + U)`.
При нулевом знаменателе показывать «нет данных», не 0% или 100%.

Учитываются показанные ответы kind=answer и insufficient_evidence. Уточняющие
вопросы, приглашения kind=invitation, служебные уведомления, отказ по границам и технические ошибки не входят
в знаменатель откликов. Показ подтверждается UI после отображения, а не выводится
из одного лишь факта завершения генерации. Маркер показа не продлевает TTL.
Тексты/ID и отметки показа существуют только в RAM живой сессии; в сохраняемую
статистику переходят суммы. Refresh не создаёт повторный показ для счётчика ответов.

Технические ошибки учитываются отдельно по безопасному коду и этапу обработки
(например, timeout поиска или ошибка генерации), без текста исключения и исходного
запроса. Один запрос может завершиться ограниченным ответом и иметь ошибку одного
инструмента: счётчики ошибок и откликов тогда описывают разные аспекты результата.

Для последовательного сравнения моделей допустима группировка агрегатов по
заданной конфигурации генератора (провайдер/модель/версия настройки) и дню.
Это общие метки развёртывания, не идентификаторы пользователей или запросов.
Запросы, URL, токены и свободные комментарии не используются как метки статистики.

При очистке/TTL агрегирование выполняется до удаления рабочих записей; повторная
очистка не добавляет второй вклад. При аварийном перезапуске API незавершённые
сессионные данные теряются: нельзя выдумывать итоговые отзывы для них. Правила
сохранения промежуточных счётчиков и отметки полноты предложены в разделе
JSON-хранилища. Архив истории ради восстановления метрик не вводится.

## Время жизни и определение бездействия

`idle_timeout_seconds = 43200` — утверждено.
`expires_at = last_activity_at + 12 часов` — согласованная серверная модель.

Считаются активностью: принятая реплика, ответ на уточнение, изменение уровня или
подробности объяснения, оценка ответа и явное открытие/обновление страницы.
На новом UI-подключении выполняется восстановление; активность регистрируется
отдельно при явном открытии/обновлении страницы пользователем. Повторные проходы
скрипта от опроса статуса не регистрируют её заново. Различение открытия страницы
и автоматического переподключения должно быть проверено при интеграции UI.
Набор событий согласован пользователем. Чтение без действий неотличимо
от оставленной вкладки и срок не продлевает. Автоматическое переподключение
WebSocket после сетевого сбоя не является явным возвращением пользователя;
сам факт нового UI-подключения не должен безусловно продлевать TTL.

Не считаются активностью: heartbeat, опрос статусов, повтор доставки того же
request_id, ретраи провайдера и завершение генерации. Автоматический heartbeat
для продления сессии исключён. Опрос статусов сохраняется для показа хода обработки
и готового ответа, но не обновляет last_activity_at или expires_at.
Отдельного абсолютного предела длительности активного разговора нет.
Явное скачивание диалога или источников и повтор скачивания не продлевают срок
сессии: last_activity_at и expires_at не изменяются. Это подтверждено владельцем
2026-09-22; формирование снимка и файла также не считается активностью.

На каждом обращении backend сначала проверяет срок. При `now >= expires_at`
сессия уже недоступна и не может быть продлена новым запросом. Периодическая очистка
освобождает RAM; предлагаемый интервал 10 секунд. Активные задания ограничены своим
deadline; даже если ошибочно затянулись, они не обходят истечение сессии.
Завершившийся после очистки/TTL результат отбрасывается по версии сессии.

Сигнал `pagehide`/`sendBeacon` из прототипа больше не удаляет сессию: уход со страницы
может быть обновлением. Закрытие вкладки оставляет данные до TTL или явной очистки.
Это сознательное техническое следствие восстановления страницы. Мгновенное удаление
при закрытии не требуется и не обещается. Явная кнопка очистки удаляет сразу на сервере.

## Контракт восстановления и защита от повторов

Сессия представляет анонимного пользователя MVP-1 и владеет запросами.
Ключ запроса — (session_id, request_id); request_id создаёт клиент до отправки,
backend назначает execution_id и связывает его с авторизованной сессией.
session_id не заменяет токен доступа. Согласованные правила:
[контракты A-05](contracts.md#общие-правила).

Предлагаемый `SessionSnapshot` содержит session_id, revision, last_activity_at,
expires_at, настройки объяснения и выбранную locale (ru в MVP-1), состояние диалога, pending_clarification,
ordered messages с message_id/role/created_at, а также active_execution_id.
Ответы сообщений включают Answer и карточки источников; сырой внутренний контекст
локальной модели в браузер не передаётся. Метаданные Evidence остаются доступны API
для продолжения разговора, даже если UI их не отображает целиком.

При дополнении контракта для утверждённого UI snapshot должен позволять восстановить
текущую роль ассистента и неизменное авторство каждого прежнего ответа. Роль
ассистента не является ролью пользователя: пользователь остаётся анонимным.
Отсутствие подписи предусмотрено только у начального «О чём поговорим сегодня?».
Приглашение без вопроса уже определено как invitation в contracts.md 1.1;
locale=ru и её восстановление также описаны в контракте. Конкретные поля роли
и остальные дополнения A-13 остаются открытыми
в [замечаниях специалистам](discussion.md).

Источники правой панели восстанавливаются из всего текущего диалога в порядке
первого появления. Одна карточка на точный URL сохраняет контекстный комментарий
и привязку к первичному ответу. Повторное использование не меняет эту привязку;
фрагменты и идентификаторы источников последующих ответов остаются в контексте
своих ответов. Разные URL автоматически не объединяются. Способ получения
комментария и передачи первичной привязки ещё требует уточнения контракта.
Смена роли не очищает диалог или панель; очистка, TTL и рестарт API удаляют
эти временные данные вместе с сессией. UI не подменяет их общим межсессионным кешем.

После refresh UI сначала запрашивает snapshot, затем опрашивает уже существующее
выполнение по active_execution_id. Новая генерация при восстановлении не запускается.
Если POST был принят, а ответ потерян при обновлении, выполнение всё равно находится
в snapshot. Если POST не дошёл, в истории нет принятой реплики; несохранённый черновик
в поле ввода не входит в гарантию восстановления. request_id предотвращает дубли
принятой отправки в пределах живой сессии.

Разделить SessionRepository, проверку доступа и оркестрацию. Сессия представляет
анонимного пользователя; аккаунты и постоянно сохраняемые на сервере диалоги
сейчас не вводятся. Пользовательский экспорт описан выше.
План перехода к регистрации вынесен в [architect-todo.md](../architect-todo.md).

## Проверки при реализации

1. Refresh после ответа восстанавливает историю, источники, настройки, текущую роль
   и авторство прежних ответов, первичную привязку и контекст карточек.
2. Refresh во время поиска/генерации продолжает опрос одного execution_id.
3. Refresh во время уточнения восстанавливает исходный вопрос и ожидание ответа.
4. В 11:59:59 бездействия сессия доступна; ровно через 12 часов — нет.
   Проверять подменой часов, без реального двенадцатичасового ожидания.
5. Автоматические heartbeat/опросы не мешают истечению открытой вкладки.
   Автоматическое переподключение после сетевого сбоя также не продлевает TTL.
6. Принятое пользовательское действие до истечения начинает новые 12 часов.
7. Очистка отзывает доступ во всех вкладках; поздний ответ не возвращает данные.
8. Другой браузерный профиль/неверный токен не получают чужую историю.
9. Перезапуск UI восстанавливает сессию; перезапуск API показывает её потерю,
   согласно согласованному хранению только в RAM.
10. Три одновременных запроса из разных сессий не блокируют чтение/очистку;
    измеряются задержка, очередь и память. Это критерии будущей проверки, не результаты.
11. Две вкладки одного профиля (включая одновременное первое открытие) используют
    один диалог; повторное создание не позволяет вести два параллельно.
12. После завершения сессии на сервере нет сохраняемой переписки, резюме или текста жалобы;
    в согласованных агрегатах нет идентификаторов и содержания диалога.
13. Смена оценки не увеличивает число оценённых ответов; refresh не дублирует ответ;
    отсутствие отклика хранится отдельно от положительной оценки.
14. Ответ, не показанный UI, и ошибка генерации не становятся условно положительными;
    итоговая агрегация сессии не выполняется дважды.
15. Агрегаты удаляются после 30 дней хранения; чтение статистики срок не продлевает.
    Удаление сессии не удаляет допустимую общую статистику и не сохраняет её переписку.
16. Сбой записи сохраняет предыдущий валидный JSON; повтор снимка не удваивает
    счётчики; штатный перезапуск читает сохранённые значения; повреждение не маскируется нулями.
17. Повторный точный URL не создаёт карточку и не меняет первичный ответ или комментарий;
    разные URL с параметрами не объединяются. Смена темы сохраняет весь список,
    уточнение без источников не создаёт фиктивную карточку; фрагменты разных ответов не смешиваются.
18. Экспорт сохраняет порядок реплик/источников, имена, оговорки и контекст без дублей
    и служебных токенов. Файл источников содержит весь список, а не только видимые карточки.
    Новая генерация, очистка и истечение сессии не дают смешанного или чужого снимка;
    конкретное поведение гонок проверяется по согласованному механизму экспорта.
19. Экспорт незавершённого разговора обозначает ожидающий ответ, не выдавая черновик
    генерации за готовый. Скачанная копия остаётся после удаления серверной сессии;
    ошибка экспорта допускает повтор без потери диалога и повторной генерации.
20. Скачивание обоих видов файлов и повтор после ошибки не изменяют last_activity_at
    или expires_at. Экспорт перед истечением не переносит границу TTL; проверять
    с управляемыми часами, отдельно от продлевающих срок действий пользователя.
