## Предварительная рекомендация для следующих проб

Первым проверить Groq; backend предлагает openai/gpt-oss-20b как технического
кандидата с поддержкой строгой схемы. Это не утверждение качества или окончательный
выбор в A-09. OpenAI/Gemini из первоначального обзора остаются справочными
альтернативами, их исследование сейчас не задерживает Groq.
Для поиска сравнить Tavily и Exa; wiki остаётся отдельным явным инструментом.

### Совместимость Groq и условия пробы

- Base URL: https://api.groq.com/openai/v1; маршрут POST /chat/completions.
  Groq заявляет совместимость с OpenAI-клиентами с исключениями: например,
  messages[].name/logprobs/logit_bias не поддерживаются, n должен быть 1.
  [Официальная совместимость](https://console.groq.com/docs/openai).
- Для openai/gpt-oss-20b документирован strict JSON Schema; поддержка зависит от
  модели. Streaming и tools в этом режиме пока не поддерживаются.
  [Structured Outputs](https://console.groq.com/docs/structured-outputs).
- В пробе — компактная схема черновика, stream=false, без tools/облачного поиска,
  reasoning_effort=low, ограниченный max_completion_tokens. Low не означает
  отсутствие reasoning-расхода: сверить фактический usage и неполный вывод.
  [API Reference](https://console.groq.com/docs/api-reference).
- [Карточка GPT-OSS 20B](https://console.groq.com/docs/model/openai/gpt-oss-20b)
  указывает $0.075 за 1 млн входных и $0.30 за 1 млн выходных токенов; цена и
  наличие модели в аккаунте проверяются перед реальной пробой.
- По [правилам данных Groq](https://console.groq.com/docs/your-data) вход/выход
  обычного inference по умолчанию не сохраняются, но возможны журналы диагностики
  и расследования злоупотреблений до 30 дней; usage-метаданные сохраняются.
  Настройки Data Controls конкретного аккаунта ещё не проверены.

### Локальный mock для тестов

По решению владельца подготовка контейнера LiteLLM передаётся DevOps как
[D-05](test-environment-task.md). Это инструмент тестового стенда, не обязательная
production-зависимость и не новый слой маршрутизации провайдеров. Документация
подтверждает mock_response в completion(), включая streaming, без вызова LLM.
Это заданный ответ; автоматическое отражение последнего сообщения как эхо
в HTTP-сервере необходимо настроить и проверить отдельно. В примере usage
содержит null: для проверки бюджетов нужны явно заданные числовые значения.
[LiteLLM mock responses](https://docs.litellm.ai/docs/completion/mock_requests).

Сценарии backend/QA для стенда D-05, B-07 и последующих B-09/B-14:

1. Изолированный локальный OpenAI-совместимый /v1/chat/completions без upstream
   и рабочих ключей. Клиент направляется на mock через base_url. Во время тестов
   исходящие вызовы провайдеров запрещены; случайный fallback недопустим.
2. Режим echo возвращает последний user.content; режим fixture — заданный валидный
   черновик JSON. Echo не обязан проходить схему Answer, fixture должен её учитывать.
3. Сценарии: 200 с детерминированным usage, 429 с Retry-After, 5xx, задержка/timeout,
   повреждённый JSON, finish_reason=length, отсутствующий или некорректный usage.
4. Проверить транспорт через выбранный клиент, отсутствие скрытых ретраев и
   возможность их отключения. Для B-14 — локальный отказ до сетевого вызова,
   конкурентные сессии и отсутствие сброса лимита при смене base_url/model.
5. Зафиксировать версию LiteLLM, способ запуска и успешные сценарии. Успех mock
   подтверждает обработку протокола и ошибок, не поведение/качество модели Groq.

Обновление DevOps: контейнер LiteLLM 1.102.1 и кандидат локального mock запущены,
HTTP-проверки и изоляция выполнены: [протокол D-05](deployment-checks.md).
SDK установлен внутри образа, локальное окружение backend не менялось.

## Проверка вместимости в лимит

Локальное измерение сериализованной схемы Answer из shared/mvp_contracts:
`json.dumps(Answer.model_json_schema(), ensure_ascii=False, separators=(",", ":"))`.
Получено 7218 символов, ceil(7218/3)=2406 оценочных токенов. Синтетический пример
готового Answer из contract-examples.json занимает 1053 символа, 351 оценочный токен.
Это измерение локального артефакта, не подсчёт tokenizer/usage облачной модели.

Вывод backend: передавать полную публичную схему при лимите 1500 вход+выход нельзя.
Генератор должен предлагать компактный черновик содержательных полей, backend
добавляет доверенные ID, точные URL и метаданные из Evidence. Это соответствует
уже принятому разделению ответственности contracts.md. B-07 проверяет вместимость
инструкций, Evidence, схемы черновика и ответа; B-09 реализует сборку публичного Answer.
Повышение лимита не принято и для продолжения документального исследования не нужно.

## Протокол дальнейших проверок

1. Подготовить локальный mock; для реальной пробы Groq обеспечить GROQ_API_KEY
   через окружение процесса, проверить доступ к модели. Выбор провайдера закрыт;
   параметры внутренних квот уже определены, не запрашивать их у Groq.
2. Зафиксировать API/model version, способ авторизации без секретов в отчёте,
   лимиты и правила данных/атрибуции. Для MCP прочитать реальные initialize/tools/list;
   использовать только поисковые и читающие инструменты, а не облачное планирование.
3. На синтетических/публичных запросах проверить поиск «история пикториализма»
   и англоязычный вариант, извлечение одного результата, пустой поиск и недоступный
   документ. Сохранить безопасный протокол: параметры без ключа, статусы, времена,
   метаданные, объёмы и ограничения использования; не записывать живые диалоги.
4. Генератору дать минимальный синтетический Evidence и запрос русского ответа.
   Измерить фактические вход/выход, неполный вывод, качество ссылочных ID и выполнение
   компактной схемы. Не отправлять полный публичный Answer schema, session ID и токены доступа.
5. Timeout, 429, некорректный JSON, слишком большой ответ и недоверенные инструкции
   проверять также на подменах; не провоцировать отказ сервиса нагрузкой.
6. Для каждого результата указать метод: документация / реальный вызов / подмена /
   не проверено. Итог B-07 — сравнение, ограничения, рекомендация и результаты проб;
   утверждение конфигурации — A-09, предметная экспертная приёмка — T-02/A-10.

## Результаты backend от 2026-09-24

Владелец подтвердил: доступа Groq пока нет. Ключи не читались, облачных LLM-вызовов
не было. Выбор провайдера закрыт; для следующей реальной пробы нужен доступ,
после него проверяются русский ответ, точный usage и совместимость модели.

- **D-05:** повторно прошли 6 HTTP-тестов `scripts/check_mock.py`. Обвязка LiteLLM
  принята backend как инструмент синтетических протокольных проверок; это не
  утверждение production-зависимости и не независимая приёмка QA.
- **Черновик:** `scripts/llm_probe.py` определяет Draft и Claim с текстом и
  evidence_ids. Фикстура DevOps подходит без изменений; ID трактуются как ссылки
  на внутренние фрагменты Evidence. Backend добавляет доверенные идентификаторы
  и метаданные публичного Answer. Полнота/ограничения/спорные версии в этой первой
  фикстуре не покрыты: её недостаточно для завершения B-09.
- **Размер:** компактная JSON Schema — 758 символов. Синтетический Groq-запрос
  целиком оценивается в 434 токена, резерв выхода 400, итого 834 по правилу 3:1.
  Это оценка, не точный usage. Резерв включает возможные reasoning-токены.
  `groq_payload()` готовит strict JSON Schema, но модель ещё не проверена.
- **Клиентская проверка:** 2 теста `scripts/check_llm_probe.py` прошли на живом mock:
  валидная фикстура и числовой usage принимаются; 429/503, повреждённый JSON,
  усечение, отсутствующий/некорректный usage отклоняются. Количество обращений
  соответствует числу проб, автоматического retry нет. Использован httpx из
  существующего dev-окружения, новых зависимостей нет.
- **Граница совместимости mock:** текущая обвязка принимает `max_tokens`, но не
  современный набор `max_completion_tokens`/`response_format`/`reasoning_effort`.
  Поэтому тесты выше проверяют ответ и ошибки, не доставку полного Groq-запроса.
  Следующее расширение D-05 — приём этих параметров и отдельные фикстуры для
  structured output; игнорирование параметра mock не подтверждает поведение Groq.
- **MediaWiki:** один реальный публичный запрос search + plaintext extract к
  en.wikipedia.org прошёл. Запрос `photography depth of field` вернул
  [Depth of field](https://en.wikipedia.org/wiki/Depth_of_field), URL и 203 символа
  текста. Это excerpt, не full_text. Содержимое целиком в отчёт не сохранялось.
  Проверка ru, пустого результата, ошибок, revision/permalink и правил атрибуции
  остаётся открытой; одна проба не означает готового gateway.
