## T-03: конкретный пакет прогонов

Исходные материалы: [B-01/B-15](b15-checks.md), [HTTP-кандидат](http-contract-draft.md),
[экспериментальный API](session-probe-backend.md), [frontend](frontend-progress.md).
Текущий результат разработчика: 69 unit-тестов и 6 Chrome-сценариев с подменами,
Ruff прошёл; живой HTTPS после поправки не проверен. Это исходное свидетельство,
которое QA воспроизводит независимо, а не готовый акт приёмки.
Перед прогоном записать HEAD и перечень/идентификатор diff, если он есть.
В другом checkout убедиться, что присутствуют shared/session_actions.py и регрессии
B-15 из этого пакета. Не тестировать старый коммит как реализацию B-15.

Из корня проекта, без ключей и облачных запросов:

```bash
PYTHONPATH=.:core-api:streamlit-ui .venv/runtime-env/bin/python -m unittest \
  discover -s tests -p '*_test.py'
.venv/runtime-env/bin/python tests/session_probe_browser_check.py
.venv/runtime-env/bin/ruff check .
.venv/runtime-env/bin/ruff format --check .
```

Прочитать и дополнить проверки независимыми ожиданиями:

- SessionActionRequest обязателен для clear/opened; пустое/некорректное тело → 422.
  F-01 возвращает `{detail: code}`, кандидат MVP — ApiError 1.1.
- S1 показана в A, в B уже создана S2: clear/opened с ожидаемой S1 и свежим CSRF
  → 409 session_changed. Сохранены S2, cookie, marker, revision и TTL; Set-Cookie нет.
- Потерян ответ успешного clear S1, появилась S2: retry сохраняет оба исходных ID
  и не удаляет S2. Новая очистка требует нового подтверждения по показанной S2.
- Старый CSRF → 403; отсутствующая cookie при живой ожидаемой сессии → 401;
  на границе TTL opened → 401, clear при пустом контексте → 204. Poll/retry не активность.
- F-02: потерянное принятие восстанавливается по request_id; сеть сохраняет ввод,
  401 очищает копию; неизвестная версия/чужой ответ отвергаются; нет скрытой генерации.
  Проверка кандидата не доказывает наличие рабочего `/mvp1` API.

Для живой части после восстановления сети запустить API/UI по инструкции B-02,
использовать отдельный браузерный профиль и выполнить:

```bash
.venv/runtime-env/bin/python scripts/check_session_probe.py
```

Ожидаются пять сценариев через Chrome → HTTPS ingress → Streamlit/API. Новые два
сценария гонки/потерянного clear ещё не исполнялись на доступном HTTPS; QA должен
проверить также корректность самого сценария и при необходимости дополнить его.
Повторить критичные шаги в настоящем Safari с записью версии и результата.
Старое подтверждение владельца не подтверждает новый код B-15 в Safari.

Владелец отложил HTTPS до возврата в прежнюю сеть: сейчас Mac 192.168.0.101,
DNS/ingress 192.168.7.100. Не менять сеть, DNS, TLS или общий стенд ради обхода.
Недоступность отмечать blocked/environment, не fail продукта и не pass.
Остальные аварийные сценарии B-02 (первая cookie, приватный режим, BFCache)
учитывать отдельно: успешный B-15 не закрывает весь A-07.

## T-02 и T-07: границы ранней проверки

T-02 не ждёт завершения A-13 целиком. Использовать согласованные contracts.md,
purpose.md и [постановку анализатора](query-routing.md); примеры архитектора —
подсказка покрытия, а не независимый эталон. Для каждого случая хранить стабильный ID,
вход, контекст, ожидаемые поля, обоснование, статус согласования и версию корпуса.
Не назначать самостоятельно пороги качества/объём выборки; спорные роли — pending.

F-07 запускается отдельно по frontend-progress.md на свободном порту 8504.
Проверить desktop/узкий viewport, одну открытую панель, клавиатуру/Escape/возврат
фокуса, inert, сохранение черновика/позиции, ввод 4–7 строк и отсутствие отправки
при переключении панели. Фиксировать браузер, viewport, масштаб и DPR.
Настоящие Android/экранная клавиатура и масштаб текста проверяются отдельно;
эмуляция не заменяет устройство. Недостающие устройства/методику согласовать
с владельцем через конкретный вопрос, окончательные визуальные параметры — с U.
Рендеринг Answer/экспорта и финальная интеграция будут следующими этапами T-07.
