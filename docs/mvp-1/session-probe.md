# F-01: исследовательский UI браузерной сессии

Дата: 2026-09-24. Исполнитель: frontend. Backend-кандидат реализован отдельно;
[заключение, запуск и результаты B-02](session-probe-backend.md).
Работа session_probe в Safari подтверждена владельцем 2026-09-24.
Полная сценарная приёмка и решение A-07 остаются открытыми.
Документ самодостаточен: локальные `decisions.md` и `tasks.md` не нужны для запуска.

## Назначение и границы

Отдельная точка входа `streamlit-ui/session_probe.py` проверяет передачу
HttpOnly-cookie в Streamlit и затем в API, refresh, автоматический reconnect,
несколько вкладок и очистку. Полноценный чат, генерация, роли и источники не нужны.
Используются только синтетическая отметка и диагностические поля сессии.
Существующий чат и его старый close/heartbeat-протокол не используются стендом.

Требования: [жизненный цикл](session-lifecycle.md),
[архитектура](architect.md), [инфраструктура D-01](deployment-checks.md).
Проверки фронтенда с подменённым API не закрывают F-01/B-02.

Сверены [contracts.md](contracts.md),
[contract-examples.json](contract-examples.json) и
[integration-research.md](integration-research.md). Предметные контракты 1.1
и их примеры используются без изменений: QueryAnalysis, SearchPlan, Evidence,
Answer, ExecutionAccepted/ExecutionResult, ApiError. В них пока нет готовых
маршрутов выдачи cookie/CSRF и SessionSnapshot; это прямо отмечено в contracts.md
и [описании моделей backend](../../shared/mvp_contracts/README.md).
Исследование B-07 касается внешних MCP/wiki/LLM и mock LiteLLM, который не
заменяет API браузерной сессии. Недостающая часть ниже относится только к F-01.

## Предложение экспериментального контракта

Это изолированное пространство `/f01/`, не окончательный HTTP API MVP-1.
Backend подтверждает/корректирует контракт и реализует тестовые маршруты.
Frontend адаптирует клиент по результатам согласования; DevOps публикует только
браузерную часть. По умолчанию cookie называется `__Host-photoagent-f01`:
HttpOnly, Secure, SameSite=Lax, Path=/, без Domain, Expires и Max-Age.
Она не должна использовать хранилище или cookie старого чата.

| Доступ | Метод и путь | Тело / результат |
|---|---|---|
| Браузер | GET `/f01/browser/context` | JSON `{session_id: UUID|null, csrf_token: string}`. Чтение не продлевает TTL и не создаёт диалог. Допустима выдача отдельной pre-session CSRF-cookie; токен сессии в JSON не возвращается |
| Браузер | POST `/f01/browser/create` | JSON `{request_id: UUID}` → 204, Set-Cookie. С действующей cookie вернуть существующую сессию; повтор не создавать второй диалог |
| Браузер | POST `/f01/browser/opened` | JSON `{request_id: UUID}` → 204. Однократно зарегистрировать явное открытие/refresh; повтор того же ID не продлевает TTL |
| Браузер | POST `/f01/browser/marker` | JSON `{marker: string}`, до 100 символов → 204. Сохранить синтетическую отметку, увеличить revision; это явное действие продлевает TTL |
| Браузер | POST `/f01/browser/clear` | JSON `{}` → 204. Отозвать доступ, удалить временные данные и сбросить cookie; повтор очистки безопасен |
| Только сервер UI | GET `/f01/internal/snapshot` | `Authorization: Bearer <cookie value>` → JSON снимка ниже; без продления TTL |

Все изменяющие браузерные запросы требуют точного допустимого `Origin` и
`X-F01-CSRF`, проверяемого backend с привязкой к браузерному контексту.
Backend должен определить защиту первоначальной выдачи CSRF, срок и ротацию
токена. Сам факт наличия заголовка не является достаточной защитой.
Отсутствующий/чужой Origin либо неверный CSRF → 403 без изменения состояния.
Просроченный/отозванный доступ → 401 или 410; недоступный маршрут/ошибка сервера
не означает потерю сессии. Ответы не содержат сырых исключений/токенов.
Все ответы браузерного API — `Cache-Control: no-store`; редиректы не используются.

Снимок содержит ровно следующие поля:

```json
{
  "session_id": "00000000-0000-4000-8000-000000000001",
  "revision": 1,
  "last_activity_at": "2026-09-23T10:00:00Z",
  "expires_at": "2026-09-23T22:00:00Z",
  "marker": "Проверка F-01"
}
```

ID позволяет сравнить вкладки, но не предоставляет доступа. Время — UTC;
TTL — 43200 секунд, проверяется API до каждого действия. Backend хранит только
хеш токена, а сессии и служебные ключи идемпотентности — в RAM.
Рестарт API теряет сессии. Постоянной истории и внешних вызовов нет.

Открытые пункты согласования: backend-ошибки и CSRF bootstrap, доверенные
proxy-заголовки, судьба незавершённого создания при потере ответа/закрытии вкладки,
ограничение RAM и очистка экспериментальных сессий. До ответа backend этот
документ не объявляет протокол безопасным или утверждённым.

## Поведение клиента

- Серверный UI только читает snapshot; мутации выполняет браузер через same-origin
  fetch с cookie и CSRF. Токен сессии не передаётся компоненту JavaScript.
- Web Locks сериализует браузерные операции между вкладками origin; context
  читается внутри блокировки. Без HTTPS/Web Locks операции остановлены с сообщением.
  Это кандидат механизма координации, его гарантия при аварийном закрытии ещё
  требует проверки совместно с backend.
- ID документа и факт регистрации открытия живут в памяти окна, переживают
  перерисовку компонента и reconnect, но меняются при явном refresh.
  Повтор после сетевой ошибки использует прежний ID открытия.
- После Set-Cookie выполняется reload для нового подключения Streamlit.
  Одноразовая отметка в sessionStorage отличает этот служебный reload от явного;
  в ней нет токена, истории или ID сессии. Новая сессия создаётся явной кнопкой.
- Polling snapshot не делает heartbeat и не регистрирует активность.
  При 401/410 копия снимка удаляется; при сетевой ошибке остаётся с предупреждением.
  Очистка требует подтверждения. Закрытие вкладки не отправляет close-сигнал.

Основание выбора API Streamlit:
[st.context](https://docs.streamlit.io/develop/api-reference/caching-and-state/st.context)
предоставляет cookie первоначального подключения только для чтения;
[компоненты v2](https://docs.streamlit.io/develop/concepts/custom-components/components-v2/communicate)
позволяют выполнять браузерные действия отдельно от серверного HTTP-клиента.
Фактическое прохождение HttpOnly-cookie через ingress требует сквозного опыта.

## Запуск и остановка

Действующие Dev/Stage не перезапускаются. Для просмотра оболочки без маршрутов
backend (покажет отсутствие cookie/неподтверждённую браузерную операцию):

```bash
PHOTO_F01_BACKEND_URL=http://127.0.0.1:8000 PYTHONPATH=.:streamlit-ui \
  .venv/runtime-env/bin/python -m streamlit run streamlit-ui/session_probe.py \
  --server.address 127.0.0.1 --server.port 8502 --server.headless true \
  --browser.gatherUsageStats false
```

Открыть `http://127.0.0.1:8502`, остановить Ctrl+C в этом терминале.
Этот просмотр не проверяет HTTPS, cookie и восстановление.
Не направлять стенд на старые `/sessions` как замену экспериментальному API.

После согласования backend/DevOps использовать тот же процесс с
`--server.baseUrlPath f01/ui`, `PHOTO_F01_BACKEND_URL` — адрес API с тестовыми
маршрутами. Ingress Dev должен направлять `/f01/ui` и `/f01/ui/*` (включая WSS)
на `host.docker.internal:8502`, GET context и четыре точных POST-пути — на backend.
Остальные `/f01/*`, включая `/f01/internal/*`, закрываются 404.
Origin браузера — `https://photoagent-dev.home.arpa`.
Не применять весь `/f01/*` как публичный API allowlist.
Обновление B-02: ingress теперь содержит точный allowlist; рабочие порты
эксперимента — API 8001 и UI 8503. Актуальные команды — в
[backend-протоколе](session-probe-backend.md#запуск-и-openapi).

Настройки UI читаются через BaseSettings: `PHOTO_F01_BACKEND_URL` (обязателен),
`PHOTO_F01_COOKIE_NAME` (по умолчанию выше), `PHOTO_F01_REQUEST_TIMEOUT_SECONDS`
(5), `PHOTO_F01_POLL_SECONDS` (3). Секретные параметры не нужны.

## Протокол совместной проверки Chrome и настоящего Safari

Записать версии macOS, Python, Streamlit, браузера и ревизию кода; использовать
отдельный тестовый профиль с синтетическими данными. Для каждого пункта записать
«пройден / дефект / не проверен», фактический результат и ограничения.
Не сохранять cookie, заголовки авторизации, HAR или дампы окружения.

Согласовано владельцем 2026-09-24: основной прогон — в чистом изолированном
профиле без расширений, дополнительный — в приватном режиме. Между независимыми
сценариями использовать новый контекст; внутри сценария refresh/reconnect/двух
вкладок сохранять нужный общий контекст, чтобы не уничтожить проверяемую сессию.
Приватный режим не означает полного отключения кеша и расширений.
Safari изолирует независимо открытые приватные вкладки; проверку общего диалога
выполнять в обычном чистом профиле с общей cookie. Приватные вкладки проверять
отдельно с учётом фактической изоляции браузера, не объявляя её дефектом backend.
Основания: [приватный Safari](https://support.apple.com/en-ph/guide/safari/ibrw1069/mac),
[расширения в приватном режиме](https://webkit.org/blog/15697/private-browsing-2-0/).

1. Первый вход: создать сессию; подтвердить атрибуты cookie без копирования значения,
   наличие cookie в UI и принятие серверного заголовка API. Записать тестовую отметку.
2. Refresh: сохранить ID/отметку, получить новую активность и срок. Отправка
   marker не повторяется. Повторные rerun и несколько циклов polling не меняют TTL.
3. Reconnect: временно разорвать только сетевое соединение тестовой вкладки;
   восстановить без reload. ID/отметка сохранены, last_activity_at не изменился.
4. Вторая вкладка: тот же ID и отметка; явное открытие может продлить TTL.
   В отдельном чистом профиле одновременно открыть две вкладки и начать сессию;
   обе должны получить один ID. Проверить также потерю ответа первого создания.
5. Очистка: отмена подтверждения ничего не меняет; подтверждение отзывает токен,
   сбрасывает cookie и очищает вторую вкладку на ближайшем опросе. Новый диалог
   создаётся явно и получает другой ID. Старая вкладка не восстанавливает удалённое.
6. CSRF: каждый POST без/с неверным Origin и CSRF отклоняется; GET не очищает.
   Другой профиль/неверный токен не получает snapshot. Внутренний маршрут закрыт ingress.
7. TTL/рестарт: совместно с backend использовать управляемые часы; ровно на границе
   сессия недоступна, reconnect/poll её не оживляют. Рестарт только отдельного
   экспериментального API согласовать, если он разделяет процесс с чьей-либо работой.

Safari проверяется вручную либо через safaridriver при разрешённой владельцем
Remote Automation. Недоступная автоматизация — ограничение проверки, не дефект
продукта. Эмуляция WebKit не заменяет установленный Safari.

## Результаты

Обновление: 2026-09-24 владелец подтвердил работу session_probe в Safari.
Ниже сохранены результаты первоначального frontend-прогона; последующий
backend-прогон и границы подтверждения Safari — в [протоколе B-02](session-probe-backend.md).

Проверено 2026-09-24: macOS 14.8.9, Python 3.14.7, Streamlit 1.63.0,
Google Chrome 153.0.8010.53. Safari установлен версии 26.6.1;
его сценарии F-01 пока не проверялись, доступность Remote Automation не подтверждена.

- `unittest discover -s tests -p '*_test.py'`: 46 тестов прошли, включая 7 новых
  проверок клиента/состояния UI (токен только в заголовке, безопасные ошибки,
  различение отзыва и сетевого сбоя, отсутствие автоматического retry).
- Chrome: 4 проверки JS-компонента с подменённым API прошли. Проверены refresh,
  повторное монтирование в том же документе, две первые вкладки, HttpOnly,
  подтверждение очистки и явный повтор после ошибки. Повторное монтирование
  не является проверкой настоящего разрыва/восстановления WSS.
- Пятая Chrome-проверка: живая оболочка Streamlit на `http://127.0.0.1:8502`
  показывает заголовок и четыре действия, исключений Streamlit нет.
  Экспериментальные маршруты в текущем API отсутствуют, поэтому сообщение
  «Браузерная операция не подтверждена» здесь ожидаемо.
- Ruff, проверка форматирования и `git diff --check` прошли.

Команды воспроизведения из корня:

```bash
PYTHONPATH=.:core-api:streamlit-ui .venv/runtime-env/bin/python -m unittest discover -s tests -p '*_test.py'
.venv/runtime-env/bin/python tests/session_probe_browser_check.py --ui-url http://127.0.0.1:8502
.venv/runtime-env/bin/ruff check .
.venv/runtime-env/bin/ruff format --check .
```

Без `--ui-url` проверяются только подмены; проверка живой оболочки помечается skipped.
Не проверены: реальное cookie → ingress → Streamlit → API, CSRF backend,
настоящий reconnect, отзыв между живыми вкладками, TTL, Safari и аварийная гонка
создания. Следующий шаг — согласовать/реализовать экспериментальные маршруты
с backend, настроить allowlist с DevOps и выполнить протокол выше.

| Участник | Результат для продолжения |
|---|---|
| Backend | Заключение по предложенному контракту: подтвердить или дать конкретные правки путей, схем, статусов, CSRF bootstrap/ротации, идемпотентности и обработки незавершённого создания. Затем реализовать экспериментальные маршруты, передать OpenAPI/примеры, команды запуска и способ управлять временем для TTL-тестов. | DevOps | После согласования контракта подключить `/f01/ui` с WSS и точный allowlist браузерных маршрутов к HTTPS Dev; внутренний snapshot оставить закрытым снаружи. Подтвердить Origin и доверенные proxy-заголовки |
| Архитектор (A-07) | Проверить предложенный механизм относительно утверждённого session-lifecycle, особенно гонки вкладок, потерю ответа создания и различение refresh/reconnect. После B-02 закрепить подтверждённый протокол; текущий кандидат не объявлять окончательным решением |
| Frontend + QA | Адаптировать клиент по согласованному контракту, выполнить протокол Chrome/настоящего Safari, отдельно записать обычный/приватный режим и ограничения автоматизации |
