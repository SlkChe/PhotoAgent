# B-02: backend-кандидат браузерного протокола

Дата: 2026-09-24. Ответственный: backend. Статус: реализован и проверяется на
отдельном стенде; работа session_probe в Safari подтверждена владельцем
2026-09-24. Окончательное решение A-07 остаётся открытым.
Дополняет [F-01](session-probe.md), не заменяет production-контракт B-01.

## Заключение по предложению frontend

Пути, методы, тела и поля snapshot из F-01 приняты для эксперимента без изменений.
Реализация — `core-api/photo_api/session_probe/`, отдельная фабрика FastAPI.
Она не подключена к приложению прототипа, не использует его UUID-доступ/heartbeat
и не вызывает LLM. Один процесс, RAM, TTL 43200 секунд, UTC.

- GET context создаёт только контекст CSRF. Cookie `__Host-photoagent-f01-context`
  имеет Secure, HttpOnly, SameSite=Lax, Path=/, без Domain и постоянного срока.
  Чужой Origin и Sec-Fetch-Site=cross-site отклоняются; CORS не включён.
  Без Origin GET допустим. Браузерные операции сериализуются Web Locks в F-01.
- CSRF — HMAC с привязкой к секретной cookie контекста и его поколению;
  сравнение выполняется без утечки по времени. POST требует точный Origin
  `https://photoagent-dev.home.arpa` и заголовок X-F01-CSRF. Proxy-заголовки
  не участвуют в решении о доступе; Uvicorn запускается с `--no-proxy-headers`.
- Сессионный bearer воспроизводимо выводится HMAC из контекста и случайного UUID
  сессии. В RAM хранятся хеши cookie/bearer и ключ процесса; исходные cookie
  не сохраняются. Повтор create восстанавливает Set-Cookie даже после потери
  ответа, не создаёт второй диалог и не продлевает TTL. Cookie контекста поэтому
  тоже является секретом восстановления и никогда не выдаётся JavaScript.
- request_id создания привязан к контексту. После отзыва/истечения прежний ID
  возвращает 409, пока контекст жив. Новый диалог требует нового явного действия.
  Журнал ограничен 256 ID; переполнение даёт 409 без вытеснения старой записи.
- opened учитывается один раз на ID документа; максимум 1024 ID на сессию,
  затем 409. Marker продлевает TTL и увеличивает revision. Повтор marker не
  идемпотентен: клиент не делает автоматический retry; это только синтетическая
  операция стенда, не контракт отправки сообщений MVP-1.
- Clear отзывает сессию и меняет поколение CSRF. Запоздавший POST со старым CSRF
  получает 403, поэтому не удалит новый диалог. Повтор после свежего context
  безопасен и возвращает 204 при уже пустом контексте. С действующей сессией
  дополнительно требуется её cookie. Потеря ответа clear исправляется чтением
  context; автоматическое создание не выполняется.
- Контекст сохраняется 24 часа после последнего create, но не удаляется раньше
  живой сессии. GET/poll не продлевают диалог. Не более 1000 контекстов по умолчанию
  (`PHOTO_PROBE_MAX_CONTEXTS`); переполнение — 503. Удаление просроченных данных
  выполняется при обращении и каждые 60 секунд. TTL проверяется до каждого доступа:
  ровно на границе чтение/мутация возвращают 401. Рестарт теряет всё состояние.
- Все ответы имеют Cache-Control:no-store. Ошибки: `{detail: stable_code}`;
  401 — доступ утрачен, 403 — Origin/контекст/CSRF, 409 — устаревшее действие или
  предел журнала, 422 — тело запроса, 503 — ёмкость. Сырых ошибок и токенов нет.

Ограничение кандидата: два первоначальных GET без общей cookie, выполненные
в обход Web Locks, могут создать разные контексты. Гарантия единого диалога
исследуется для штатного браузерного клиента, не для произвольных HTTP-клиентов.
Авария до получения первой cookie может оставить пустой контекст до очистки;
постоянная история при этом не создаётся. Архитектор должен оценить эту границу.

## Запуск и OpenAPI

Из корня, в отдельных терминалах; не запускать второй процесс на занятом порту:

```bash
PYTHONPATH=.:core-api .venv/runtime-env/bin/python -m uvicorn \
  photo_api.session_probe.app:create_app --factory --host 127.0.0.1 --port 8001 \
  --no-access-log --no-proxy-headers

PHOTO_F01_BACKEND_URL=http://127.0.0.1:8001 PYTHONPATH=.:streamlit-ui \
  .venv/runtime-env/bin/python -m streamlit run streamlit-ui/session_probe.py \
  --server.address 127.0.0.1 --server.port 8503 --server.baseUrlPath f01/ui \
  --server.headless true --browser.gatherUsageStats false
```

Рабочие ключи стенду не нужны. Для запуска использовалось очищенное окружение.
Swagger: `http://127.0.0.1:8001/docs`; JSON: `http://127.0.0.1:8001/openapi.json`.
Swagger на HTTP предназначен для чтения: Secure-cookie проверяются через HTTPS.
Браузерная точка входа: `https://photoagent-dev.home.arpa/f01/ui/`.

В `docker/ingress/Caddyfile` добавлены только GET context и четыре POST пути к
порту 8001; UI/WSS `/f01/ui` и `/f01/ui/*` идут к 8503. Остальные `/f01/*` — 404,
включая internal snapshot. Stage не получает эти маршруты. Конфигурация проверена
`caddy validate` и применена перезапуском ingress; API/UI Dev/Stage не перезапускались.
Остановить отдельные API/UI через Ctrl+C в терминалах. Общий ingress не останавливать.

## Воспроизводимые проверки и результаты

```bash
PYTHONPATH=.:core-api:streamlit-ui .venv/runtime-env/bin/python -m unittest \
  discover -s tests -p 'session_probe_api_test.py'
.venv/runtime-env/bin/python scripts/check_session_probe.py
```

Часы внедряются через `create_app(clock=...)` только в Python-тестах. Публичного
маршрута перемотки времени нет. Шесть backend-тестов проверяют потерю Set-Cookie,
разные ID создания, отзыв, повтор clear, CSRF/Origin, лимит контекстов, restart,
marker, неизменность TTL от чтения, дедупликацию opened и точную границу 12 часов.

Результат 2026-09-24: **3 живых теста Chrome прошли**.
Живой прогон Chrome использует новый обычный профиль без расширений, HTTPS с
проверкой сертификата, реальные backend/UI и синтетические данные. Проверяются:
HttpOnly-cookie → Streamlit → внутренний snapshot, marker/refresh, отключение сети
с явным закрытием WSS тестовой вкладки и проверкой нового соединения без reload,
две первые вкладки, очистка/новый ID, allowlist и CSRF.
Одного offline/online в Chrome оказалось недостаточно: существующий WSS оставался
открытым. Поэтому тест инструментирует WebSocket только в своём профиле, закрывает
его при offline и требует появления нового WSS после online; TTL не меняется.
Тест не сохраняет cookie, HAR и переписку. Работа session_probe в настоящем
Safari подтверждена владельцем 2026-09-24. Это ручное подтверждение владельца,
не результат автоматизации backend. По отдельным сценариям и приватному режиму
детальный протокол не предоставлен; их покрытие этим подтверждением не утверждается. Потеря ответа create проверена на backend,
аварийное закрытие настоящей вкладки в этот момент ещё требует браузерного прогона.

Обычный Dev-прототип на портах 8000/8501 во время проверки не был запущен;
его `/health` возвращал 502. Эксперимент использует собственные процессы;
готовность старого прототипа не является результатом B-02.

## Передача и оставшиеся действия

Backend-блокер «нет контракта/маршрутов» из F-01 устранён. Frontend/QA могут
повторить живой прогон, дополнить протокол по приватному режиму и сценарию аварии вкладки.
DevOps получает конкретный allowlist и порты для ревью. Архитектор получает
CSRF/recovery-кандидат и измерения для A-07; готовность MVP-1 не объявляется.
