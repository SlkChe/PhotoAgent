# Архитектурные задачи следующих этапов

Дата консолидации: 2026-09-21. Источник: записка о прототипе 0.1 от 2026-09-11,
коммит `ded8934` (ранее architect_notes.md, затем mvp-1/prototype-review.md),
отложенные разделы архитектуры и последующее обсуждение.

**Статус: предложения для будущего рассмотрения, не требования MVP-1 и не разрешение
на их реализацию.** Номер следующего этапа и его состав пока не утверждены.
Действующие границы: [цели MVP-1](mvp-1/purpose.md), [архитектура MVP-1](mvp-1/architect.md),
[жизненный цикл данных](mvp-1/session-lifecycle.md).

В MVP-1 уже выбраны анонимный текстовый диалог, RAM одного процесса API,
потеря переписки при перезапуске, удаление по TTL/очистке, одна сессия на браузерный
профиль и один облачный генератор из конфигурации. Сохраняемая 30 дней общая
статистика не является постоянной историей диалогов; её хранилище относится к A-06.

## Предложения, требующие пересмотра решений MVP-1

| Предложение | Какое ограничение потребуется пересмотреть | Когда рассматривать |
|---|---|---|
| Аккаунты и подтверждённая личность | Сейчас пользователь представлен только временной сессией, доступ ограничен приватной сетью | На следующем этапе, при согласовании регистрации |
| Постоянная история и PostgreSQL | Сейчас сообщения и контекст находятся в RAM и удаляются с сессией/при перезапуске | Когда нужна история между посещениями или устройствами |
| Раздельные сроки входа, рабочего контекста и истории | Сейчас одна временная сессия владеет всем диалогом | Вместе с аккаунтами и сохраняемыми диалогами |
| «Новый чат» сохраняет предыдущий | Сейчас один диалог на браузерный профиль; новый диалог завершает текущий | Вместе со списком сохраняемых диалогов |
| Несколько API workers или экземпляров | RAM одного процесса не обеспечивает общее состояние, блокировки и дедупликацию | После измерений, подтвердивших необходимость масштабирования |
| Сохраняемые задания и защита от дублей после перезапуска | Сейчас задания и ключи request_id исчезают с сессией | При требовании продолжать длительную работу после перезапуска |
| Продолжение разговора с нескольких устройств | Cookie MVP-1 не устанавливает постоянную личность человека | После появления подтверждённого владельца |
| Фотографии и объектное хранилище | MVP-1 — текстовый образовательный модуль, без загрузки/анализа фотографий | При отдельном согласовании работы с изображениями |
| Кеш результатов в core-api | Действующие правила запрещают кеширование backend; рабочее состояние сессии не является кешем | Только по измеренной необходимости и отдельному решению |
| Отдельные микросервисы по темам | MVP-1 — модульный монолит, темы являются метками и профилями поиска | Если появятся независимые требования по нагрузке, развёртыванию или владельцам компонентов |

## Регистрация, модель данных и права доступа

Рассмотреть отдельные сущности:

| Сущность | Назначение и предполагаемый жизненный цикл |
|---|---|
| Пользователь | Владелец настроек и диалогов, до удаления учётной записи |
| Сохраняемый диалог | История, принадлежащая пользователю; собственные правила хранения и удаления |
| Сообщение | Реплика пользователя или ассистента, порядок и время; хранится с диалогом |
| Рабочая сессия | Временное состояние взаимодействия и свой TTL |
| Выполнение | Принятое сообщение, статус обработки, результат/ошибка и срок хранения результата |

Срок входа пользователя не объединять с TTL рабочего контекста. Текущий анонимный
session_id не превращать автоматически в user_id. Перенос анонимного диалога
на учётную запись потребует отдельного решения и подтверждения права на него.

В качестве варианта входа рассмотреть OpenID Connect. Отдельно спроектировать
передачу подтверждённой личности между UI и API: вход в Streamlit сам по себе
не заменяет авторизацию HTTP API, а присланное клиентом поле user_id не является
доказательством личности. Backend проверяет владельца на каждом обращении.
Секреты по-прежнему поступают из окружения процесса; не вводить st.secrets или
хранение ключей в файлах как побочный эффект интеграции.

Проверки: пользователь A не может читать, продолжать, изменять или удалять диалог B,
в том числе прямым вызовом API. Для нескольких вкладок/устройств согласовать
одновременное редактирование, порядок сообщений и конфликты версий.

## Сохраняемая история и постоянное хранилище

Рассмотреть одну PostgreSQL-базу, доступную только core-api; UI работает через API.
Начальные данные:

- диалог: ID, владелец, название, время создания/изменения, режим хранения;
- сообщение: ID, диалог, автор, порядок, время, содержимое;
- выполнение: ID, исходное сообщение, request_id, статус, результат или ошибка.

Согласовать сохранение автоматически, по явному действию либо два режима — временный
и сохраняемый. Для сохраняемого диалога «Новый чат» создаёт новый, не удаляя прежний;
«Удалить диалог» — отдельное действие. Закрытие вкладки и истечение рабочего TTL
не должны уничтожать постоянную историю. Очистка рабочих данных и удаление истории
получают разные семантику и пользовательские действия.

Проверку повторной отправки перенести в устойчивое хранилище, например через
уникальность `(conversation_id, request_id)`. Проверить сохранение гарантии между
процессами API и после перезапуска. Не держать транзакцию БД во время поиска/LLM;
фиксировать состояния короткими операциями, предусмотреть согласование конкуренции.

Подготовить новые миграции, резервное копирование и проверку восстановления.
Политика удаления должна учитывать сообщения, результаты, вложения и сроки хранения
резервных копий. Постоянная БД для истории не требует введения кеша backend.

## Масштабирование и длительные выполнения

При нескольких экземплярах API нужны общее хранилище, согласование изменений
конкретного диалога и общий механизм защиты от дублей; увеличение workers без
этих изменений не решает задачу. Не переносить общую блокировку всех пользователей
из RAM в БД или внешнюю очередь.

Если требуется продолжение работы после перезапуска, рассмотреть фоновых исполнителей
с сохраняемыми заданиями, статусами и результатами. Возвращение пользователя должно
позволять получить уже начатый результат без повторной оплаты и дублирования сообщений.
Отдельно определить отмену, повтор после сбоя, таймаут, блокировку/аренду задания
и правила его восстановления. Лимиты частоты и одновременных заданий после регистрации
применять к подтверждённому владельцу.

Обосновывать инфраструктуру измерениями: число активных пользователей, интенсивность
запросов, допустимое время ответа, очередь, ошибки, ресурсы и квоты внешних систем.
Лимит 1000 записей сессий в прототипе не является доказательством ёмкости сервиса.

## История и контекст модели

Отдельный компонент подготовки контекста выбирает релевантные сообщения и резюме
из истории, соблюдая ограничения объёма. При появлении постоянных диалогов рабочий
контекст должен восстанавливаться из них; истечение TTL производного контекста
не удаляет первичные сообщения. Для поиска по большой сохраняемой истории можно
проверить семантический поиск и отдельную векторную БД, только при подтверждённой
потребности. Предварительное индексирование всего интернета не является целью.

## Фотографии и расширение сценариев

При отдельном согласовании загрузки фотографий: файлы размещать в объектном
хранилище, метаданные и связи с сообщениями — в БД. Определить ограничения размеров,
доступ, обработку и удаление вместе с резервными копиями.

Каркас прототипа «Теория · Поиск · Разбор кадров» и исходная диаграмма с PostgreSQL
не являются схемой MVP-1. Расширение на анализ кадров и другие задачи общего
ассистента фотографа требует новой фиксации границ; текущие пять тематик описывают
образовательный текстовый модуль. Самостоятельные агенты с независимой памятью
не следуют автоматически из расширения предметной области.

## Развитие интерфейса

Для сохраняемых диалогов добавить вход, список разговоров, восстановление истории
и продолжение. Историю большого объёма загружать порциями. API остаётся источником
данных, st.session_state — состоянием отображения.

После согласования нескольких устройств определить синхронизацию и конкуренцию
в одном диалоге. При масштабировании Streamlit учитывать WebSocket и привязку
пользовательской сессии к серверу. Другой frontend выбирать по требованиям к UX
и измеренной нагрузке, а не как обязательную часть регистрации.

## Явная маршрутизация между MCP

Условное развитие из обсуждения: если пилот выявит специализацию нескольких MCP,
можно добавить явную локальную маршрутизацию по признакам запроса. Задать и проверить
правила выбора зарегистрированных инструментов, бюджет и наблюдаемость выбора.
Это требует дополнения алгоритма и конфигурации, но не предполагает автоматического
переключения на другой сервер после сбоя. В первой реализации MVP-1 MCP выбирается
конфигурацией развёртывания. Это возможное развитие по результатам эксплуатации,
не обязательная задача текущего этапа.

## Сценарий приёмки этапа с регистрацией

Вход → создание диалога → отправка сообщений → выход → возвращение и продолжение.
Проверить:

- сохранение истории после перезапуска API и повторного входа;
- независимость истории от TTL рабочего контекста и кнопки «Новый чат»;
- изоляцию владельцев, включая прямые запросы к API;
- отсутствие дублей после повторной доставки и перезапуска;
- корректную подготовку контекста из сохранённого диалога.

До реализации согласовать режим сохранения/удаления, способ входа, передачу личности,
нагрузку и необходимость работы с нескольких устройств. Старое предложение внедрить
аккаунты и БД до подключения реальных ИИ-обработчиков не применяется к MVP-1:
текущий порядок — сначала локальный анализ, поиск и генерация во временной сессии.

Исторические наблюдения от 2026-09-11: доступ по UUID, глобальная блокировка
SessionStore.send(), отсутствие собственных ID/времени сообщений и статусов выполнений
требуют исправлений в MVP-1. Общий жизненный цикл истории/сессии и потеря RAM после
перезапуска теперь являются согласованными ограничениями временного режима.
Они станут проблемами только при новых требованиях о постоянной истории.
Перенос документов не является отчётом об устранении проблем в коде.
