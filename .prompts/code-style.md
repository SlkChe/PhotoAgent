# Общие правила ведения проекта, Code Style и безопасности

**Твоя обязанность:**
— Cледить за чистотой кодовой базы, безопасностью данных и архитектурной целостностью репозитория.
- Создавай локаничный компактный код, длина функции не более 70 строк, при необходимости декомпозируй алгоритм.

## Безопасность и управление конфигурацией (Credentials & Env)
- **Источник секретов:** Приложение получает секреты из окружения процесса при запуске. В Python-коде допускаются имена переменных, но не реальные значения паролей, токенов, API-ключей, строк подключения с учётными данными или запасные рабочие ключи. Файловое хранение запрещено, кроме согласованного локального исключения ниже.
- **Локальная отладка:** Разработчик вводит ключ через скрытый запрос в терминале. Запускаемый из этого терминала сервис или отладчик наследует окружение. Значение не должно попадать в текст команды, историю shell или конфигурацию запуска IDE.
- **Чтение и проверка:** Каждый сервис использует собственный класс `BaseSettings` из `pydantic-settings` для чтения и валидации окружения. Обязательные секреты проверяй при запуске. Сообщение об ошибке должно содержать название отсутствующего или некорректного параметра, но не его значение. Загрузка `.env` не обязательна.
- **Разделение доступа:** Ключи ИИ-провайдера и поисковых сервисов получает только `core-api`. В `streamlit-ui` передавай лишь необходимые ему настройки и, если потребуется, отдельный секрет для доступа к бэкенду. Оба сервиса читают конфигурацию через `BaseSettings`; `st.secrets` не используется.
- **Файлы конфигурации:** `.env` допускается только для несекретных локальных настроек: портов, адреса бэкенда, режима запуска. Не создавай и не изменяй `.env` и `.env.local` без согласования. Их исключение из Git — дополнительная защита, а не способ защищённого хранения секретов.
- **Файл-шаблон:** При добавлении переменных обновляй `.env.example`: указывай названия параметров и безопасные примеры несекретных настроек; значения секретов оставляй пустыми. Реальные локальные файлы окружения не должны попадать в коммиты.
- **Логи и интерфейс:** Не выводи секреты, заголовки авторизации и полный объект настроек в логи, ответы API, UI или диагностические отчёты, в том числе при ошибках валидации конфигурации.
- **Тесты:** Автоматические тесты используют фиктивные значения и подмену внешних вызовов. Для ручной отладки используй отдельные ключи разработки с ограниченными правами и расходами.

### Локальное исключение для Dev и HTTPS на Mac

Утверждено владельцем 2026-09-23. Исключение разрешает хранить секреты приложения
Dev в `.devsec/.env.local`, а ключи и сертификаты локальной HTTPS-инфраструктуры
Mac в `.devsec/ssl/`. Локальный ingress может обслуживать Dev и Stage.
Секреты приложения Stage/Prod и TLS-ключи будущего VPS под исключение не попадают.
Это исключение имеет приоритет над общим запретом файлового хранения для указанных
путей и назначения; оно не разрешает размещать секреты в корневых `.env`/`.env.local`.

- До создания секретов исключи всю `.devsec/` из Git и Docker-контекста.
  Не добавляй содержимое принудительно в Git, образы, архивы передачи, облачную
  синхронизацию или диагностические выгрузки. Ignore не защищает уже отслеживаемые файлы.
- Создавай каталоги с правами `700`, секретные файлы — `600`, используя `umask 077`.
  Эти права не защищают от процессов того же пользователя или администратора.
- Dev-запуск явно читает `.devsec/.env.local` как данные, не исполняет через `source`,
  и передаёт разрешённые параметры только нужному дочернему процессу.
  Приложения продолжают использовать `BaseSettings`; автопоиск секретных файлов
  приложением не вводится. Не печатай значения и не передавай их в аргументах команд.
- Ключи Dev должны иметь отдельные права и бюджет. Секреты приложения не передаются
  ingress, UI или mock. Не монтируй всю `.devsec/` в контейнер.
- Разделяй ключ CA и серверные ключи. Обычный ingress получает только необходимые
  серверные сертификаты/ключи на чтение; ключ CA доступен лишь операции выпуска.
  На клиентские устройства передаётся публичный сертификат CA, никогда его ключ.
- Содержимое `.devsec/.env.local` заполняет владелец локально; не запрашивай реальные
  ключи в чате. Утверждение исключения само по себе не разрешает читать или выводить
  имеющиеся секреты. При утечке ключи заменяются, одного удаления файла недостаточно.


## Правила форматирования исходного кода и стандарты Python (Code Style)
-**Базовый стандарт:** Код должен строго соответствовать PEP 8.
-**Инструменты линтинга:** Мы используем Ruff, включая категории правил E, W, N, F, I и форматировщик 'ruff format'.
-**Современная типизация (Type Hinting):**
  - Обязательно типизируй все аргументы функций и возвращаемые значения.
  - Используй встроенные generic-типы: 'list[str]' вместо 'typing.List[str]', и 'dict[str, int]' вместо 'typing.Dict'.
  - Используй оператор '|' для объединения типов: 'int | None' вместо устаревего 'Optional[int]'.
-**Структура импортов:** Группируй импорты в следующем порядке:
1. Стандартные библиотеки Python ('os', 'sys', 'json').
2. Сторонние библиотеки ('fastapi', 'pydantic', 'streamlit').
3. Локальные модули и пакеты проекта; пути импортов должны соответствовать фактической структуре приложения.

## Культура ведения репозитория
- При создании обычного Python-пакета добавляй в его каталог `__init__.py`. Для каждого нового модуля отдельный `__init__.py` не требуется. Существующий `__init__.py` не перезаписывай автоматически.
- Для имён Python-модулей и каталогов импортируемых пакетов используй `snake_case`; для каталогов сервисов и документов — `kebab-case`. Сохраняй стандартные имена файлов, перечисленные в `AGENTS.md`.
- Не используй тип `typing.Any`. Встроенная функция `any()` разрешена.
- Принятые проектные решения фиксируй в `decisions.md`, указывая дату, решение, область применения и статус. Переноси требования в целевые документы; удаляй рабочую запись только после ознакомления участников и подтверждённого переноса этих документов в `main`, согласно `AGENTS.md`.
- Пиши комментарии к коду только там, где логика неочевидна (архитектурные хаки, оптимизации). Не комментируй очевидный код.
- Комментарии и документацию (Docstrings) пиши на русском языке, а имена переменных, функций и классов — строго на английском.
